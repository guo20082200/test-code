# MySQL 面试题 —— 架构、高可用与性能优化

> 适用岗位：中高级后端 / DBA。架构能力从"会用"到"能设计"的分水岭在主从、高可用与容量规划。

---

## 一、日志体系（必考）

1. redo log 追问链：
   - 为什么需要 redo（WAL 预写日志思想：先写日志后改数据，崩溃后重放）？
   - 物理日志 vs 逻辑日志的本质（记录页的物理变更 vs 记录 SQL 语义）；
   - LSN、checkpoint 机制（脏页列表怎么推进）、`innodb_log_file_size` 与 `innodb_log_buffer_size` 怎么定？
2. binlog 追问链：
   - statement / row / mixed 三种格式的区别与选型（row 的优劣势、为什么现在主流 row）；
   - binlog 的写入时机（事务提交时）与 `sync_binlog` 参数；
   - binlog 与 redo log 的**两阶段提交**（prepare → commit）：崩溃恢复时怎么判断事务是否提交（redo 有 prepare + binlog 有完整事务才提交）？为什么必须有这个顺序——没有两阶段提交会怎样（主从不一致）？
   - binlog 的用途盘点：主从复制、Canal 监听（数据同步到 ES/数仓/缓存）、闪回、误删恢复。
3. undo log 与 MVCC/回滚的关系；undo 表空间膨胀与回收（`innodb_max_undo_log_size`、purge 线程）。

## 二、主从复制（必考）

4. 复制原理完整链路：
   - 主库 binlog → dump 线程 → 从库 IO 线程（relay log）→ SQL 线程回放；
   - 半同步复制（semi-sync）与异步复制的差异与崩溃窗口；
   - `sync_binlog=1` + `innodb_flush_log_at_trx_commit=1` + 半同步的组合是什么（组提交 + 主从均不丢）？
5. 主从延迟追问链（必考）：
   - 延迟指标怎么看（`SHOW SLAVE STATUS` 的 Seconds_Behind_Master 的局限）；延迟产生的根因清单：大事务、DDL、单线程 SQL 回放、从库负载、锁冲突、机器差异；
   - 并行复制（MTS）：`slave_parallel_workers`、基于库的并行 vs 基于 WRITESET 的并行（`slave_parallel_type=LOGICAL_CLOCK`），为什么后者能跨库并行；
   - 延迟治理方案：拆分大事务、读写分离路由（延迟敏感走主库）、强制走主、并行复制调优、从库扩展；
   - 场景题：双十一期间从库延迟 30 秒导致报表数据不准，你的止损与根治方案。
6. 复制拓扑与切换：
   - 主主复制（双写）的冲突风险；一主多从 + 级联复制的场景；
   - 主从切换流程（MHA / MGR / 手动 failover）：切换时怎么保证不丢数据（等 binlog 追平 / 半同步 / 5.7 的 `WAIT_FOR_EXECUTED_GTID_SET`）；
   - GTID 复制 vs 基于位点（file+pos）复制：GTID 解决什么问题（自动定位位点）、`gtid_executed` 与跳过错误事务（`gtid_purged`）。
7. 读写分离架构：
   - 应用层路由（Sharding-JDBC）vs 中间件（ProxySQL / MyCat / MaxScale）的对比；
   - 延迟导致的读写不一致（写完马上读）处理：强制路由主库、延迟容忍、缓存桥接；
   - 从库负载均衡与故障摘除的机制（ProxySQL 健康检查）。

## 三、高可用与备份恢复

8. 高可用方案对比追问链（架构题）：
   - 主从 + MHA 的切换时间、脑裂防护；
   - MySQL Group Replication（MGR）：Paxos 组通信、单主/多主模式、什么场景用；
   - 传统方案 vs MGR vs 云厂商 RDS 高可用的取舍；
   - 脑裂怎么防：MHA 的 fencing、半同步丢主后的数据补齐策略。
9. 备份与恢复（必考，区分运维实战）：
   - 逻辑备份（mysqldump）vs 物理备份（XtraBackup）的区别与选择；`--single-transaction` 一致性快照原理；
   - 完整备份 + binlog 增量恢复的演练：某天误删一张表，恢复到删除前一刻的完整步骤（全量恢复 → 追 binlog 到指定位点）；
   - 备份的验证（定期恢复演练）与备份监控（备份失败告警、备份大小变化）；
   - XtraBackup 的原理（拷贝 + redo 追平）为什么能做在线物理备份。
10. 场景题：让你设计数据库高可用 + 灾备方案（RPO/RTO 目标怎么定），主库在机房 A、备库在机房 B，给出复制架构、切换预案、演练计划。

## 四、分库分表（必考）

11. 分库分表时机判断追问链：
    - 单库瓶颈的信号清单：CPU、连接数、磁盘 IO、单表数据量（多大该分？经验值 vs 实际依据）；
    - 为什么不建议"为了分而分"：带来的问题清单（分布式事务、跨库 join、全局排序分页、扩容、聚合）；
    - 先做哪些低代价优化（归档、读写分离、缓存、索引、分区表）？
12. 分片键设计追问链：
    - 分片键怎么选（与查询模式匹配：按用户 ID 分 → 商家视角查询怎么处理）；
    - 分片键的"基因法"：怎么让按订单号也能路由到正确分片（订单号里嵌入用户 ID 后缀）？
    - 非分片键查询的兜底：异构索引（额外同步一张映射表/宽表）、广播表（字典表全分片复制）、双写双分片。
13. 分库分表中间件对比：ShardingSphere（客户端 jar，SQL 解析改写）vs MyCat / 自研 proxy（服务端）的架构差异与取舍；数据迁移怎么做（双写 + 全量对账 + 切读的完整步骤）。
14. 扩容方案追问链（高频）：
    - 翻倍扩容（2→4→8，用 `% n` 取模的再哈希，为什么 2 的幂好迁）vs 一致性哈希（虚拟节点、迁移数据量）vs 目录表（映射再映射）；
    - 一致性哈希的"哈希偏斜"问题怎么缓解；
    - 在线扩容不停机的迁移流程设计（新库 → 双写 → 历史数据迁移 → 校验 → 切读 → 下线）。
15. 全局唯一 ID（分片后必答）：雪花算法（位结构、时钟回拨处理）、号段模式（Leaf-segment，双 buffer 预取）、Redis incr——分别适合什么量级。

## 五、性能优化与监控

16. 性能优化方法论（给一个真实案例模板）：
    - 一条 SQL 从慢到快的完整优化流程：EXPLAIN → 索引调整 → 改写 SQL → 参数调整 → 架构调整（缓存/分库）逐级升级的决策依据；
    - 批量操作优化：`INSERT ... VALUES` 多条合并、批量 UPDATE 的分批（大事务拆小）、`LOAD DATA`。
17. 参数调优清单：连接数（max_connections 与线程池）、innodb_buffer_pool_size（>75% 物理内存的经验与依据）、innodb_io_capacity 与刷脏（innodb_max_dirty_pages_pct）、sort_buffer_size/join_buffer_size 的合理值（为什么不能盲目调大——per-session 内存）。
18. 监控体系：核心指标清单（QPS、TPS、连接数、慢查询数、Buffer Pool 命中率、复制延迟、磁盘 IO 与容量）；哪些告警必须配、误报怎么治理；`performance_schema` / `sys` 库的常用排查语句。
19. 磁盘与容量规划：IOPS 与延迟对 MySQL 的影响（机械盘 vs SSD vs NVMe）、redo/undo/binlog 的 IO 模式差异、磁盘空间告警的紧急处理（删 binlog/扩容/迁移）。
20. 场景题：
    - 线上数据库 CPU 100% 的完整排查树（慢 SQL 定位 → explain → 优化 → 兜底限流）；
    - 从库磁盘要满了，但 binlog 又必须保留两天——给出方案（压缩、异地存储、重新评估保留策略）；
    - 给一个"月度千万级新增流水表"做容量规划与归档设计。
