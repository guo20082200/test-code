# 数据库面试题 —— MySQL 与 PostgreSQL 对比与选型

> 适用岗位：中高级后端 / 架构方向。对比题是近年面试增长最快的板块，考察的是"能不能脱离惯性做技术判断"。

---

## 一、核心机制对比（必考）

1. 架构模型对比追问链：
   - 进程模型（PG 一连接一进程）vs 线程模型（MySQL 一连接一线程）在连接数、内存、稳定性上的差异；这决定了两者在高连接并发下的不同表现；
   - 两者对"高并发短连接"的适配策略（PG 需要 PgBouncer 连接池，MySQL 为什么相对宽容）。
2. MVCC 实现对比追问链（最高频）：
   - MySQL：原地更新 + undo 版本链（旧版本在 undo log）；PG：新行插入 + xmin/xmax 标记（旧版本留在表里）；
   - 由此推导两个结论：MySQL 的 UPDATE 不产生"表膨胀"但 undo 膨胀；PG 的 UPDATE 产生表膨胀但读快照的代价更低（无 undo 链回滚）；
   - 快照语义：MySQL 的 ReadView 判断 vs PG 的 xmin/xmax + 快照结构（pg_current_snapshot 的 xip 数组），两者都是"快照隔离"，谁更纯粹（PG 的 RR 无幻读 vs MySQL RR 仍有幻读）；
   - 高频 UPDATE 场景分别谁更有优势：为什么"账本/计数高频更新"在 PG 上要特别小心（膨胀），MySQL 更合适？
3. 索引体系对比追问链：
   - 聚簇索引（MySQL 必须有主键、二级索引存主键值）vs 无聚簇索引（PG 堆表 + 独立索引、任何列可唯一）；
   - 覆盖索引的达成路径差异：MySQL 靠二级索引包含所有查询列；PG 靠 INDEX-Only Scan + VM（可见性映射），追问：PG 的 Index Only Scan 在什么情况下会退化成回表（VM 未设置、真空未跑）；
   - 索引类型广度：PG 的 GIN/GiST/BRIN/Hash/部分/表达式索引 vs MySQL 的 B+ 树 + 空间索引 R-tree 的适用边界；
   - 为什么 PG 的"无主键表"也能正常工作而 MySQL 会生成隐藏 rowid（性能注意点）。
4. 事务与隔离对比：PG 的 RR 真无幻读（纯快照）vs MySQL RR 用间隙锁防幻读——两种方案的代价对比（PG 的写冲突直接报错需要重试 vs MySQL 的间隙锁阻塞与死锁风险），"乐观 vs 悲观"的思想差异在哪。

## 二、复制与高可用对比

5. 复制机制对比追问链：
   - MySQL：binlog（逻辑）→ 从库 SQL 线程回放；PG：WAL（物理）→ 从库直接重放，几乎没有"回放成本"；
   - 延迟对比：PG 物理复制的追平速度 vs MySQL 逻辑复制的追平速度；两者在大事务、DDL 下的表现差异（PG 的 DDL 也是 WAL 重放，从库无 DDL 阻塞？——追问 DDL 在 PG 从库是否也锁表）；
   - 版本兼容：PG 物理复制要求主从同大版本（逻辑复制可跨版本）vs MySQL binlog 的兼容性；
   - 高可用方案对比：Patroni + 共识（etcd）vs MHA/MGR/Orchestrator——自动切换的成熟度与脑裂防护。
6. 读扩展对比：PG 的 hot standby（从库只读，无 WAL 应用延迟读阻塞）vs MySQL 从库的 binlog 回放与查询互不影响；两边"从库查询慢"的根因差异。

## 三、功能能力对比（特色功能）

7. 数据类型与 SQL 能力对比：
   - PG 类型丰富度（数组、范围、枚举、复合、几何、网络地址、JSONB vs MySQL 的 JSON）——什么场景这些类型成为选 PG 的理由；
   - 窗口函数、CTE 递归、`DISTINCT ON`、`RETURNING` 子句（PG 独有）、upsert 的语法差异（`ON CONFLICT DO UPDATE` vs MySQL `ON DUPLICATE KEY UPDATE` 的语义差异：MySQL 的"唯一键冲突会消耗自增 ID"的坑）；
   - MySQL 8.0 追平的能力（CTE、窗口函数、CHECK 约束生效）——现在还有哪些是 MySQL 仍不如 PG 的（部分索引、表达式索引的丰富度、扩展生态）。
8. JSON 能力对比：MySQL JSON（二进制存储但无独立检索类型、虚拟列 + 生成列索引）vs PG JSONB（GIN 索引、`jsonb_path_ops`）——高频 JSON 检索场景的选型结论。
9. 全文检索对比：MySQL 的 FULLTEXT（ngram 中文分词）vs PG 的 tsvector + 中文扩展——都只是"够用"，什么时候两者都该换 ES。

## 四、运维与生态对比

10. 备份恢复对比：MySQL 的 XtraBackup / 闪回（binlog）vs PG 的 PITR（基础备份 + WAL 重放 + recovery_target）、pg_rewind 快速追赶——误删数据的恢复速度哪个更占优；
11. 高并发读写场景的生态对比：
    - MySQL：读写分离 + 分库分表（ShardingSphere）成熟度高；PG：原生分区 + 逻辑复制 + Citus（分布式扩展，shared-nothing）的路线；
    - 各自的分布式方案成熟度、社区人才储备、公司既有架构的迁移成本——给出你的"改造 vs 迁移"判断框架。
12. 版本演进关注点：MySQL 8.0 的 New Data Dictionary / 原子 DDL / clone 插件；PG 16/17 的改进（逻辑复制改进、并行能力、`pg_stat_io`）——你关注了哪些，生产升级到哪一版，为什么。

## 五、选型决策（架构题）

13. 选型决策追问链（压轴）：
    - 新项目让你选型 MySQL or PG，给一个带权重的评估矩阵（事务复杂度、JSON 需求、读写比例、运维团队熟悉度、扩展路径、云厂商支持、成本）；
    - 分别给三个场景下结论：① 电商核心交易系统 ② 数据密集型分析/报表库 ③ 多租户 SaaS（JSONB + RLS）——为什么这么选；
    - 反直觉题：什么情况下 PG 反而该被换成 MySQL（团队能力、分库分表路线、既有中间件生态）？
14. 迁移与双跑：从 MySQL 迁 PG（或反向）的适配清单与风险清单（SQL 兼容、序列、事务重试、连接池、监控盲区）；双写方案（怎么保证两边一致 + 对账）与切换流程。
15. 开放题：你更看好 MySQL 还是 PG 的未来生态？给依据（社区、云厂商策略、PG 的扩展能力 vs MySQL 的简单可靠），表达观点并说明为什么，避免"中立到底"。

## 附：评估要点

| 维度 | 权重 | 观察点 |
|---|---|---|
| 机制对比 | 40% | MVCC/索引差异能现场推导、不背书 |
| 复制与高可用 | 20% | 物理 vs 逻辑复制本质、方案选型 |
| 功能能力 | 20% | 特色功能场景、版本追平意识 |
| 选型决策 | 20% | 评估矩阵完整、敢于下结论有依据 |

**判定要点**：能说"PG 无聚簇索引、MySQL 有 undo"算中级；能推演两者 MVCC 差异的连锁影响（膨胀、快照、幻读）算高级；能承担迁移决策、给完整评估矩阵并推动落地算资深。
