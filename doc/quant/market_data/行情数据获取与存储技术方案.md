# 行情数据获取与存储技术方案

> 阶段目标：打通量化系统的**数据地基**——通过 Twelve Data 行情接口拉取数据，落地到 PostgreSQL，为后续指标计算、回测、实盘信号提供统一数据源。
>
> 关联文档：[time_series](TwelveData-time_series接口文档.md) · [quote](TwelveData-quote接口文档.md) · [eod](TwelveData-eod接口文档.md) · [time_series_cross](TwelveData-time_series_cross接口文档.md) · [earliest_timestamp](../asset_catalogs/10-最早时间戳-earliest_timestamp.md) · [exchange_schedule](../asset_catalogs/12-交易所交易时间表-exchange_schedule.md)

## 1. 现状与约束

| 项 | 现状 |
|---|---|
| 技术栈 | Spring Boot 4.1.1 + Java 17 + WebClient（pom 已含 `spring-boot-starter-webclient`） |
| 已有资产 | `http/dto/twelvedata/` 下 4 个行情响应 DTO；`application.properties` 已配置行情接口地址与 apikey |
| 缺口 | pom 无数据库依赖；无数据同步模块；apikey 明文写在配置文件（需迁移至环境变量） |

**核心约束**：
1. `time_series` 计费 **1 credit / symbol / 请求**（与 `outputsize`、`interval` 无关），成本可控但受套餐限速（Basic 8 次/分钟 起，套餐越高限速越宽）
2. 每次请求最多返回 5000 根 K 线，更早历史需分页拉取
3. 数据可能被修正（复权、错误回补），入库必须支持**幂等覆盖**

## 2. 总体架构

```
┌─────────────┐   ┌──────────────┐   ┌─────────────┐   ┌──────────────┐
│ 调度器       │ → │ 配额检查      │ → │ 拉取器       │ → │ 入库器        │
│ Scheduled    │   │ /api_usage   │   │ WebClient   │   │ JDBC batch   │
└─────────────┘   └──────────────┘   └─────────────┘   └──────────────┘
      ↑                  ↓                  ↓                  ↓
┌─────────────────────────────────────────────────────────────────────┐
│ PostgreSQL：标的池 / K线表 / 同步游标 / 拉取日志                        │
└─────────────────────────────────────────────────────────────────────┘
```

四个职责分离的组件：

| 组件 | 职责 | 对应实现建议 |
|---|---|---|
| 调度器 | 定时触发 + 交易时段感知 | Spring `@Scheduled`，结合 `exchange_schedule` 数据判断开市 |
| 配额检查 | 调用 `/api_usage` 判断剩余额度，不足则跳过本轮 | 简单包装类，1 credit/次 |
| 拉取器 | 按 symbol+interval 请求 time_series，处理分页 | 复用现有 WebClient 配置与 `TimeSeriesResponse` DTO |
| 入库器 | 批量 upsert 写入 PG，更新同步游标 | MyBatis-Plus Mapper（手写 SQL）+ `ON CONFLICT` |

## 3. 数据库设计

> 可执行 DDL 已落盘：[schema.sql](schema.sql)（含建表、约束、索引与字段注释），建库时直接执行即可。

### 3.1 表清单

| 表 | 用途 |
|---|---|
| `td_symbol` | 标的池（要跟踪哪些 symbol、来自哪个交易所） |
| `td_bar` | K 线数据（所有 interval 共用一张表，主键区分） |
| `td_sync_cursor` | 同步游标（每个 symbol+interval 已同步到的时间） |
| `td_fetch_log` | 拉取日志（每次任务的结果、credits 消耗） |

### 3.2 DDL

> 完整可执行 DDL（含索引、注释）以 [schema.sql](schema.sql) 为准，本文不重复维护副本。要点：
> - `td_bar` / `td_sync_cursor` 以 **symbol 代码**（`VARCHAR(32)`）关联标的，逻辑外键不建 FK 约束，入库路径零 JOIN
> - `td_bar` 唯一键 `(symbol, interval, bar_time)`，代理主键 `id BIGSERIAL` 兼容 MyBatis-Plus
> - `td_symbol` 除标识与分类外，还落盘接口 meta 属性（`instrument_type` / `currency` / `exchange_timezone`）

### 3.3 关键设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 价格类型 | `NUMERIC(18,8)`，不用 float | 金融数据禁用浮点累计误差 |
| 时区 | 统一存 UTC（`TIMESTAMPTZ`） | API 响应的 datetime 带交易所时区，入库前统一转 UTC，查询时再按需转 |
| 幂等写入 | `INSERT ... ON CONFLICT (symbol, interval, bar_time) DO UPDATE` | 复权/回补数据自动覆盖旧值 |
| bar 表关联键 | 直接存 `symbol` 代码，不用 FK | 零 JOIN 入库；同一 symbol 跨交易所重名时以 `symbol:exchange` 形式区分（见下注） |
| 单表 vs 多表 | 所有 interval 共用 `td_bar` | interval 值域小且固定，减少表数量；数据量大后按 interval+时间分区 |
| 原始 JSON 存档 | 暂不存 | K 线字段固定，无需回放原始报文；后续如需审计再加 |

> **重名风险注**：`td_symbol` 的唯一键是 `(symbol, exchange, asset_type)`，而 `td_bar` 只以 symbol 为键。若同一代码在多个交易所上市且都需要跟踪（如 BRK.A/B、两地上市公司），入库时将 symbol 写成 `MSFT` 或 `AAPL:XNYS` 的复合形式即可保持唯一——是否启用取决于标的池范围，初期美股单交易所可不用。

## 4. 数据获取设计

### 4.1 多标的合并请求（已实测验证）

`time_series` 的 `symbol` 参数支持**逗号分隔多标的**（如 `symbol=AAPL,MSFT,NVDA`），一次请求可拿到多个标的的同一 interval 数据。已用 AAPL,MSFT,NVDA + 1day 实测通过，关键结论：

| 维度 | 结论 |
|---|---|
| 计费 | **不省 credits**——按 symbol 数计（3 个 = 3 credits，已用 api_usage 验证）。省的是 HTTP 请求数 |
| 响应结构 | 顶层按 symbol 分键，各自带独立 `meta`/`values`/`status`。与单标的结构不同，**需要专门的 DTO**（如 `Map<String, TimeSeriesResponse>`），现有单标的不通用 |
| outputsize | **每标的**各自生效（outputsize=5 时每家各回 5 根） |
| 错误隔离 | 无效标的只在自己 key 下报 error，不影响其他标的 |

**对调度的影响**：

- **日线同步优先用合并请求**：一批 50–100 个 symbol，100 标的从 100 次请求降到 1–2 次，限速压力基本消失（Basic 8/min 也不再是瓶颈）
- **分钟线仍按单标的或小批量**：增量窗口由游标控制、首拉受 outputsize=5000 分页约束，批量合并对翻页逻辑帮助不大
- **拉取器实现**：请求层需要两条路径——`fetchSingle(symbol, ...)`（分钟线/回补/翻页用）与 `fetchBatch(List<symbol>, ...)`（日线批量用），batch 响应解析后**复用同一套 upsert 入库逻辑**

### 4.2 首次全量回补（Backfill）

```
1. 查 earliest_timestamp 得到该 symbol 的最早可用时间
2. 从当前时间向前分页拉取：time_series?outputsize=5000&timezone=UTC
   - 响应含 next_page_token 时继续请求直到拉完或到达目标起点
3. 每页入库 + 更新游标（游标取本页最早 bar_time - 1）
```

注意：**首拉顺序与分页方向**——`time_series` 默认返回最新数据，带 `page` 参数（部分套餐）或 `next_page_token` 向历史翻页；翻页期间若产生新 K 线不影响历史页一致性。

### 4.3 日常增量同步

```
SELECT last_bar_time FROM td_sync_cursor WHERE symbol=? AND interval=?
→ 请求 time_series?start_date=<last_bar_time+1>&outputsize=5000
→ upsert 入库（ON CONFLICT 覆盖）
→ 更新游标为本次最大 bar_time
```

对 `1day` 线：交易日收盘后（按 `exchange_schedule`）触发一次，**多个标的合并为一次 batch 请求**（见 4.1）。
对分钟线：按 interval 对应节奏触发（如 `5min` 线每 5–10 分钟一次），仅交易时段内调度。

### 4.4 实时报价（可选补充）

`quote` / `price` 单次 1 credit/symbol，用于盘中信号触发；**每次拉到即写 `td_bar` 的时间分桶**（如当前分钟），不建单独快照表——K 线表本身就是最新价的落地形式，避免双写不一致。

### 4.5 credits 与限速预算

| 场景 | 计算 | credits/天 |
|---|---|---|
| 100 只标的日线，每标的每交易日 1 次 | 100 × 1 | 100 |
| 10 只标的首拉 3 年 1min 线（一次性） | 10 × ~30 页 ≈ 300 | 300（一次性） |
| `/api_usage` 探测每 10 分钟 1 次 | 144 | 144 |

**限速策略**：拉取器内部用信号量/队列将请求速率压到套餐限速的 80%（如 Basic 8/min → 实际 6/min）；收到 HTTP 429 时按响应头退避重试。

### 4.6 可靠性

- **失败重试**：单 symbol 失败仅记 `td_fetch_log`，不阻塞同批其他标的（与 `/batch` 错误隔离语义一致）
- **配额不足**：本轮直接 `skipped_no_quota`，等待下个周期（用 `/api_usage` 的 `plan_daily_limit - daily_usage` 预判）
- **空洞检测**（二期）：对每个 symbol+interval，按交易时段/日历生成应有 bar_time 序列，与库中实际比对，缺口触发定向回补

## 5. 代码结构建议

```
com.goaerion.testcode.http
├── config/                  # 已有 WebClient 配置，增加 TD 限速信号量
├── dto/twelvedata/          # 已有 4 个行情 DTO，直接复用
└── quant/                   # 新增 quant 模块
    ├── symbol/SymbolPoolService.java      # 标的池管理
    ├── fetch/MarketDataFetchService.java  # 拉取编排（配额→分页→入库）
    ├── fetch/RateLimiter.java             # 限速
    ├── storage/TdBarMapper.java            # BaseMapper + 手写批量 upsert SQL
    ├── storage/TdSyncCursorMapper.java     # 游标读写
    └── scheduler/MarketDataScheduler.java # @Scheduled 入口
```

**依赖新增**（pom.xml）：

```xml
<!-- MyBatis-Plus：Spring Boot 4 必须使用 boot4 starter 坐标，且需 3.5.15+；3.5.16 对齐 mybatis-spring 4.0.0 -->
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-spring-boot4-starter</artifactId>
    <version>3.5.16</version>
</dependency>
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>
<!-- 可选：Flyway 管理上面的 DDL 迁移 -->
```

持久层选型 **MyBatis-Plus**：标的池、游标、日志等单表 CRUD 用 `BaseMapper` 零 SQL 完成；批量 K 线 upsert、翻页查询等复杂 SQL 用 Mapper XML / 注解手写（`ON CONFLICT DO UPDATE` 仍需手写 SQL）。注意 Spring Boot 4 下 starter 坐标是 `mybatis-plus-spring-boot4-starter`，旧的 `mybatis-plus-boot-starter` / `mybatis-plus-spring-boot3-starter` 自动配置不生效。

**配置**（application.yml）：

```yaml
spring:
  datasource:
    url: jdbc:postgresql://${PG_HOST:localhost}:${PG_PORT:5432}/${PG_DB:quant}
    username: ${PG_USER:postgres}
    password: ${PG_PASSWORD:postgres}
    driver-class-name: org.postgresql.Driver

mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true   # td_bar.bar_time ↔ barTime
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl  # 开发期打印 SQL，生产关闭
  global-config:
    db-config:
      id-type: auto   # td_symbol.id BIGSERIAL 数据库自增
  mapper-locations: classpath*:mapper/**/*.xml

# Twelve Data —— apikey 迁移到环境变量，不要明文提交
# twelvedata.apikey=${TWELVEDATA_APIKEY}
# 拉取限速（按套餐调整，取限速值的 80%）
# twelvedata.rate-limit-per-minute=8
```

## 7. 风险与注意事项

1. **apikey 安全**：当前 `application.properties` 中明文 apikey 必须改为环境变量注入，避免入库泄露
2. **复权问题**：Twelve Data 返回的日线可能含复权调整（`adjusted` 相关参数见 time_series 文档）；策略上要么固定用同一口径（如全复权），要么在拆股/分红事件后对窗口做定向重拉——建议先固定口径，等接入 fundamentals/dividends 后再处理重拉
3. **多交易所日历差异**：增量同步依赖 `exchange_schedule`，A股/美股/加密货币节奏不同；crypto 7×24，调度需按 asset_type 区分
4. **分页与限速的冲突**：全量回补期间翻页请求也计入限速，长回补任务要支持断点续传（游标机制天然支持：中断后从 `td_sync_cursor` 继续）
