## 一、中间件原理与深度

### 消息队列

#### 1. Kafka/RocketMQ/RabbitMQ 深度对比

> 对比架构模型（推 vs 拉、协调组件）、事务/延迟/顺序消息支持与实现，交易主链路决策矩阵。

**总体对比矩阵：**

| 维度 | Kafka | RocketMQ | RabbitMQ |
|---|---|---|---|
| 消息模型 | Pull（long polling），消费位点是 offset，可重放 | Pull 为主体，Push 是长轮询封装 | Push（broker 主动 deliver） |
| 协调组件 | KRaft（内置 Raft）或 ZK | NameServer：无状态、互不通信，客户端轮询拉路由 | 无外部协调，Erlang 集群镜像/quorum 队列 |
| 存储 | 分区日志，顺序写 + sendfile 零拷贝 | 所有队列统一写一个 CommitLog（顺序写）+ ConsumeQueue 索引 | 每队列独立文件 + 索引，队列数多了性能退化 |
| 吞吐量级 | 百万/s | 十万/s | 万级/s |
| 堆积能力 | 极强（日志型设计） | 强 | 弱（堆积后性能明显下降） |

**三类特殊消息的实现：**

- 事务消息
  - RocketMQ：half message 先落到系统 topic（RMQ_SYS_TRANS_HALF_TOPIC，对消费者不可见）→ 生产者执行本地事务 → commit/rollback（消息写回真实 topic / 删除标记）→ 超时未决由 broker 回查本地事务状态。解决"本地事务与发消息的原子性"，即最终一致。
  - Kafka：事务只保证"跨多分区写入的原子性 + read_committed 消费"。机制：producer 幂等（PID + seq）→ transaction coordinator + `__transaction_state` topic 记录状态 → 两阶段提交，写 control batch（commit/abort marker）。不解决与业务 DB 的一致性。
  - RabbitMQ：无事务消息，只有 publisher confirm / transactional channel（性能差）。
- 延迟消息
  - RocketMQ：4.x 18 个固定级别（内部 SCHEDULE_TOPIC_XXXX + 定时任务回投）；5.x 基于时间轮 + timer log 支持任意精度，最大可配天数。
  - RabbitMQ：TTL + 死信交换机（队头阻塞问题：前一条长延迟会挡住后面短延迟），或 delayed-message-exchange 插件（基于 Mnesia 表，节点重启恢复有边界）。
  - Kafka：无原生，需外部时间轮服务 / 分层 delay topic 自建。
- 顺序消息
  - Kafka：单分区有序，生产端按 key 哈希 + 同步发送；破坏点：重试乱序（需 max.in.flight=1 或幂等）、分区扩容后 hash 重分布。
  - RocketMQ：生产端按 queue 选择（MessageQueueSelector），消费端 MessageListenerOrderly 拿 queue 锁（broker 端锁 queue + 客户端加锁），顺序消费失败只能本地重试不能跳过。
  - RabbitMQ：单队列 FIFO，但并发消费即失序。

**交易主链路决策矩阵（示例）：**

- 一级权重：可靠性（事务消息/刷盘策略/副本机制）、消息不丢能力（同步刷盘/多副本 ISR）。
- 二级：延迟 P99、顺序/延迟/事务原生支持度、堆积恢复速度。
- 三级：运维复杂度、团队熟悉度、多语言生态、成本。
- 结论范式：交易链路选 RocketMQ（事务/延迟/顺序原生 + 同步刷盘可控）；日志、埋点、大数据管道选 Kafka（吞吐 + 生态：Kafka Connect/Streams）；RabbitMQ 用于低吞吐、复杂路由（exchange 模型）的传统系统。

#### 2. Kafka 无 ZK 化（KRaft）

> KRaft 解决了什么问题？为什么提升扩展性？

- 核心动机（KIP-500）：
  - 消除双元数据系统：原来 controller 依赖 ZK watch 感知 broker/分区变化，元数据在 ZK 与 Kafka 内存里双份，故障切换慢（重新加载全量元数据，秒~分钟级）且有一致性风险。KRaft 把元数据变成内部 Raft 日志（`__cluster_metadata`），controller quorum（3/5 节点）多数派提交，active controller 故障切换毫秒级，standby 从快照+日志热恢复。
  - 运维简化：去掉独立 ZK 集群的部署、监控、版本兼容矩阵。
- 扩展性提升的本质：
  - ZK 模式下 controller 全量 watch 几十万分区的 znode 变更，rebalance / controller 故障恢复时产生 watch 风暴，分区数成为硬天花板；KRaft 元数据增量传播 + 快照机制，可支撑百万级分区。
  - 元数据写入走 Raft 多数派，不再有 ZK session 过期引发的误判与重风暴。
  - controller 与 broker 角色解耦（可合并部署），broker 增量拉取元数据，避免全量推送。
- 落地细节：3.3 起 KRaft production ready；升级需要 metadata 迁移工具（ZK → KRaft 混合模式过渡）；部分旧运维习惯（动态改配置走 ZK）需迁移到新 API。
#### 3. MQ 使用场景盘点与滥用

> 列出所有使用场景，哪些不该用 MQ。

- 典型正当场景：削峰填谷（秒杀扣减请求进队列）、异步解耦（订单后置动作：通知、积分、风控异步化）、广播分发（配置变更、缓存失效）、大数据管道（埋点入湖）、最终一致（本地事务 + 事务消息）。
- 常见滥用（不该用的）：
  - 强一致链路用 MQ 拆步：如"扣库存 + 扣款"用消息串联，失败补偿链复杂、不一致排查成本远高于同步调用收益。
  - 请求-响应用 MQ 模拟同步 RPC（reply-to + 阻塞等待）：延迟不可控、超时语义混乱，应直接 RPC。
  - 用 MQ 做"数据双写同步"而无对账：丢一条就是长期数据漂移；正确做法是 binlog 同步 + 对账修复任务。
  - MQ 只当背压阀但不治理：无限流、无死信、无堆积告警，消费挂了没人知道。
  - 小体量场景硬上 MQ：每天几千条消息的发通知场景，线程池 + 延时任务即可，MQ 引入的是额外故障面与运维成本。
  - 用 MQ 传大 payload（几 MB 报文/文件）：拖垮网络与存储，应传引用（OSS 地址）。
  - 链式级联消息（A 触发 B、B 触发 C）：无全局视图、无 trace，应改为编排层（状态机/工作流）。
- 判断标准一句话：MQ 的收益（削峰/解耦/异步）必须 > 引入的故障面 + 最终一致成本；且上游必须能容忍"消息延迟/重试/乱序"，否则不该用。

#### 4. 堆积 5000 万条：SOP 与根因框架

> 完整应急处置 SOP + 根因分析框架。

**应急处置 SOP（先止血，后根因）：**

1. 定性影响面：堆积主题/消费组、lag 曲线、生产速率 vs 消费速率差值，估算消化时间 `T = lag / (consume_rate - produce_rate)`，判断是"缓慢累积"还是"正在恶化"。
2. 三分钟定位消费速率为何下降：消费者存活数、是否 rebalance 风暴、消费端异常重试占比、下游（DB/RPC）延迟、消息体是否突增。
3. 止血手段（按见效速度）：
   - 扩容消费者并发（注意：消费者数 > 分区数无效，Kafka 需同步扩分区）。
   - 旁路搬运：新建一个临时 topic（分区数 ×10），一个轻量消费者只做搬运不做业务，再由大并发消费者消费临时 topic——牺牲顺序换吞吐，这是处理千万级堆积的标准动作。
   - 业务降级：跳过通知/审计等非关键逻辑、慢 SQL 改批量、下游限流放开、增加缓存。
   - 若消息可丢（日志类）：调短保留时间靠 TTL 清理，或重置 offset（需业务确认）。
4. 防次生灾害：消费端拉取批量调小防 OOM、下游 DB 防打死、盯 lag 转折点。
5. 复盘：T+1 输出报告（根因、止损动作有效性、预防项进 backlog）。

**根因分析框架（五类）：**

- 生产突增：营销活动、上游故障引发的重试风暴、消息放大（一条业务消息裂变多条）。
- 消费变慢：代码缺陷（串行 RPC、慢 SQL）、下游依赖劣化、GC 停顿。
- 消费失效：rebalance 风暴、重试死循环、死信未处理导致"看似在消费实则原地打转"。
- 结构性问题：分区数与消费并发不匹配、热点分区（分片 key 倾斜）、单条大消息拖慢整批。
- 容量错配：扩容后未缩回、保留时间/磁盘配置错误。
### RPC 与注册中心

#### 5. Dubbo3 应用级服务发现

> 与接口级对比；百万实例场景注册中心压力怎么算。

- 接口级（Dubbo2）：每个"接口 + 版本 + 分组"注册一条 URL。一个应用 50 个接口 → 注册中心数据量 ×50；订阅者要接收全量接口 URL 列表推送，payload 巨大。
- 应用级（Dubbo3）：注册中心只存"应用名 → 实例列表（ip:port + 元数据）"，"接口 → 应用"的映射下沉到元数据中心（metadata report）。数据量从 O(接口数 × 实例数) 降为 O(应用数 × 实例数)，推送粒度变成应用级。
- 压力量化（示例口径）：
  - 100 万实例、平均每应用 20 个接口：接口级 ≈ 2000 万条 URL 记录；单实例上下线触发对"订阅了该接口的所有消费者"的 watch 扇出，推送 payload 数百 KB，注册中心写放大严重。
  - 应用级 ≈ 100 万条实例记录；推送只发生一次（应用维度），消费者本地按接口 → 应用映射还原，配合客户端缓存 + 增量对比，注册中心 CPU/带宽下降一到两个数量级。
- 配套机制：Nacos 2.x 走 gRPC 长连接 + 推拉结合（连接数 O(实例)，变更推送按订阅者聚合）；客户端有快照容灾（注册中心全挂时用本地快照兜底）。
- 迁移注意：双注册双订阅过渡、metadata report 的可用性成为新依赖点。

#### 6. 健康检查误判与流量残留

> 心跳/TTL/连接状态的误判场景；下线后流量残留处理。

- 机制与误判：
  - 心跳 + TTL（客户端周期上报）：误判来源——FULL GC 长停顿导致心跳超时被摘除，恢复后又重新注册（上线抖动 + 注册风暴）；网络抖动误摘。
  - 长连接状态（Nacos 2.x gRPC）：TCP 半开连接/假死时服务端感知滞后，需要应用层心跳兜底；注册中心自身过载导致心跳处理延迟，会"批量误摘"放大故障。
  - 主动探活（HTTP/TCP）：健康检查接口若依赖 DB 等下游，下游抖动会被误判为实例不可用，造成连锁摘除雪崩——健康检查应只反映本进程存活，业务健康用另一个指标。
  - 时钟问题：TTL 判定基于服务端时间，NTP 跳变会误判。
- 流量残留治理：
  - 标准优雅下线顺序：先向注册中心主动反注册（不是等心跳超时）→ 等待消费者缓存刷新（推送延迟 + 客户端缓存周期，一般 10~30s）→ 拒绝新请求、处理存量请求 → 退出进程。K8s 场景放在 preStop：反注册 + sleep（大于缓存刷新周期）再收 SIGTERM。
  - 长连接场景（gRPC/Dubbo triple）：服务端发 GOAWAY 主动断流，比等客户端感知更快。
  - 兜底：客户端对已摘除实例的调用失败做快速 failover + 熔断，重试要求幂等；监控"调用已下线 IP"的残留流量作为下线流程正确性的验收指标。

#### 7. RPC 泛化调用、异步调用、隐式传参

> 三者实现原理 + 二次封装增强。

- 泛化调用：客户端不依赖 provider 接口 jar，`GenericService.$invoke(method, paramTypes, args)`，POJO 用 Map 表示并配泛化序列化器；provider 端通过反射 + 预生成的 Wrapper 类分发到实现。典型用途：API 网关、自动化测试平台、跨语言接入。代价：类型安全丢失、反射开销、schema 无校验（需自己补）。
- 异步调用：请求发出后立即返回 CompletableFuture，底层通过请求 ID → DefaultFuture 映射，IO 线程收到响应后按 ID 唤醒 promise；超时用时间轮管理。Dubbo 2.7 起 AsyncRpcResult 全链路异步，不阻塞业务线程。陷阱：异步后 ThreadLocal 上下文（trace、租户）会丢失，需要在回调里显式恢复。
- 隐式传参：RpcContext attachments / 协议扩展 header，随请求透传 traceId、灰度标签、压测标记、租户 ID，不进方法签名。注意：attachments 默认只在相邻两跳传递，跨多层需要每跳的 filter 显式向下复制。
- 二次封装增强（结合项目讲 2~3 个即可）：
  - 上下文体系：trace/灰度/租户/压测标自动注入与透传（filter 链统一实现，业务无感）。
  - 稳定性模板：超时/重试/熔断默认值策略化（按接口等级），接 Sentinel，防止各业务自己拍超时。
  - 线程池隔离：核心/非核心接口分离线程池与 IO 资源。
  - 治理能力：调用关系自动上报（基于注册与调用元数据生成拓扑）、出流量染色（影子库压测）、统一异常码映射。
### 网关与流量

#### 8. Nginx/OpenResty worker 模型、upstream、动态 upstream

> worker 事件驱动模型、upstream 转发机制、动态 upstream 的实现路线。

- worker 模型：master 加载配置/绑定端口/管理 worker；worker 单线程事件驱动（epoll/kqueue），数量 = CPU 核数；连接与请求全部非阻塞；限流等状态存共享内存 zone；多 worker 竞争 accept 的惊群用 SO_REUSEPORT（每 worker 独立监听队列）或 accept_mutex 解决。
- upstream 机制：`ngx_http_upstream_module` 状态机——选 peer（负载均衡算法实现 init/get/free 回调接口，round robin/least_conn/hash 均为插件）→ 建连 → 转发 → 读响应；失败重试由 proxy_next_upstream 控制；被动健康检查（max_fails + fail_timeout）；主动检查需第三方模块或商业版。
- 动态 upstream 三条路线：
  - OpenResty 方案：`balancer_by_lua*` 阶段用 lua-resty-core 的 balancer API 每请求动态选节点；上游列表与健康状态放 `lua_shared_dict`，由 timer 定时探测（lua-resty-upstream-healthcheck），控制面通过 Admin API 写入，全程无 reload。
  - APISIX 方案：etcd watch 增量推送到每个 worker 内存，路由（radixtree 匹配）+ upstream + 插件全部热生效。
  - 折中方案：nginx + nginx-upsync-module 从 Consul/etcd 拉上游列表，减少 reload 场景。
- 关键细节：动态 upstream 必须处理好 keepalive 连接池与节点摘除的关系（摘节点要优雅 drain 已有连接）。

#### 9. 自研网关 vs 开源网关选型；APISIX 优势

> 自研 vs 开源的选型论证；APISIX 的 etcd + 动态路由优势与代价。

- 选型论证框架：
  - 需求盘点：协议（HTTP/gRPC/WebSocket）、插件需求（认证/限流/灰度/WAF）、扩展语言偏好、动态性要求（秒级路由生效？）、性能要求、有无控制面/多集群诉求。
  - 候选对比：
    - Spring Cloud Gateway：Java 栈顺滑、与 Nacos/Sentinel 集成好；响应式编程门槛、性能中等、动态性弱（要自研 refresh）、没有现成控制面。
    - Kong：OpenResty 底座、插件生态最全、企业支持；数据面依赖 DB（Postgres），社区版架构重。
    - APISIX：etcd + 全动态，性能好，控制面极简。
    - 自研：只有当认证体系/协议/合规有强定制且愿意长期养团队时才考虑，否则是负债。
  - 结论范式：默认选开源（APISIX/Kong 为主），Java 中小团队求快选 SCG；把"自研"降级为"在开源上做插件"，而不是造轮子。
- APISIX 的 etcd + 动态路由优势：
  - etcd 是 Raft 强一致存储，watch 增量推送 → 路由/上游/插件变更秒级生效且各数据面节点最终一致，无 reload（连接不断）。
  - 数据面无 DB 依赖：每个 worker 从 etcd 同步全量配置在内存，单个节点故障不影响其它节点，扩容即生效。
  - 插件编排：路由-插件-上游解耦，Lua/WASM 扩展，热插拔。
  - 代价：引入 etcd 运维（快照备份、成员变更）、深度定制需要 Lua 技能。

#### 10. 网关全局单点的容量计算

> 连接数、带宽、TLS 握手开销怎么估。

- 连接数：空闲连接本身便宜（每连接内核 + 用户态几十 KB 级），真正约束是"并发活跃请求"。用 Little's Law：`并发请求数 = 峰值 QPS × 平均耗时`；长连接（WS/SSE）单独按并发连接数规划，受 worker_connections × worker 数、fd 上限、内存约束。
- 带宽：`入向 + 出向 ≈ 峰值 QPS × (请求均长 + 响应均长) × 8`；注意出向（响应/文件下载）通常是大头。高 PPS 场景关注软中断（多队列网卡 + RSS + irqbalance），而不只是 bps。
- TLS 握手：RSA-2048 完整握手单核约几百次/秒，ECDSA P-256 快 5~10 倍；会话复用（session ticket / TLS1.3 PSK、0-RTT）把复用握手的 CPU 降到 1/10 以下。估算公式：`TLS CPU ≈ 新建连接速率 × 单次握手 CPU 耗时 / 核数`，水位控制在 50% 以下；把"新建连接率"压下来（keepalive、连接复用）比堆机器更有效。
- 工程校准：
  - 单机压测 → 线性外推要打折（共享 LB、内核锁、跨 NUMA），经验系数 0.7~0.9。
  - 预留 2 倍冗余 + 弹性扩容；网关必须无状态（有连接态的要考虑长连接重连风暴）。
  - 系统参数：worker_connections、fs.file-max、tcp_tw_reuse、upstream keepalive 池。
  - 结论输出形如："峰值 5 万 QPS、平均响应 5ms → 并发 250 请求；新建连接 2000/s（复用率 96%），带宽 400Mbps 出向；4 台 8C 网关，TLS ECDSA，水位 40%，留弹性到 8 台。"
## 二、存储选型与架构

### 关系型数据库

#### 11. MySQL 深度

> MVCC 链路、redo/binlog 两阶段提交与组提交、主从延迟治理、大表 DDL 对比。

**MVCC 与 ReadView：**

- 每行隐藏字段：trx_id（最后修改的事务）、roll_pointer → undo log 版本链。
- ReadView 四要素：活跃事务列表 m_ids、min_trx_id、max_trx_id（下一个待分配）、creator_trx_id。可见性：trx_id < min 可见；≥ max 不可见；介于两者间则看是否在活跃列表，不可见就沿 undo 链回溯找旧版本。
- RR vs RC 的本质差异只有一点：ReadView 的生成时机——RR 在事务第一次快照读时生成并全程复用；RC 每条快照读都重新生成。这就解释了两种隔离级别的所有行为差异。
- RR 防幻读：快照读靠 MVCC；当前读（`for update`/update/delete）靠 next-key lock（记录锁 + 间隙锁）。注意同一事务内快照读与当前读可能看到不同结果（经典边界）。
- 长事务危害：ReadView 不释放 → undo 链不能 purge → 版本链膨胀、历史版本回溯变慢、undo 表空间涨。

**redo/binlog 两阶段提交与组提交：**

- 为什么必须两阶段提交：redo log（InnoDB 物理日志）与 binlog（Server 层逻辑日志）是两个独立日志，崩溃恢复时以"redo prepare 且 binlog 完整 → 提交；binlog 缺失/不完整 → 回滚"为裁决。若先写 redo 后写 binlog 崩溃 → 主库有数据从库没有；反之 → 从库有主库没有。两阶段提交保证两份日志的事务集一致，主从才一致。
- 组提交：双 1 配置（sync_binlog=1 + innodb_flush_log_at_trx_commit=1）下 fsync 是瓶颈。binlog 组提交三阶段：flush（组内事务 binlog 写 OS cache 并拼接）→ sync（一次 fsync 带走整组）→ commit。redo 组提交由 binlog 组提交的 leader 顺带带动（保证 prepare 顺序与 binlog 顺序一致）。参数 binlog_group_commit_sync_delay/_no_delay 可用小延迟换更大组、提升吞吐。
- 面试加分点：能讲出"组提交解决的是磁盘 IOPS，不是锁"以及"并行复制正是复用组提交的 last_committed 信息"。

**主从延迟：**

- 根因分类：① 回放单线程/并行度不足；② 大事务（一个巨大 event 无法拆分并行）；③ 从库无索引导致回放全表扫；④ 从库规格低或读流量过载；⑤ 网络带宽；⑥ 大 DDL。
- 治理：
  - 并行复制：5.7 LOGICAL_CLOCK（同组提交的事务可并行回放）；8.0 WRITESET（按行哈希做冲突检测，依赖窗口更细，并行度显著提升，WRITESET_SESSION 保会话顺序）。从库参数 replica_parallel_workers / replica_parallel_type。
  - 业务侧：拆大事务、binlog_row_image 控制、从库独立规格、读流量按延迟阈值摘除。
  - 监控：Seconds_Behind_Master 不可靠，用 pt-heartbeat 或 GTID 落后事务数；延迟敏感读走主库或强制路由标记。

**大表 DDL：**

- MySQL 8.0 instant DDL：只改元数据（加列，8.0.29 后支持任意位置），秒级完成；限制：不能同时加索引/改类型等。
- Online DDL（INPLACE）：加索引、改列等，允许并发 DML，但需重建数据 + 应用增量日志，大表耗时且放大主从延迟。
- pt-osc：触发器 + 影子表 + 分批拷贝 + 原子 rename；缺点：触发器损耗与冲突风险、外键处理麻烦。
- gh-ost：伪装从库拉 binlog 回放影子表，无触发器；可限速、可暂停、可先跑 no-op 演练，是当前主流。
- 选型：8.0 且满足 instant 条件 → instant；否则 gh-ost；pt-osc 用于有触发器依赖兜底的场景。前置检查：磁盘 2 倍空间、主从延迟水位、cutover 阶段短暂元数据锁。

#### 12. 分库分表中间件

> SQL 解析改写、结果归并、分布式 ID 的坑。

- 处理链路五步：
  1. SQL 解析：ANTLR 或自研 parser → AST（table/condition/order/agg/limit）。
  2. 路由：按分片键条件定位库表；无分片键 → 全库全表广播（性能杀手，治理上要禁用或强制走绑定表）。
  3. 改写：逻辑表名 → 物理表名；补分片键；改写 limit/order by/聚合（把 `limit 100000,10` 改成 `limit 0,100010`）；自增主键回填处理。
  4. 执行：多库并发执行；受 max-connections-size-per-query 约束，超过则内存归并，否则流式归并。
  5. 归并：流式排序归并（优先）、分组归并、聚合归并、分页归并（大 offset 会把前 10 万行全部拉回内存丢弃，这是深分页在分库分表下更痛的原因）。
- ShardingSphere-JDBC（进程内，无中间层，语言受限）vs Proxy（MySQL 协议代理，语言无关但多一跳延迟 + proxy 自身高可用）。
- 分布式 ID 的坑：
  - UUID 无序 → InnoDB 页分裂、缓存命中差。
  - 雪花 ID：时钟回拨（策略：小回拨等待、大回拨告警拒绝）、workerId 分配要持久化（ZK/DB 号段）、机器号冲突导致静默重复是最难排查的坑。
  - 号段模式：DB 批量取号 + 双 buffer 预加载；重启后 ID 跳跃。
  - 分片键与 ID 的"基因法"：把分片键（如 user_id 后几位）嵌进订单 ID，使订单 ID 自身可路由，避免二次查询。
  - 业务唯一约束跨分片失效（手机号唯一）：分库后本地唯一 ≠ 全局唯一，需要独立的索引表/注册服务。
### NoSQL 与新型存储

#### 13. Redis 架构深水区

> 主从复制与 backlog 溢出、Cluster gossip 与槽迁移、单线程与 6.0 多线程、大规模治理量化。

**主从复制：**

- 全量：首次 `PSYNC ? -1` → master `bgsave` 生成 RDB（fork，页表复制 + COW 内存膨胀风险）→ 传 RDB，期间写命令进 replication buffer → slave 清库加载 → 回放增量。
- 增量：replication backlog 是环形缓冲区（默认 1MB）。slave 断线重连带 replid + offset，offset 仍在环形区内 → 部分重同步；被覆盖 → 退化为全量。
- 溢出后果链：网络抖动/主线程长阻塞 → offset 被覆盖 → 全量 RDB → 主库 CPU/磁盘/带宽打满 + COW 可能 OOM → 多 slave 同时触发则雪崩。治理：backlog 按"可容忍断线时长 × 写入速率"放大（如 512MB）、repl-diskless-sync、错开全量、repl-timeout 调整。
- 拓扑：级联复制/扇出缓冲降低主库压力。

**Cluster：**

- 哈希槽：`CRC16(key) mod 16384`。为什么 16384：gossip 消息携带槽位 bitmap，2KB 大小可控；集群规模（≤1000 节点建议值）也用不了更多槽。
- gossip：PING/PONG/MEET/FAIL 四种消息，节点随机选邻居交换自身+第三方节点视图（含槽 bitmap、config epoch），O(N²) 收敛最终一致；故障判定：主观 PFAIL → 过半 master 确认 → 标记 FAIL 并广播。
- 槽迁移流程：目标节点 `SETSLOT n IMPORTING` → 源节点 `SETSLOT n MIGRATING` → 逐 key `MIGRATE`（源加锁、序列化传输、目标写入、源删除，原子）→ `SETSLOT n NODE <target>` 广播（epoch 提升仲裁）。
- 迁移期请求处理：key 还在源 → 源正常处理；不在 → 源返回 ASK 重定向，客户端带 ASKING 再请求目标；槽已迁移完成 → MOVED。smart client 更新本地槽表。协议上不存在双写：任意时刻一个 key 只有一个权威节点，业务要做的是客户端按协议重试 + 幂等。多 key 命令跨槽报错，用 hash tag `{user1000}` 强制同槽。

**单线程与 6.0：**

- 快的真正原因：纯内存 + 高效数据结构（SDS、跳表、listpack/quicklist）+ epoll 事件循环 + 无锁无上下文切换。CPU 不是瓶颈，网络 IO 与内存才是。
- 6.0 改了什么：IO 线程多线程化——读包/解析协议、写回响应并行化（io-threads）。没改什么：命令执行仍单线程，原子性与无锁语义不变（这一点常被追问）。后台线程一直存在：bgsave、AOF fsync、lazy-free、关闭 fd。

**大规模治理（量化示例，替换成自己的数据）：**

- 实例收敛：800+ 小实例 → 集群化合并到 ~60 个节点，CPU/内存成本降 40%，运维告警减半。
- 大 key：RDB 离线分析 + memory usage 抽样，top 大 key（如百万成员的 hash）拆分桶化；del 全部改 unlink（lazy free）。
- 慢查询平台：slowlog 采集聚合，禁用 keys/hgetall 全量，scan 化改造，P99 延迟从 15ms 降到 3ms。
- 热点 key：本地缓存（一级）+ key 加随机后缀打散（二级）+ 读写分离；监控 cluster 节点 QPS 方差作为热点告警。
- 内存：maxmemory-policy 按场景（缓存 lfu/队列 noeviction）、active-defrag 开启、过期采样频率调优。

#### 14. Elasticsearch

> 写入链路与近实时、深分页取舍、分片与 reindex。

**写入链路与 NRT：**

- 协调节点按 `_routing = hash(doc_id) % 主分片数` 路由 → primary 写内存 index buffer + translog → 同步复制到 replica → 双写成功返回。
- refresh（默认 1s）：buffer 生成新 segment 并打开为可搜索——这就是"近实时"（写入到可搜有 ~1s 延迟）的根源；refresh 越频繁小 segment 越多。
- translog：先写日志再落段，宕机恢复靠重放 translog；flush（段提交）时 fsync segment、清 translog。
- merge：后台把小段合并成大段，同时物理清除"删除标记"（删除只是打墓碑）与更新旧版本；merge 是 IO/CPU 大户，需限制并发与段大小（max_num_segments、tier 配置）。
- 写入调优：bulk 批量化、refresh_interval 调大到 30s、写入期副本数降 0、translog 同步策略按丢失容忍度调整。

**深分页：**

- from+size：每个分片都要返回 from+size 条到协调节点全局排序再丢弃前 from 条，内存/CPU 随 from 线性恶化；默认 max_result_window=10000。适合管理后台浅分页。
- search_after：用上一页最后一条的排序值（必须带唯一 tiebreaker，如 _id 或 _shard_doc）继续取下一页；配合 PIT（point in time）获得一致性视图；性能与页深无关，适合 C 端无限滚动。
- scroll：建快照批量拉取，维持搜索上下文有成本、不适合实时搜索，适合离线全量导出（官方也建议 PIT + search_after 替代）。
- 一句话取舍：实时浅分页 from+size；实时深分页/流式 search_after+PIT；全量离线用 scroll（或 reindex）。

**分片数与 reindex：**

- 分片：单分片 10~50GB 经验区间；总主分片数 ≈ 预估总量 / 30GB 并向上取整；主分片数建索引后不可改（split/shrink 除外，且要求倍数关系）；副本提升读吞吐但不提升写吞吐；分片过多会放大集群状态与查询扇出开销。
- reindex：`_reindex` 内部 scroll 拉 + bulk 写；目标索引先设副本 0、refresh_interval=-1，完成后恢复；支持 script 变换、冲突处理；跨集群配 reindex.remote.whitelist。
- 生产迁移方案：数据量小 → 直接 reindex 停写窗口；数据量大 → 双写（新逻辑写新旧两套）+ 全量 reindex + 按时间增量追平 + 对账 + 灰度切读，最后下旧索引。
#### 15. HBase/Cassandra 与 LSM

> 适用场景；LSM 写放大/读放大权衡与 compaction 策略。

- 适用场景：写吞吐高、按 rowkey 点查/范围扫、大宽表。典型：订单流水、消息/会话存储、用户画像标签、feed 流存档、监控时序。HBase：强一致（CP，Region 单副本服务）、依赖 HDFS/ZK、生态重；Cassandra：AP、去中心 gossip、多 DC 复制、原生 TTL（时序友好）。
- LSM 写路径：WAL → MemTable（跳表）→ 满了 flush 成不可变 SSTable → 后台 compaction 合并。顺序写是 LSM 高写吞吐的根源。
- 三种放大：
  - 写放大：compaction 反复重写同一份数据（leveled 典型 ~10x）；SSD 上直接影响寿命与成本。
  - 读放大：一次读要查 MemTable + 多层多个 SSTable；靠 bloom filter（false positive 概率 vs 内存占用）、block cache、key 范围分区缓解。
  - 空间放大：size-tiered 下旧版本冗余多，空间占用可能达数据量 2x。
- compaction 策略：
  - Size-Tiered：同大小段合并，写友好、简单；空间/读放大高，适合写多读少纯吞吐场景。
  - Leveled（RocksDB/Cassandra LCS）：每层按 key 范围切分、层间 key 重叠受控；读放大低、写放大 ~10x，适合读也多的场景。
  - FIFO / TimeWindow：TTL 淘汰型，适合时序日志。
  - HBase：minor/major 两级，major 全量合并 IO 巨大，需错峰、手动控制。
- 权衡结论：读多写多用 B+ 树；写多 + 扫描为主选 LSM，并把 compaction 与前台写隔离（限流、错峰、分层存储）。

#### 16. ClickHouse/Doris 等 OLAP 选型

> 选型对比；Join、更新能力的局限。

- ClickHouse：单表极致性能（列存 + 向量化执行 + 稀疏主键索引），MergeTree 家族成熟。短板：① Join 弱——hash join 在内存做，分布式 join 要手动设计（broadcast/字典表/colocate），大表 join 易爆内存；② 更新删除是 mutation（异步重写整个 part，重代价）或 ReplacingMergeTree 去重不可靠，适合不可变事实表；③ 并发能力弱——单查询吃满多核，几十个并发就饱和；④ 扩容数据再均衡麻烦。
- Doris/StarRocks：MPP 架构，FE/BE 分离；分布式 shuffle join、colocate join、bucket shuffle 原生支持，Join 能力强；数据模型 Duplicate/Aggregate/Unique（Unique 主键模型 MoW 支持高频更新）；导入实时性好（Flink + Routine Load 秒级可见）；并发与 SQL 兼容性更好，BI 场景友好。代价：运维组件更多（FE 选主）、超大单表极限性能略逊 CK。
- 选型维度：查询模式（宽表单表聚合为主 → CK；多表 join 即席分析 → Doris）、更新需求（不可变 → CK；准实时 upsert → Doris Unique/StarRocks 主键表）、并发量（少量分析师 → CK；数百 QPS 报表 → Doris）、生态与团队栈、数据规模与成本。
- 共同边界：两者都不是 OLTP，不能承担交易库角色；超高基数精确去重要看内存代价（或 BITMAP/近似算法）。

#### 17. TiDB 等 NewSQL

> 什么场景值得引入；与"MySQL 分库分表 + 中间件"对比论证。

- 值得引入 TiDB 的场景：数据量到 TB 级且单 MySQL 实例/单分片扛不住；业务 SQL 复杂（多表 join、聚合、跨分片事务），分库分表改造成本与风险过高；需要在线水平扩缩容；HTAP（TiKV 行存 OLTP + TiFlash 列存副本 + MPP 分析）混合负载；对强一致要求高（Raft 多数派 + Percolator 2PC + PD 全局 TSO）。
- 与分库分表路线对比：
  - 分库分表 + 中间件：性能上限高（单分片就是原生 MySQL）、生态成熟、成本低；但应用侵入大——分片键设计绑定业务、跨分片 join/事务/分页要业务自己绕、扩容再平衡靠工具且痛、中间件层（ShardingSphere）本身有学习与运维成本。
  - TiDB：对应用近似透明（MySQL 协议，但有兼容性差异：优化器行为、隐式主键、热点写入需 AUTO_RANDOM、部分语法不支持）、容量与吞吐在线伸缩（PD 调度 region）、分布式 ACID 开箱即得；代价：写入延迟比单机高（2PC 多次 RTT）、组件多（PD/TiKV/TiFlash/TiDB）资源占用大、运维体系全新、简单场景性价比低。
  - 决策论证范式：先用"读多写少 + 明确分片键 + 可预估数据量"证明自己不需要 NewSQL（分库分表更省）；只有"复杂 SQL + 强事务 + 规模持续增长 + 团队愿意建新运维体系"四个条件同时满足才引入 TiDB。
- 过渡策略：TiDB 可先做 MySQL 从库角色承接分析查询（DM 同步），验证兼容性与性能后再切主流量。

#### 18. 对象存储（S3/OSS）

> 业务架构典型用法；元数据管理与海量小文件的坑。

- 典型用法：
  - 静态资源：前端资源/图片上传 OSS + CDN 回源，签名 URL 防盗链。
  - 用户上传：服务端签发临时凭证（STS）或预签名 URL，客户端直传，绕开应用服务器带宽。
  - 归档：日志、DB 备份走生命周期（标准 → IA → 冷归档）降本。
  - 数据湖底座：Iceberg/Hudi 表存 OSS，Spark/Flink/CK 直读。
  - 大文件交换：MQ 只传对象引用不传内容。
- 元数据管理：对象存储只有平坦命名空间和极少系统元数据（ETag、user meta）；业务检索（按类目/标签/时间找文件）必须业务元数据落库（MySQL/ES），对象 key 设计带语义前缀（日期分区）利于按前缀扫描；list 全量遍历是反模式。
- 海量小文件的坑：
  - 成本：每对象有固定元数据与请求计费，千万级小文件存储费和请求费都不划算。
  - 性能：list 慢、目录（前缀）并发 list 有限速、小文件随机读延迟高。
  - 解法：打包归档（自定义容器格式 + 索引文件）、Hudi/Iceberg compaction 合并小文件、缩略图等派生小文件直接走 CDN 不回源。
  - 语义坑：对象存储没有原子 rename（rename = copy + delete），不能当文件系统用；分片上传 + 断点续传做大文件；幂等用 Content-MD5/ETag 校验。
## 三、技术判断与选型

#### 19. 顶住压力否决流行技术方案的经历

> 论证过程。

- 表达结构（STAR + 数据）：背景与方案主张 → 我的论证 → 结论与结果。
- 论证方法论（这是面试官真正想听的）：
  1. 先定义问题：这个新技术解决的是我们当前的真实瓶颈，还是一个"看起来先进"的伪问题？用现有监控/压测数据锚定真瓶颈（P99？成本？故障率？）。
  2. 量化收益：预期收益有多少？有没有可验证的数字，还是只有官方案例？
  3. 算 TCO：学习/迁移/运维/招聘/社区风险五项隐性成本逐项列出，通常这里是压垮"流行方案"的地方。
  4. 主动收集反方证据：已知生产故障案例、踩坑文章、竞品对比，诚实呈现"最坏情况我们能不能承受"。
  5. 给替代方案 + 最小验证：不否定方向，而是提出"用 2 周时间盒做 POC，带验收指标"，把争论变成实验。
- 结果表达要点：结论是"达成共识"而非"我赢了"；可能被采纳为小范围试点而非全量上线；体现的是工程判断与共识能力，不是权力压制。
- 可选话术：把"要不要用"改写成"在什么约束下可以用、什么条件下必须撤"。

#### 20. 引入新中间件的标准评估清单

> 清单维度；退出成本为什么重要。

- 功能：核心能力覆盖率，缺失能力的 workaround 代价与长期维护成本。
- 性能：拒绝官方 benchmark，用自己数据分布与负载模型自测；看 P99/P999 而非均值；记录资源开销（CPU/内存/磁盘 IO）。
- 可靠性：故障模式清单（脑裂、丢数据、降级行为）、备份恢复是否演练过、监控告警接入成本、是否有流控/过载保护。
- 运维：部署复杂度（有状态服务？）、升级兼容策略、扩缩容是否在线、排障工具链（慢查询、heap dump、metrics 是否齐）、社区排障资料丰富度。
- 安全与合规：认证授权、审计日志、加密、license（AGPL 等传染性协议）、数据出境。
- 社区与生态：版本发布节奏与破坏性变更历史、issue 响应、生产级案例规模、是否有商业公司兜底、与现有技术栈集成成本。
- 成本：资源成本 + 人力成本 + 机会成本，按 3 年 TCO 算。
- 退出成本：数据可导出性（格式是否开放）、API 是否兼容行业标准（MySQL 协议/Kafka 协议类兼容层是巨大加分项）、是否有等价替代品、双跑迁移可行性。
- 退出成本为什么重要：
  - 引入即负债：中间件是"租约"不是"买断"，社区停更、性能天花板、公司战略调整都可能强制退出，退出时数据与调用方改造是最大成本。
  - 退出通道在引入时最便宜：接口抽象隔离、数据格式中立、不依赖私有特性（依赖私有特性要单独评审并登记），等出事再想退就晚了。
  - 它同时倒逼评估的诚实度：想清楚"怎么退"，才会认真回答"该不该进"。

#### 21. 最老的组件与升级策略

> 评估要不要升级；灰度/双跑/回滚怎么定。

- 常见答案素材：JDK 8、CentOS 6/7、MySQL 5.6/5.7、ES 5.x、Spring 4.x、老网关。
- 评估维度：
  - 硬性风险：EOL 时间线（厂商停止安全补丁）、高危 CVE、与新依赖的兼容冲突（新框架不再支持旧版本）。
  - 软性风险：招聘与新人上手、可观测生态（metrics/trace）接入困难、性能与稳定性欠账。
  - 收益：升级带来的性能/成本/安全收益，能否量化。
  - 输出：升级收益-风险矩阵，按"安全风险 > 兼容冲突 > 收益"排优先级，不升级要有书面风险确认。
- 升级策略：
  - 前置：梳理升级路径（跨多版本不可跳级，如 MySQL 5.6 → 5.7 → 8.0 逐步）、兼容性清单（API/配置项/默认值/数据格式变更，如 MySQL 8.0 的默认字符集与认证插件、ES 7 去 type）、回滚预案与数据兼容原则（schema 只增不改不删）。
  - 灰度：按实例/集群/流量比例逐级放量，客户端与协议层保持双协议兼容期。
  - 双跑：新旧并行处理同流量，用 diff 工具比对结果；数据层双写 + 对账；设定止损线（差异率 > 0.1% 即暂停）。
  - 回滚：配置开关一键切回旧版本；升级前快照（DB 物理备份、配置版本化）；升级窗口内保留旧实例随时接管。
  - 节奏：每步一个验收门，不合并动作。
#### 22. 自研 vs 开源 vs 商业采购决策框架；错误选型复盘

> 自研/开源/采购决策框架；举一个做错的选型，代价与教训。

- 决策框架（四问）：
  1. 业务核心度：这是否构成差异化竞争力？非核心能力自研就是浪费。
  2. 开源成熟度：有无生产级验证、活跃社区、商业兜底。
  3. 团队能力：是否有 ≥3 人能读源码并持续维护？自研是"永久贷款"，人力要按 3 年算。
  4. 3 年 TCO：采购费 vs 自研人力 vs 开源运维人力（含故障成本）。
  - 快速判定：非核心 + 开源够用 → 开源；核心 + 开源严重不匹配 + 有人力 → 自研（谨慎，先插件化）；强合规/企业支持诉求 → 商业采购。
  - 中间态最常见：基于开源二次开发（遵守 license），把自研范围压缩到插件与胶水层。
- 错误选型复盘模板（面试必须敢讲真事）：
  - 背景：当时为什么选（被什么信息/趋势说服）。
  - 错在哪：低估运维成本 / 高估团队能力 / 未验证真实负载 / 没设退出机制——对应评估清单缺失项。
  - 代价量化：迁移 X 人月、线上事故 N 次、多花成本 X 万。
  - 教训机制化：不是"下次注意"，而是把缺失项补进团队评估 checklist、评审流程（如：任何中间件引入必须附 POC 报告与退出方案）。

#### 23. 技术债管理

> 识别、登记、偿还排期机制；业务没空还债怎么办。

- 识别：三类——代码债（重复/腐化/无测试）、架构债（强耦合/单点/过期依赖）、运行债（手工操作多、告警噪音）。量化信号：模块变更成本上升曲线、缺陷与故障复盘根因重复出现、需求交付周期异常长的模块。
- 登记：技术债台账，每条债当作 backlog item 管理——描述、影响范围、利息（每迭代因它多付的成本）、偿还方案、估时、负责人、优先级；P0（会引发事故）~P3（可拖）。
- 偿还排期机制（四条腿）：
  - 固定配额：每迭代预留 15%~20% 工时给技术债，形成制度而非口头约定。
  - 顺手治理（童子军军规）：改到相关模块时做限定范围的清理，控制边界防止重构失控。
  - 故障驱动：复盘产出的还债项直接进下个迭代，优先级最高。
  - 专项攻坚：季度性技术专项，需要管理层背书，带明确验收指标。
- 业务没空还债怎么办：
  - 翻译成业务语言：不还债的风险敞口（故障概率 × 单次故障损失）vs 偿还成本，做成一页纸决策材料；用"需求交付效率"对比数据说话（还债前后同规模需求耗时）。
  - 借势排期：新需求要动该模块之前先治理（顺路还债最便宜）、借事故复盘窗口、借安全/合规审计的外部压力。
  - 分级止损：EOL 组件、高危安全漏洞这类债不参与排期博弈，直接升级为风险项走危机通道。
  - 原则：技术债管理本质上是一个"跟业务的信用体系"——按期还债、定期汇报利息，团队才有持续预算。

#### 24. 面对花哨但不熟悉的新技术

> 学习与评估路径；避免拍脑袋。

- 路径（带时间盒）：
  1. 定位（半天）：读官方文档的设计动机与"它解决什么问题"，明确与现有技术是替代还是互补；看它自己声称不解决的场景。
  2. 原理速读（1~2 天）：架构图、数据模型、一致性/容错模型；至少读一份设计文档或论文、翻一遍关键路径源码（如存储引擎的写路径）。
  3. 反面信息（半天）：HN/GitHub issue 里的故障报告、竞品对比、生产踩坑文章——重点收集"什么时候不该用"。
  4. POC（1~2 周）：用自己的真实数据集与负载模型压测（绝不用官方 demo 数据），除了性能还要演练运维全流程：部署、监控接入、备份恢复、kill -9 故障恢复、升级。
  5. 小规模试点：选非核心、可回退的链路跑一个完整迭代，暴露长尾问题。
  6. 输出决策文档：收益/风险/成本/退出通道四段式，提交团队评审；结论可能是"引入""继续观察"或"明确不用并写明理由"。
- 避免拍脑袋的机制：
  - 结论必须挂在"数据 + 实验 + 反方证据"上，三者缺一就明确说"我目前只有初步印象，需要 POC 验证"——承认未知是合法且加分的答案。
  - 区分两种活动：好奇心驱动的学习（随时做）与生产引入决策（必须走流程）；前者靠后者约束。
  - 反直觉提醒：对"花哨"技术，第一反应应是找它不适用的场景，而不是找它适用的场景。
