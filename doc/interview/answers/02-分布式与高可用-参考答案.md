# 分布式与高可用 参考答案

> 开放式题没有唯一答案，以下为「要点框架 + 关键细节 + 权衡取舍」，面试时应结合个人项目展开。原题见 ../02-分布式与高可用.md

## 一、分布式理论

### 1. CAP 与 BASE 的落地体现

> 原题：CAP 与 BASE 在你负责的系统里怎么体现？举一个亲手做过的"牺牲 C 保 A"的例子。

- 先纠正对 CAP 的理解（避免背概念）：
  - P 不是可选项，网络分区/节点宕机必然发生；取舍只发生在分区发生那一刻：保可用（AP，返回可能旧的本地数据）还是保一致（CP，拒绝服务直至多数派恢复）
  - 无分区时 C、A 可以兼得；分区恢复后通过同步走向最终一致
  - CAP 里的 C 是线性一致性，不是"数据差不多一样"；A 是每个非故障节点都能在合理时间内响应
- 在系统里的体现（示例说法，替换为自己的项目）：
  - 注册中心：Nacos AP（服务列表短暂不一致可容忍）vs ZK/etcd CP（选主期间整体不可用）
  - 系统内部分层：交易链路强一致（本地事务 + DB 约束），展示链路最终一致（缓存 + 异步刷新），形成"一系统多一致性级别"
- "牺牲 C 保 A"实例框架（场景 → 不一致窗口 → 兜底）：
  - 例：商品详情页库存/价格走缓存异步刷新，允许秒级"超卖展示"；下单时强一致扣减库存兜底，把脏读限制在"展示层、不可造成资损"的范围内
  - 例：双活下非核心写入（收藏/浏览记录）单元内自洽、异步汇总，分区期间继续可写，恢复后合并
- BASE 对应：基本可用（分区时降级非核心功能）、软状态（"支付处理中"等中间态可见）、最终一致（消息 + 对账保证收敛）
- 权衡表述：牺牲 C 换 A 的前提是"不一致的业务代价 < 不可用的代价"，且必须能回答：不一致窗口多长、业务感知到什么差异、出现差异谁兜底

### 2. Raft 选举、日志复制、成员变更

> 原题：Raft 的选举、日志复制、成员变更讲一遍；组件底层不是 Raft，为什么还要懂它？

**选举：**
- 三种角色 Follower/Candidate/Leader；Follower 在随机选举超时（一般 150~300ms，随机化防选票瓜分）内没收到心跳，自增 term 发起 RequestVote
- 投票约束：每个 term 只投一票（先到先得）；候选者日志不能比自己旧（先比最后一条日志 term，再比 index）——保证已提交日志不被覆盖
- 获多数派选票当选，立刻追加一条 no-op 日志提交以间接确认前任日志；PreVote 预选举先探测能否拿到多数派，防止被隔离的节点反复涨 term、回归后干扰集群
- term 是逻辑时钟：见到更大 term 立即变 Follower

**日志复制：**
- 写请求全部经 Leader：追加本地日志（未提交）→ 并行发给 Follower → 多数派 ack 后推进 commitIndex 提交 → apply 到状态机 → 响应客户端
- 一致性检查：AppendEntries 携带 prevLogIndex/prevLogTerm，Follower 校验失败则拒绝，Leader 递减 nextIndex 重发，保证日志前缀一致（日志匹配特性）
- Follower 上被覆盖过的冲突条目会被 Leader 的日志回滚覆盖
- 读优化：ReadIndex / lease read，避免每次读走日志，但 lease read 需处理时钟漂移

**成员变更：**
- 直接整体替换配置可能出现两个多数派（旧配置一个、新配置一个）导致脑裂
- 标准方案 joint consensus（C_old,new 联合多数派两阶段切换）；工程上更常用单步变更（每次增删一个节点，同样安全，etcd 默认实现）

**为什么不是 Raft 也要懂：**
- 共识是通用问题模型：ZK 的 ZAB、etcd 的 Raft、Kafka KRaft、ES 主选举、Redis Sentinel、TiDB PD 本质都在解"选主 + 多数派复制"
- 懂机制才能做对工程决策：为什么 ZK 写要过半、Kafka 何时该配 acks=all + min.insync.replicas、脑裂时谁是"对的"数据、监控中 leader 频繁切换说明什么
- 话术：承认组件实现差异，但强调底层模型相通——配置调优、故障定位、容灾设计都依赖它

### 3. 脑裂与防脑裂机制

> 原题：脑裂是什么？系统里有哪些防脑裂机制（quorum、fencing token、仲裁节点）？

- 定义：网络分区/心跳丢失时旧主与新主同时存在并接受写入，导致数据分叉甚至丢失
- 本质：租约/心跳依赖网络与时钟，而二者都不可靠，"我认为我是主"无法自证唯一
- 防脑裂机制（按层）：
  - quorum 多数派：ZK/etcd/Raft/ES，多数派才能当选与写入，少数派分区自动降级；反模式：偶数节点均分两机房，任何分区都拿不到多数派
  - 仲裁节点/witness：三节点中放轻量仲裁（ZK observer、云厂商仲裁实例），不存数据只投票，成本换安全性
  - fencing token：获取锁/租约时发单调递增令牌，存储层校验并拒绝旧令牌写入——专治"旧主被隔离后恢复、自己不知道已下台继续写"（Kleppmann 对 Redlock 的经典论证）
  - 资源层隔离（STONITH）：切换时强制断电/卸载旧主的共享存储，物理上杜绝双写
  - 数据层兜底：唯一约束、版本号乐观锁、GTID/binlog 位点回退检测（备库拒绝写位点更旧的数据）
- 常见案例：
  - Redis 主从 + Sentinel 切换期间客户端仍连旧主写 → 配 min-replicas-to-write + min-replicas-max-lag，旧主失联从库后拒绝写
  - DB 主备切换：VIP 漂移 + 备库只读 + 切换流程强制"确认旧主降级只读"步骤，禁止双主双写
- 权衡：quorum 用"少数派不可用"换一致性；fencing 需存储层配合并非处处可用——组合使用并以演练验证
### 4. 时间不可靠：NTP 跳变与时钟漂移

> 原题：NTP 跳变、物理时钟漂移会引发什么问题？逻辑时钟、HLC、TrueTime 等规避手段？

- 典型事故面：
  - 租约/锁误判：持锁节点时钟快，锁已被收回仍认为持有 → 双写；Leader 租约内因漂移被判过期 → 双主
  - NTP step 跳变（回拨/前跳）：定时任务重复触发或漏跑、token/证书有效期判断错乱、监控日志时间线错乱、基于时间戳的幂等/限流窗口错位
  - 跨机房 skew：按时间戳比新旧数据的逻辑失效，消息/日志乱序误判
- 规避手段（按体系）：
  - 逻辑时钟：Lamport 定全序、向量时钟定因果并做冲突检测（Dynamo 系）；只保证相对顺序，不映射物理时间
  - HLC（混合逻辑时钟）：物理时间 + 逻辑计数，CockroachDB 等使用；接近物理时间且不受回拨影响
  - TrueTime（Spanner）：原子钟 + GPS 硬件授时，返回不确定区间 [earliest, latest]，提交等待（commit wait）跨过区间实现外部一致性——用硬件成本换时间精度
  - 中心化授时 TSO：TiDB PD / OceanBase 全局单调授时服务，单点风险靠集群化规避
- 工程可落地的实践：
  - 用版本号/单调序列替代时间戳做"谁更新"判断；时间只用于展示、TTL 等容忍误差的场景
  - 租约与锁按最坏时钟漂移留 buffer；NTP 配置为渐进 slew、禁止大步进；部署 clock skew 监控告警
  - 业务排序依据 binlog 位点/GTID/消息 offset，而非消息自带时间戳

### 5. 幂等设计手段盘点

> 原题：唯一索引、状态机、token 机制、乐观锁……各自适用边界？写接口幂等的标准做法？

**手段对比表：**

| 手段 | 原理 | 适用场景 | 边界与坑 |
|---|---|---|---|
| DB 唯一索引 | 冲突插入报错，捕获后转查询返回 | 创建类（订单号/流水号防重） | 分库分表后唯一性仅分片内；最终兜底，不可绕过 |
| 状态机（条件更新） | update ... set status=新 where id=? and status=旧 | 有状态流转（订单、支付） | 只防状态重复推进不防创建重复；非法流转是报错还是返回首次结果要定义 |
| token 机制 | 进页面领一次性 token，提交时 Redis Lua 原子"校验+删除" | 表单防重复提交，前端可配合 | token 服务不可用会阻塞主流程；必须 Lua 保证原子 |
| 乐观锁 version | 带版本号条件更新，失败重试 | 更新类、冲突率低 | 高冲突时重试风暴；需请求方有重试语义 |
| 悲观锁 for update | 事务内锁行再判断 | 低并发、强一致（账户余额） | 死锁/长事务/热点行风险，高并发是灾难 |
| 去重表 / Redis setnx | 以业务幂等键先行占位 | MQ 消费、入口拦截 | 需 TTL 兜底；占位与业务操作要同事务或可回滚，否则留脏占位 |
| 消息去重（msgId） | 消费前 insert ignore 去重表 | 消费端幂等 | 必须与业务操作同库同事务才可靠 |

**写接口幂等标准做法（分层组合）：**
1. 入口：客户端生成请求幂等键（或服务端下发 token），服务层 Redis 拦截重复请求，命中直接返回首次结果
2. 核心：DB 唯一索引兜底（唯一业务键），冲突时查询并返回已有记录——不依赖 Redis 可靠性
3. 状态类业务叠加状态机条件更新，防重复推进与状态回退
4. 关键认知：幂等不仅是"不重复执行"，还要"重复请求返回与首次相同的结果"；幂等键要设 TTL 并建索引，重试方必须复用同一键
5. MQ 消费：msgId + 业务键去重表与业务同事务，再由对账兜底

### 6. 分布式锁实现对比

> 原题：Redis/Redisson/Redlock/ZK/etcd/DB 锁的对比？"所有场景都用 Redis 锁"的问题？

**实现对比表：**

| 实现 | 一致性 | 原理 | 优点 | 坑/边界 |
|---|---|---|---|---|
| Redis SET NX PX + Lua | AP | 单 key 原子 set + 过期时间 + 唯一 value 防误删 | 简单、高性能 | 锁先过期业务未完 → 双持；主从异步复制，故障转移瞬间锁丢失 |
| Redisson | AP | 可重入 hash + 看门狗定时续期（默认 30s 锁，每 10s 续） | 解决"业务没执行完锁先过期"，API 完善 | 进程 GC/分区时续期线程停摆 → 锁过期；仍是 AP，不保证切换不丢锁 |
| Redlock | 多数派 | 向 N 个独立实例加锁，多数派成功且总耗时 < TTL | 缓解单实例故障转移丢锁 | 依赖时钟假设（Kleppmann：进程暂停/时钟跳变仍可双持）；运维重；要正确性应上 fencing 而非 Redlock |
| ZK | CP | 临时顺序节点 + 最小序号持锁 + watch 前驱释放 | 会话断开自动释放防死锁、公平队列 | 吞吐低（写走 leader + 过半）；羊群效应；会话超时敏感 |
| etcd | CP | lease + revision 事务比较（create revision 判断先后） | 线性一致读、lease 自动释放、watch 高效 | 吞吐低于 Redis；lease TTL 要匹配业务耗时 |
| DB | 强 | 唯一索引占位 / for update / version | 与业务同事务最可靠，版本号天然是 fencing token | 性能差、锁表膨胀、占连接 |

**给"全用 Redis 锁"的建议：**
- 先分清锁的目的：效率锁（防重复计算，偶发失效无害）可用 Redis；正确性锁（防资金双扣、防超卖）不能只靠 Redis——必须叠加 DB 唯一索引/乐观锁/状态机兜底，或改用 CP 组件
- 必须有 fencing：锁携带单调 token/版本号落库校验
- 锁内代码要短：不做 RPC、不做长事务；TTL 覆盖最坏耗时 + 看门狗续期兜底
- 锁粒度按业务键细化，避免全局锁；finally 中用 Lua 原子"判断 value + 删除"防误删
- 结论话术：分布式锁是"减少冲突的手段"而非"正确性的保证"，正确性永远由数据层约束兜底

## 二、数据一致性与事务

### 7. 与业务方达成"最终一致"共识

> 原题：一致性要求最高的系统？从"业务不接受不一致"到"最终一致兜底"怎么达成共识？

- 方法论：把抽象的"一致/不一致"翻译成业务语言——不一致窗口多长、哪些字段可能不一致、业务表现为哪种错误、发生概率与损失
- 先分级拆解"绝对一致"诉求：
  - 资金账务：不允许错账——强一致事务 + T+1 对账 + 人工差错兜底（钱不多不少，允许晚一点对平）
  - 状态类（订单状态、库存展示）：分钟级最终一致可接受
  - 展示类（评价、积分）：小时级可容忍
- 共识过程：给出量化承诺（如 99.99% 5s 内一致，剩余 0.01% 由对账 24h 内修复）→ 双跑/演练数据佐证 → 明确兜底责任与告警升级路径 → 业务方书面确认遗留风险归属
- 个人案例框架（替换为项目）：支付回调驱动订单状态：原同步强一致链路 RT 高、支付方抖动直接阻断下单 → 改为"支付侧本地事务 + 消息投递 + 订单侧幂等消费 + 15 分钟对账"，对业务承诺 5s 内 99.99% 一致并开放差异率监控大盘
- 关键话术：让业务理解"不一致 ≠ 错账"，用补偿与对账把风险从"系统不可用"转移为"数据晚一点对平"

### 8. 对账系统设计

> 原题：准实时 vs T+1 的架构差异、差异数据处理流程、对账系统的对账。

**架构差异：**

| | 准实时对账 | T+1 对账 |
|---|---|---|
| 数据源 | 双向流水消息/binlog 流（Canal + Flink） | 双方账单文件/全量表（Hive/Spark 批） |
| 时效 | 秒~分钟级发现差异 | 次日全量核对 |
| 成本 | 高（常驻流计算 + 存储） | 低（批任务） |
| 定位 | 核心资金链路快速发现与止损 | 全量兜底、最终定论、财务出账口径 |

- 二者互补：准实时管"快"，T+1 管"全与准"

**差异数据处理流程：**
- 采集 → 标准化（统一流水模型：单号/金额/状态/时间/方向）→ 配对（以业务单号为 key，核对金额、状态、笔数）→ 差异分类：
  - 单边（一方有一方无）：先区分"在途"（时间差，挂起进下一周期）与真差异
  - 金额不符：重复支付/部分退款/幂等重放
  - 状态不符：超时未知态（一方成功一方失败）
- 处理方式：
  - 自动修复：可重推的消息重推、未知态主动反查渠道修正，全部动作写入差异台账
  - 人工工单：不可自动处理的生成工单，SOP 化（核对凭证、渠道查证、调账审批），超时自动升级（一线 → 主管 → 财务）
  - 长款/短款分池挂账，限期核销并考核核销率

**对账系统的对账（自证）：**
- 覆盖率硬校验：业务侧总笔数/总金额 vs 对账侧已配对数，缺口即漏对，每日强制执行
- 任务健康监控：账单文件未到、对账任务失败/延迟告警
- 抽样人工复核 + 财务独立报表交叉验证
- 指标化：当日差异当日闭环率、挂账余额趋势、单边账清零时效

### 9. 可靠消息最终一致完整链路

> 原题：生产端确认、存储、投递重试、消费幂等、死信、补偿——每一环失败场景想清楚。

逐环"机制 + 失败场景 + 对策"：

1. 生产端确认
   - 机制：本地消息表（业务事务内落消息记录 + 定时扫描补发）或事务消息（RocketMQ 半消息 + 状态回查）；同步 send + ack
   - 失败：本地事务成功但发送失败/结果未知 → 本地消息表扫描补发；broker 收到但 ack 丢失 → 重发由消费幂等消化
2. 存储
   - 机制：持久化刷盘（关键消息同步刷盘）、多副本（DLedger/Raft）
   - 失败：broker 宕机丢未刷盘消息 → 同步刷盘 + 副本 ≥ 2；单点 → 集群化
3. 投递与重试
   - 机制：ack 机制 + 失败重试队列，指数退避（10s/30s/1m/5m…），设最大次数
   - 失败：消费者全挂 → 消息堆积，监控积压量并支持消费组扩容；重试风暴 → 退避 + 消费端限流
4. 消费幂等
   - 机制：msgId/业务键去重表与业务同事务；状态机防重复推进
   - 失败：at-least-once 必然重复；乱序 → 按业务键分区有序或版本号比较丢弃旧消息
5. 死信（DLQ）
   - 机制：超最大重试入死信队列，告警 + 死信处理平台（查看、修数、限速重放）
   - 失败：代码 bug 导致必然失败刷爆死信 → 先修 bug 再重放，重放限速防二次风暴
6. 补偿兜底
   - 机制：定时任务扫描中间态/超时单据主动核对 + T+1 对账最终兜底
   - 原则：消息链路是"尽力送达"，正确性由幂等 + 对账闭环保证，不指望消息本身 100% 可靠

- 自检四问（面试加分）：消息丢了怎么办、重复了怎么办、顺序错了怎么办、堆积了怎么办——每问都有答案才算链路想清楚
### 10. Seata AT 模式原理

> 原题：AT 模式原理（全局锁、undo_log、二阶段异步提交）？什么场景不能用 AT？

**原理：**
- 角色：TC 事务协调器（独立部署）、TM 事务发起方（@GlobalTransactional）、RM 资源方（代理数据源）
- 一阶段：RM 拦截业务 SQL → 解析出前镜像（beforeImage）→ 执行 SQL → 取后镜像（afterImage）→ undo_log 与业务 SQL 在同一本地事务提交（原子）→ 向 TC 注册分支并申请全局锁
- 二阶段提交：TC 通知异步删除 undo_log，几乎零成本——因为一阶段已提交本地事务、不长期持有 DB 锁，这是 AT 比 XA 快的根本原因
- 二阶段回滚：按 undo_log 生成反向 SQL 补偿；回滚前校验当前数据与 afterImage 一致，不一致说明存在"脏写"（被全局事务之外的修改过），转人工处理
- 全局锁：TC 维护行级锁（表名 + 主键），防止两个全局事务并发改同一行导致回滚冲突；一阶段提交前必须拿到全局锁，拿不到自旋重试至超时回滚
- 隔离级别：默认全局读未提交（一阶段提交后对外可见）；要读已提交需 @GlobalLock + select for update，性能明显下降

**不适合 AT 的场景：**
- 高并发热点行：全局锁把并行压成串行，吞吐骤降（秒杀扣库存）
- 不支持的 SQL/存储：复杂 SQL、非 MySQL 系、NoSQL
- 长事务/大事务：全局锁与 undo_log 持有时间过长，冲突与回滚风险放大
- 性能敏感核心链路：镜像快照写 + 全局锁 RPC 开销不可忽视
- 跨异构系统调用：AT 只管 DB，第三方接口需 TCC/SAGA/消息
- 选型对比：TCC（高性能、业务侵入大，要处理空回滚/幂等/悬挂）、SAGA（长流程状态机编排）、可靠消息最终一致（解耦场景首选）

### 11. 分库分表三座大山

> 原题：跨库分页、跨库 JOIN、跨库事务怎么处理？重新设计会先做哪一步？

- 跨库分页：
  - 业务收敛：禁止深分页，跳页改游标（分片键 + id 连续翻页），产品侧砍掉"第 1 万页"
  - 中间件归并：各分片取 top N 归并——页越深要取 N+offset 条，内存网络开销线性恶化
  - 二次查询法（精确）：第一次各分片取 min(id) 区间估算全局 offset，第二次按修正区间取，减少传输但实现复杂
  - 正解：列表检索交给异构索引（ES/HBase），DB 只做单键详情，分析走 OLAP
- 跨库 JOIN：
  - 规范上禁止；应用层两次查询内存组装（小表驱动 + 控制 in 条数）
  - 数据冗余消除 JOIN（订单冗余商品快照）
  - 复杂查询上宽表/ES/数仓
- 跨库事务：
  - 设计规避优先：同一聚合按同一分片键聚拢（订单与明细同键），多数"事务"退化为单库本地事务
  - 真跨库走柔性：可靠消息最终一致 / TCC；Seata AT 仅适合低频管理后台类
- 重新设计先做哪一步（标准框架）：
  1. 先论证"是否必须分"：数据增长曲线、瓶颈到底是 QPS、容量还是慢 SQL
  2. 先做低成本手段：SQL 与索引治理、读写分离、缓存、冷数据归档
  3. 真要分时，第一步是定分片键与查询模型（哪些查询必须支持、如何路由），其次选型中间件（ShardingSphere/自研 proxy），最后才是迁移方案——分片键定错是返工之源

### 12. 故障预案文档目录结构

> 原题：系统全挂了，写一份故障预案文档的目录结构。

1. 系统概览：架构图（部署/依赖/数据流）、核心链路说明、SLA 与业务等级、负责人矩阵
2. 故障分级与响应机制：P0~P3 定义（影响面与判据）、响应时限（发现→响应→止血→恢复）、oncall 与升级路径（如 15 分钟未止血升级至谁）、内外部沟通模板（客服话术、公告文案）
3. 故障场景库（核心章节，每场景一页）：现象（告警特征/指标表现）→ 影响评估 → 定位手段（大盘/日志/trace 入口）→ 止血动作（可执行步骤含命令模板与开关位置）→ 恢复与验证 → 根因排查入口
4. 止血手段清单（可用动作目录）：限流阈值表（各接口当前值/建议值）、可降级开关清单（名称/位置/影响/回滚方式）、扩容 SOP（半自动脚本）、切流 SOP（DNS/网关/单元）、回滚 SOP（版本/配置）
5. 资源与联系方式：上下游负责人、云厂商/运营商通道、紧急权限申请预案（故障时怎么最快拿到权限）
6. 演练记录：每次演练时间、场景、结果、预案修订记录（预案必须有演练背书）
7. 复盘模板：时间线、根因、action item（负责人 + deadline）
8. 附录：监控大盘链接、runbook 索引、关键配置快照、历史故障案例库
- 原则：止血优先于定位；每个动作要能让值班同学不看代码直接执行
### 13. 多机房/异地多活

> 原题：同城双活/两地三中心/异地多活差异；单元化路由；跨机房同步与切机房不丢数据；切流演练。

**三方案对比：**

| | 同城双活 | 两地三中心 | 异地多活（单元化） |
|---|---|---|---|
| 拓扑 | 同城两机房双活、数据同步复制 | 同城双中心 + 异地冷/温备 | 多城市机房同时承载读写 |
| 抵御 | 机房级故障（断电/火灾/光缆） | 机房级 + 数据异地容灾 | 城市级灾难 |
| RPO/RTO | RPO≈0、RTO 分钟级 | 灾备切换 RPO 可能分钟级、RTO 小时级（冷备） | 单元内 RPO=0、整体 RTO 分钟~小时 |
| 成本 | 中（双份资源 + 低延迟同步，同城的物理优势） | 中低（异地可缩容冷备） | 高（多城资源 + 全面改造） |
| 改造难度 | 低~中 | 低 | 高（路由/数据/中间件全面改造） |

- 结论：按业务等级与预算选型——核心交易上单元化，长尾业务同城或冷备即可

**单元化路由：**
- 分片维度：按用户 UID hash 取模/分段映射到单元（一致性哈希便于扩单元），用户一次会话内所有读写封闭在归属单元完成
- 流量路径：GSLB/DNS（城市级调度）→ 接入网关读全局路由配置（按 UID 后缀/映射表路由）→ 转发到归属单元；非归属请求网关层纠偏转发
- 数据层：单元内 DB 只存归属用户数据；全局数据（商品、库存、配置）采用"中心写 + 全单元同步读"或按类目再拆分
- 关键机制：路由规则版本化下发、越单元写校验拒绝、路由变更支持用户级灰度

**数据同步与切机房不丢数据：**
- 同步：DTS/otter 类 binlog 同步，双向同步防回环（打标过滤）；延迟秒级以内并监控告警
- 冲突处理：优先"避免"——任一时刻每份数据只有一个可写单元（切流期间旧单元停写）；无法避免才用版本号/LWW，但 LWW 丢并发写，仅限非核心数据
- RPO=0 的标准切流流程（按用户集灰度为粒度）：
  1. 目标单元预建，确认同步位点追平（延迟=0）
  2. 对切流用户集：旧单元停写（秒级窗口，返回友好提示）
  3. 校验增量位点已全部到对端——这一步保证 RPO=0
  4. 切路由规则 → 新单元开放写入
  5. 以秒~分钟级不可写窗口换零丢失；不能接受窗口则退化为 RPO>0 的异步切流，需业务明确选择
- 回切：反向执行同一流程，回切条件写入预案

**切流演练：**
- 先预发/影子单元全流程演练，线上从小流量用户集开始
- 步骤：审批与周知 → 预检（同步延迟/容量/开关状态）→ 按预案切 → 验证（核心链路冒烟 + 监控对比）→ 观察 30~60 分钟 → 回切演练 → 复盘修订预案
- 回切触发条件自动化：核心错误率 > x%、耗时劣化 > y%、同步异常、资损监控告警即自动回切

### 14. 稳定性体系四件套

> 原题：限流、熔断、降级、隔离的落地细节。

**限流：**
- 单机限流：令牌桶（允许突发）/漏桶（恒速），Sentinel/Guava 本地实现；无外部依赖、零 RT，缺点是扩缩容后总阈值漂移、流量不均时各机误差
- 集群限流两种实现：
  - 中心计数（Redis+Lua 滑动窗口/令牌桶）：精确，但增加 RT 且引入 Redis 依赖——必须预设 Redis 故障时退化到单机兜底值
  - 控制面分配：配置中心按实例数下发单机配额（总配额/实例数），实例心跳上报动态再分配——准精确、无调用开销，主流做法
- 阈值来源：全链路压测出单机极限 → 限流值设为极限的 70~80% 水位 → 结合 DB 连接数、缓存命中率等依赖水位二次校准 → 上线后按监控回归修正

**熔断：**
- 三种策略选择：
  - 慢调用比例：下游劣化常表现为变慢而非报错（线程池打满），核心链路首选
  - 错误率：异常类故障（超时/5xx），通用
  - 异常数：低流量接口比例无统计意义时用绝对数
  - 实践：核心链路"慢调用 + 错误率"双规则叠加
- 状态机：closed → 统计窗口超阈值 → open（fail-fast 不消耗下游）→ 静默期 → half-open
- 半开并发探测控制：仅放行 N 个探测请求（通常 1~3 个，原子计数/单线程投递），其余请求直接走降级；探测达标 → closed，任一失败 → 回 open，防止半开期大流量打到未恢复的下游

**降级：**
- 开关管理：配置中心托管（秒级推送、灰度、回滚），变更走审批流 + 操作审计 + 开关生效监控（推了开关必须确认生效）
- 预案分级：
  - L1 非核心读降级：关推荐/评价/榜单，用户无感
  - L2 功能降级：写入异步化、返回缓存快照、砍附加功能
  - L3 核心保护：非核心链路拒绝、只读模式、排队限流
- 纪律：每个开关演练验证过、有明确回滚方式；清理长期没用过的死开关

**隔离：**

| 方式 | 原理 | 适用 | 坑 |
|---|---|---|---|
| 线程池隔离 | 依赖各自独立线程池，超时可中断 | RPC 慢调用 | 线程切换开销；池数量失控耗内存；队列堆积 OOM，须配队列长度与拒绝策略 |
| 信号量隔离 | 计数器限并发，同线程执行 | 本地调用、快速返回 | 真阻塞会占住容器线程（Tomcat 线程耗尽），必须配超时，不适合慢调用 |
| 集群/资源隔离 | 核心与非核心应用、DB、缓存实例物理分离 | 架构层 | 成本高；要防"共享中间件"把核心拖下水 |

- 定位：入口限流 → 依赖熔断 → 兜底降级 → 资源隔离，是防御纵深而非四选一
### 15. 依赖治理

> 原题：依赖拓扑怎么画？强弱依赖怎么识别和治理？循环依赖怎么解？

- 画依赖拓扑：
  - 静态：代码/配置扫描（RPC 引用、MQ topic、数据源、缓存 key）生成调用关系
  - 动态：全链路 trace（SkyWalking/自研）聚合成服务调用图，带 QPS/RT/错误率权重，比静态更真实
  - 输出：按"核心链路 → 一跳依赖 → 二跳依赖"分层渲染，标注同步/异步、超时、降级配置
- 强弱依赖识别：
  - 定义：强依赖 = 它挂我核心功能不可用；弱依赖 = 它挂我可降级可接受
  - 金标准是故障演练：对每个依赖做隔离注入（断网/超时/返错），观察核心链路是否受影响——代码里有 try-catch 不等于真弱依赖（超时没配、线程池共享都会穿帮）
  - 产出依赖清单：每个依赖标注强弱、超时值、降级方案、负责人
- 治理：
  - 强依赖异步化/消息化（下单不强依赖营销、积分服务）
  - 弱依赖补齐：超时收敛（下游超时之和 < 上游 RT 预算）、熔断、降级开关
  - 二跳以上依赖收敛扇出，缩短依赖链
- 循环依赖（A 调 B、B 调 A）：
  - 根因是业务边界没划清；解法按优先级：事件驱动（一方改发订阅）→ 下沉公共服务 → 按读写拆接口 → 数据冗余替代调用
  - 治理渐进式：先冻结新增 → 迁移高频路径 → 下线旧接口

### 16. 容量规划

> 原题：大促容量从 QPS 推导到机器数的完整链条，漏哪环会翻车？

- 完整推导链（每环注明数据来源）：
  1. 目标 QPS：历史大促基线 × 年增长系数 × 活动系数 × 安全系数；拆分到核心接口（下单/支付/详情各自峰值）
  2. 单机容量：全链路压测（影子流量）实测——取"CPU 70% 时的吞吐"为安全容量，不是压到 100% 的裸极限
  3. 应用实例数：峰值 QPS ÷ 单机安全容量 × 冗余系数（≥1.5，跨可用区容灾再加）
  4. 线程与连接：Little's Law，峰值并发 = QPS × 平均 RT(s)，线程池 ≥ 并发 × 1.2；DB 总连接 = 实例数 × 池大小 ≤ max_connections 的 70%
  5. DB：峰值 QPS/TPS 对照压测值、慢查询水位、磁盘增长（大促订单量 × 行宽）、主从延迟
  6. 缓存：峰值 QPS × (1−命中率) = 回源 DB 的 QPS——命中率降 5% 可能让 DB 流量翻倍，必须单独立"命中率下降"压测场景
  7. 带宽：QPS × 平均响应体大小 ×（1 + 监控/旁路系数），与机房出口上限核对
  8. MQ：峰值消息量 vs 消费能力，算积压增速与追平时间
  9. 第三方：渠道/短信/风控限额，提前申请提额并做降级预案
- 经典翻车点（背几条）：
  - 只压应用没压 DB；或压测时缓存全命中、线上真实命中率低
  - 漏热点 key（爆款把单个分片打满，"平均容量"毫无意义）
  - 漏消息积压与异步任务堆积
  - 只扩应用没扩 DB 连接与带宽
  - 漏第三方限额（短信限流阻塞登录链路）
- 机制保障：容量模型表格化，每期大促压测回填真实数据，超水位自动触发扩容审批

### 17. 混沌工程

> 原题：故障注入演练过什么场景？怎么防止演练事故影响线上？

- 典型注入场景（按层次）：
  - 资源层：CPU 打满、内存泄漏、磁盘写满、fd 耗尽
  - 网络层：延迟注入（+200ms/2s）、丢包、断网、DNS 故障
  - 进程层：杀进程（验证自愈与冷启动时长）、单实例摘除
  - 依赖层：DB 主从切换、缓存实例宕机（验证穿透与重建）、MQ broker 宕机、下游 RPC 全挂（验证熔断降级生效）、第三方超时
  - 机房层：可用区断电演练（切流预案的实战验证）
- 防演练事故（爆炸半径控制）：
  - 环境递进：预发 → 线上单实例 → 1% 流量 → 逐步放大；首次演练避开业务高峰
  - 白名单与标签：仅对带演练标签的实例/用户注入；登录、支付回调等敏感路径先排除
  - 自动熔断：设护栏指标（核心错误率、RT 阈值），超限平台自动停止注入并恢复现场
  - 一键终止 + 现场值守（演练指挥、观察员、各系统 oncall 拉群）
  - 审批与周知：走变更单，业务方与客服提前知晓，避免"演练被当真实故障上报"
  - 注入动作精确记录、可自动回滚（ChaosBlade/ChaosMesh destroy）
- 价值闭环：每次演练输出"发现的问题 → 修复 → 回归演练验证"，否则演练沦为表演

### 18. RTO/RPO 目标与验证

> 原题：RTO/RPO 目标值多少？怎么验证达标？

- 定义：RPO = 灾难时最多丢多少时间的数据；RTO = 故障发生到业务恢复的时长
- 目标值示例（按业务分级）：
  - 核心交易：同城机房级 RPO=0、RTO < 5 分钟（自动切换）；城市级 RPO < 1 分钟、RTO < 30 分钟
  - 一般业务：RPO < 5 分钟、RTO < 1 小时
  - 长尾系统：RPO < 24h（备份恢复）、RTO < 4 小时
- 验证方式（纸面目标无效，必须实测）：
  - 定期切流演练：真实切机房/切主库，按演练时间线度量 RTO（告警确认 → 决策 → 切换 → 验证恢复），而非只算技术切换耗时
  - RPO 验证：切换后用数据比对工具核对同步位点/行数/关键单据；异地备份做真实恢复演练（备份可用性经常是假的）
  - 红蓝对抗/不预告突袭演练，检验真实响应能力
  - 每次演练记录实测 RTO/RPO 与目标对比，未达标出 action item 跟踪
- 常见坑：RTO 只算机器切换、漏算决策与验证时间；异步复制下 RPO 被低估；备份从未真正恢复过

## 四、数据层架构

### 19. 分库分表

> 原题：分片键选择与无分片键查询（基因法/异构索引/宽表）；扩容方案对比与迁移停机窗口；什么情况建议不拆。

**分片键选择：**
- 原则：覆盖 80% 以上高频查询维度；数据分布均匀防热点；主键与分片键绑定（订单号中嵌入买家基因）
- 核心查询不带分片键的三种解法：
  - 基因法：生成主键时把分片键 hash 融入 id（订单号后几位携带买家基因），按订单号查即可直接推路由——只解决"主键可推路由"类查询
  - 异构索引：按另一维度（卖家）建索引表/索引库（binlog 同步，只存主键与路由键），先查索引再回查主表——多一份存储与秒级同步延迟
  - 宽表/搜索引擎：ES 承接多维组合查询，DB 只做单键详情
- 决策顺序：能基因法就不加存储；维度多、组合复杂直接 ES

**扩容方案对比：**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 翻倍扩容 | 2^n 库 → 2^(n+1)，旧分片数据一半迁往新片 | 迁移量 50%、路由体系不变（取模翻倍逻辑清晰） | 只能成倍扩；仍有迁移与切换动作 |
| 一致性哈希 | 环 + 虚拟节点，加节点只迁 1/N | 迁移量最小、支持任意节点数 | 数据易倾斜需虚拟节点调优；路由实现复杂；范围查询不友好 |
| 全量迁移（通用） | 全量迁移 + binlog 增量追平 + 校验 + 灰度切换 | 不依赖分片规则，可顺便治理数据 | 周期长（天级）、工程复杂 |

- 通用迁移流程（目标：不停机或秒级窗口）：
  1. 存量全量迁移（并行灌库）
  2. 增量同步：订阅旧库 binlog 追平差量（按主键覆盖写保证幂等）
  3. 数据校验：行数 + 抽样字段 md5 + 全量 checksum
  4. 灰度切换：双写/双读比对 → 按用户灰度切读 → 切写 → 旧库只读观察一周后下线
  5. 停机窗口作为兜底预案（校验不过/切流异常时停写几分钟做最终对齐），目标是不启用它
- 关键细节：迁移期间旧库只增不删（或延迟删）、切流开关支持一键回滚旧库

**建议不加分库分表的场景（先做这些）：**
- 读写分离 + 缓存解决读瓶颈
- 冷数据归档（多数"大表"归档后回到单库舒适区）
- 索引与 SQL 治理（很多是慢 SQL 伪装成容量问题）
- 分析类大查询外移列存（ClickHouse/Doris）
- 量级可预期（3 年内 < 5000 万行、峰值 QPS 不高）——或直接选 NewSQL/云原生分布式库
- 判断标准：分库分表引入的复杂度（跨库查询/事务/运维）是否已被问题规模证成

### 20. 冷热分离与归档

> 原题：归档策略、归档后查询怎么路由、归档数据回查怎么设计。

- 归档策略：
  - 条件：时间（如 6 个月前）+ 访问频率双判断；保留期由合规决定（金融类 5 年），到期才删除
  - 执行：T-1 定时分批（主键游标、每批几千行）迁入归档库 → 校验（行数/sum/md5）→ 分批删除热库数据（避开高峰，删除本身也是大事务风险点）
  - 归档目标选型：独立 MySQL 实例（简单查询）、ClickHouse/Doris（分析）、对象存储 + 数仓（超长期）；归档表同样要按单号/用户建索引
- 归档后查询路由：
  - 业务层路由：按查询时间条件分流热库/归档库（用户可见的"选择时间范围"）
  - 透明路由：中间件按时间条件自动路由，或热库查不到自动查归档（联邦查询）——开发体验好但复杂度与延迟高
  - 落地建议：客服/运营低频查询提供独立的归档查询工具页，不进交易主链路
- 回查设计：
  - 归档查询 API：单号/用户 + 时间范围查询，走归档库索引，加限流与访问审计（谁查了什么）
  - 数据回捞：极少数需修复的场景提供"回捞到热库"受控流程（审批 + 幂等），不做常驻双写
  - 合规：归档数据脱敏、访问日志留存

### 21. 慢查询治理闭环

> 原题：慢 SQL 发现 → 治理 → 防劣化（上线前 SQL 审核门禁）的闭环怎么做。

- 发现（度量先行）：
  - DB 层：慢日志采集 + pt-query-digest 聚合、云库性能洞察/全量 SQL 审计
  - 应用层：全链路 trace 标注 SQL 耗时、DAO 层 P99 监控
  - 平台化：慢 SQL TopN 榜单（执行次数 × 平均耗时，按影响面定级），自动派单到 owner（从代码提交归属推导）
- 治理：
  - 分级限期：P0 核心链路 3 天、P1 7 天、P2 排期
  - 手段优先级：加/改索引（explain 验证）→ SQL 改写（去函数包裹索引列、深分页、select *）→ 架构手段（缓存/异步/批量化）→ 拆表
  - 验收：治理前后耗时/扫描行数对比回填平台，闭环率作为团队指标
- 防劣化（上线门禁，重点讲落地）：
  - 发布卡点：发布平台识别新增/修改 SQL，自动在影子库跑 explain，校验是否走索引、扫描行数估算、是否全表扫；不达标阻断发布或需 DBA 审批豁免
  - 大表 DDL 门禁：超阈值行数的表变更强制走 DBA 平台（gh-ost/pt-osc）+ 容量评估
  - 全量回归：核心接口 SQL 回放，对比执行计划劣化
  - 运行时兜底：慢 SQL 数量突增告警 + 一键 kill + 限流
- 闭环机制：度量（榜单）→ 责任（派单到人）→ 门禁（增量不再新增慢 SQL）→ 复盘（每次故障反推一条新规则进门禁）

### 22. 缓存架构顶层设计

> 原题：多级缓存的失效策略、缓存命中率下降的排查思路、缓存层的容量规划。

- 多级缓存与失效策略：
  - 分层：本地缓存（Caffeine，百毫秒~秒级 TTL，抗热点与 Redis 抖动）→ Redis 集群 → DB
  - 更新策略：cache aside（先更新 DB 再删缓存）；删除优先于更新（避免并发写乱序留脏数据）；读写并发窗口用延迟双删
  - 可靠失效：业务侧删缓存可能失败 → 订阅 binlog（Canal）兜底删缓存/广播版本号，本地缓存按版本失效
  - TTL 设计：基础 TTL + 随机抖动防集中过期雪崩；热点 key 逻辑过期（不删数据、异步刷新）
  - 一致性定位：本地缓存接受秒级不一致，强一致的你不该走缓存——按业务容忍度选方案
- 命中率下降排查（按概率排序）：
  1. 容量不足：内存到阈值触发 LRU 驱逐（看 evicted 指标），常见于大 key 挤占
  2. 集群变更：扩缩容/主从切换导致 key 重分布、slot 迁移期 miss 抖动
  3. 流量结构变化：新活动引入新 key 集合；恶意/异常流量请求不存在的 key（穿透）
  4. 过期集中：同批 key 相同 TTL 集中失效（雪崩）
  5. 代码变更：key 前缀/序列化方式变更导致读写不一致
  - 工具：命中率曲线分段对比、hotkey 分析、大 key 扫描、miss key 采样统计
- 容量规划：
  - 估算：key 总量 × 平均 value 大小 × 1.5（碎片与元数据开销）× 增长系数；区分常驻 key 与短 TTL key
  - 水位：内存 70% 告警、85% 触发预案；QPS 按集群分片数 × 单分片上限核算并留 50% 余量
  - 结构手段：大 key 拆分（>10KB 警戒线）、热 key 本地化/多副本、核心与非核心业务实例隔离（防互相驱逐）
  - 演练：缓存整体宕机演练，验证 DB 能扛住"缓存全失效"的回源压力——这决定了缓存真正可用的安全水位
