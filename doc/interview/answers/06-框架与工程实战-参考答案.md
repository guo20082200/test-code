## 一、Spring 与主流框架

### 1. Spring Bean 生命周期追问链

> **原题要点**：实例化→属性填充→Aware→BeanPostProcessor→init→销毁；三级缓存解决循环依赖；为什么三级不是两级；哪些循环依赖依然解决不了。

**完整生命周期**

- 实例化：`createBeanInstance`，构造器/工厂方法创建原始对象
- 属性填充：`populateBean`，依赖注入（@Autowired 在此阶段由 AutowiredAnnotationBeanPostProcessor 处理）
- Aware 回调：BeanNameAware → BeanClassLoaderAware → BeanFactoryAware；容器类 Aware（ApplicationContextAware 等）经 BeanPostProcessor（ApplicationContextAwareProcessor）回调
- 初始化前置：BeanPostProcessor#postProcessBeforeInitialization
- 初始化：@PostConstruct → InitializingBean#afterPropertiesSet → init-method（顺序固定）
- 初始化后置：BeanPostProcessor#postProcessAfterInitialization —— AOP 代理通常在此生成（AbstractAutoProxyCreator）
- 使用；销毁：@PreDestroy → DisposableBean#destroy → destroy-method（容器 close 时对单例执行）

**三级缓存**

| 缓存 | 存的内容 |
|---|---|
| 一级 singletonObjects | 完整成品 Bean |
| 二级 earlySingletonObjects | 提前曝光的半成品（已实例化、未填充属性） |
| 三级 singletonFactories | ObjectFactory（lambda：getEarlyBeanReference） |

- 过程（A↔B 循环依赖）：A 实例化后把 ObjectFactory 放入三级缓存 → 填充属性时触发 B 创建 → B 填充属性需要 A → 依次查一、二级未命中后调用三级缓存工厂 → 若 A 需要 AOP，此时通过 getEarlyBeanReference 提前生成代理，产物放入二级缓存并删掉三级 → B 拿到 A 的早期引用完成初始化 → A 继续填充属性、初始化，成品进一级缓存
- **为什么是三级而不是两级**：
  - 纯引用型循环依赖两级也能解决，问题出在 AOP 的生成时机
  - Spring 设计原则是代理在初始化之后生成；三级缓存放工厂，只有真正发生循环依赖时才提前生成代理，正常 Bean 的代理仍由初始化后置生成，生命周期语义不被破坏
  - 若只有二级缓存，要么所有 Bean 实例化后立即提前做 AOP 判断（破坏语义、浪费），要么循环依赖发生时拿不到代理
- **依然解决不了的**：
  - 构造器注入：实例化阶段就互相需要，早期引用还没机会进缓存 → BeanCurrentlyInCreationException（可用 @Lazy 生成占位代理缓解）
  - prototype 作用域：容器不缓存实例，不做早期引用暴露
  - 补充：@Async 代理 Bean（AsyncAnnotationBeanPostProcessor 在 postProcessAfterInitialization 返回新对象而非复用早期引用），形成循环依赖时启动报错

### 2. BeanFactory 与 FactoryBean

> **原题要点**：两者区别；getObject 何时被调用；MyBatis Mapper / Feign Client 如何利用。

- BeanFactory：IoC 容器顶层接口，是"Bean 的工厂"，负责 Bean 定义、创建、依赖装配
- FactoryBean：本身是一个 Bean，由用户实现以定制"复杂对象的创建过程"；容器里注册的是 FactoryBean，getBean(name) 拿到 getObject() 产物，getBean("&" + name) 才拿到 FactoryBean 本身
- getObject 调用时机：该 Bean 第一次被 getBean / 被依赖注入时触发，产物（单例）缓存到 factoryBeanObjectCache
- 框架利用：
  - MyBatis：@MapperScan 把接口注册为 MapperFactoryBean 的 BeanDefinition，getObject() 返回 MapperProxy（JDK 动态代理）——把"接口→SQL 执行代理"的创建逻辑封装，无需为每个 Mapper 手写实现类
  - OpenFeign：FeignClientFactoryBean#getObject() 构建 HTTP 客户端代理
  - 价值：批量注册时只注册一个 BeanDefinition 模板，产物按需延迟创建

### 3. Spring 事务失效的 N 种场景

> **原题要点**：自调用、非 public、异常被 catch、rollbackFor、传播行为配错、多线程……踩过哪个坑、怎么发现。

- 自调用（this.method()）：绕过代理对象，切面不生效 → 解决：AopContext.currentProxy()（需 exposeProxy = true）、拆分类、注入自身代理
- 方法非 public：代理不增强（Spring 6 起支持 protected/package-private，但默认配置仍按 public）
- 异常被 try-catch 吞掉：切面感知不到异常，照常提交
- 抛受检异常默认不回滚：默认只回滚 RuntimeException/Error，需 rollbackFor = Exception.class
- 传播行为配错：内层 NOT_SUPPORTED/NEVER 导致非事务执行；内层 REQUIRES_NEW 抛异常被外层 catch，但外层已被标记 rollback-only → UnexpectedRollbackException
- 多线程调用：事务上下文（Connection 绑定 ThreadLocal）不跨线程，子线程操作不在同一事务
- 类没被 Spring 管理（new 出来）、内部 new 依赖对象
- final / static 方法：CGLIB 无法覆写
- 数据库引擎不支持事务（MyISAM）、@Transactional 导错包、未启用事务管理器
- **踩坑案例（示例，结合自己项目）**：大事务方法里 catch 了下游异常只打日志，前面的部分写入照常提交造成脏数据；发现路径：对账差异 → binlog 里发现"失败"记录仍落库 → Arthas watch 确认异常在代理调用之前已被吞 → 修复：catch 后重新抛出业务异常或手动 setRollbackOnly
### 4. 事务传播行为

> **原题要点**：REQUIRED / REQUIRES_NEW / NESTED 区别与场景；REQUIRES_NEW 挂起外层事务的底层动作。

- REQUIRED（默认）：有事务则加入，无则新建——绝大多数业务场景
- REQUIRES_NEW：挂起当前事务，新建独立事务。场景：操作日志/审计流水无论主事务成败都要落库；两个动作不允许相互影响
- NESTED：当前事务内设置 Savepoint，内层可单独回滚，外层回滚则内层必然回滚；仅 JDBC 事务管理器支持。场景：批量处理，单条失败回滚自身不影响整批
- 记忆点：REQUIRES_NEW 是两个独立事务（外层回滚内层不回滚）；NESTED 是同一事务内的局部回滚（外层回滚内层必回滚）
- REQUIRES_NEW 挂起的底层动作：
  - AbstractPlatformTransactionManager#suspend → DataSourceTransactionManager#doSuspend：把 ThreadLocal 绑定的 ConnectionHolder 解绑，包装成 SuspendedResourcesHolder 保存
  - 新事务从连接池再取一个 Connection 重新绑定 ThreadLocal
  - 内层提交/回滚后 doResume 恢复外层 ConnectionHolder
  - 注意：同时占用两个连接，高并发 + 外层长事务 → 连接池耗尽互等

### 5. Spring MVC 请求处理流程；Interceptor 与 Filter

> **原题要点**：MVC 流程；两者区别与执行顺序。

- 流程（DispatcherServlet#doDispatch）：
  1. HandlerMapping 找到 HandlerExecutionChain（Handler + 拦截器链）
  2. Interceptor.preHandle（返回 true 才继续）
  3. HandlerAdapter 调用 Controller（HandlerMethodArgumentResolver 解析参数、HttpMessageConverter 消息转换）
  4. 返回值处理：@ResponseBody 直接经消息转换器写 JSON；否则 ViewResolver 渲染
  5. 异常由 HandlerExceptionResolver（@ControllerAdvice/@ExceptionHandler）处理
  6. postHandle → 渲染 → afterCompletion（无论是否异常都执行）
- 区别：
  - Filter 是 Servlet 规范、容器级，拦截所有请求（含静态资源），只有 request/response，依赖 Web 容器；Interceptor 是 Spring MVC 机制，只拦 handler，可注入 Spring Bean，能拿到 Handler 与 ModelAndView
  - 执行顺序：Filter → DispatcherServlet → preHandle → Controller → postHandle → afterCompletion（逆序）→ Filter 返回
  - 异常时 postHandle 不执行、afterCompletion 仍执行（适合清理 ThreadLocal 等资源）
  - 分工惯例：Filter 做编码/CORS/认证（Spring Security 过滤器链）；Interceptor 做登录校验、权限、traceId、接口日志

### 6. Spring Boot 自动装配原理

> **原题要点**：@EnableAutoConfiguration → spring.factories / AutoConfiguration.imports → 条件注解；starter 结构。

- @SpringBootApplication 复合 @EnableAutoConfiguration → @Import(AutoConfigurationImportSelector)
- 候选配置来源：Spring Boot 2.7 之前读 META-INF/spring.factories 的 EnableAutoConfiguration key；2.7+/3.x 改为 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（一行一个全限定类名）
- 加载全量候选后按条件注解过滤：@ConditionalOnClass（classpath 有该类）、@ConditionalOnMissingBean（用户自定义优先）、@ConditionalOnProperty（开关）、@ConditionalOnWebApplication 等，由 ConditionEvaluator 完成匹配；再按 @AutoConfigureOrder/Before/After 排序注册
- 自研 starter 结构：
  - xxx-autoconfigure：自动配置类（@AutoConfiguration + @Bean）、属性类（@ConfigurationProperties）、imports 注册文件、可选 spring-configuration-metadata 提示
  - xxx-starter：空聚合工程，只引 autoconfigure 与三方依赖
  - 要点：@ConditionalOnMissingBean 留扩展口、默认值合理、依赖设为 optional 避免强耦合

### 7. Spring Cloud 组件组合；Eureka 自我保护

> **原题要点**：注册发现/配置/网关/熔断怎么组合；Nacos 替代 Eureka 后的自我保护机制还了解吗。

- 典型组合（示例，按自己项目讲）：
  - 注册 + 配置：Nacos（配置动态刷新 @RefreshScope，灰度用 namespace/group 隔离）
  - 网关：Spring Cloud Gateway（路由、JWT 鉴权、RequestRateLimiter 限流、灰度 Header）
  - 调用：OpenFeign + LoadBalancer，超时/重试统一收敛在配置
  - 熔断限流：Sentinel（热点参数限流、熔断降级规则持久化到 Nacos）
  - 链路：SkyWalking/Zipkin traceId 打通
- Eureka 自我保护：Server 在 15 分钟内心跳续约比例低于 85% 时判定可能网络分区，进入自我保护——不再剔除过期实例，宁可保留可能已死的信息（AP 取向）。代价是可能返回已下线实例，客户端需配重试与快速失败
- 对比 Nacos：临时实例走心跳检测、实例变更主动推送（UDP/gRPC），感知比 Eureka 客户端定时拉取快；持久实例服务端主动探测

### 8. MyBatis：#{} 与 ${}、缓存、插件

> **原题要点**：本质区别；一/二级缓存作用域与生产建议；插件原理与实战用途。

- #{}：预编译占位符 ?，PreparedStatement 设参，防 SQL 注入
- ${}：字符串拼接，有注入风险；只用于动态表名/列名/order by，且必须白名单校验
- 一级缓存：SqlSession 级，默认开启；同 session 相同语句命中，增删改/commit/close 清空。Spring 集成下每次请求一个 SqlSession，基本命不中；要注意共享 session 时可能读到旧值
- 二级缓存：namespace 级，需显式开启；要求结果可序列化；多表 join 时跨 namespace 失效感知不到 → 脏读风险。生产建议：关闭，统一交给 Redis；分布式部署下本地二级缓存天然不一致
- 插件原理：Interceptor 接口 + 责任链；MyBatis 用 JDK 动态代理包装 Executor / StatementHandler / ParameterHandler / ResultSetHandler 四大对象，@Intercepts/@Signature 声明拦截点，Plugin.invoke 串链
- 实战：PageHelper 分页（拦截 StatementHandler 改写 SQL + count）、慢 SQL 打印（记录超阈值 SQL 及参数耗时）、数据脱敏（拦截 ResultSetHandler 对手机号等字段打码）

## 二、MySQL 与数据访问

### 9. 索引追问链

> **原题要点**：B+ 树选型与树高；聚簇/二级/回表/覆盖/ICP；最左前缀与联合索引列顺序；explain 解读。

- 为什么 B+ 树：
  - vs B 树：非叶子节点不存数据，单页（16KB）能放更多键 → 树更矮 IO 更少；数据全在叶子且叶子成有序链表 → 范围/排序是顺序遍历
  - vs 红黑树/二叉树：二叉树太高（百万级 20+ 层，每层一次 IO）；B+ 树 3~4 层
  - vs 哈希：只支持等值，不支持范围、排序、最左前缀
- 树高估算（2000 万约 3 层）：页 16KB；非叶节点按 bigint 主键 8B + 页指针 6B = 14B → 每页约 16384/14 ≈ 1170 键；叶子按每行 1KB 存 16 行 → 3 层容量 1170 × 1170 × 16 ≈ 2190 万；根节点常驻内存，3 层树通常 1~2 次磁盘 IO
- 聚簇 vs 二级索引：
  - 聚簇（主键索引）叶子存整行；二级索引叶子存"索引列 + 主键值"
  - 回表：二级索引拿到主键后回聚簇索引取整行
  - 覆盖索引：查询列全在索引中，免回表（extra: Using index）
  - ICP 索引下推：把过滤条件下推到存储引擎层，用索引里已有的列先过滤再回表，减少回表次数（extra: Using index condition）
- 最左前缀：联合索引 (a,b,c) 支持 a / a,b / a,b,c 的等值组合；跳过 a 失效；范围条件（b > x）之后的列无法用于等值与排序；like 'x%' 可走前缀
- 列顺序三原则：等值列在前、范围列在后；区分度高的在前；排序列紧跟等值列后避免 filesort；尽量覆盖高频查询
- explain 解读路径：
  - type：const/eq_ref/ref/range/index/ALL，出现 ALL 重点看
  - key 与 key_len：实际用到的索引及长度（判断联合索引用了几列）
  - rows：预估扫描行数，结合 filtered
  - extra：Using index（覆盖）、Using index condition（ICP）、Using where（server 层过滤）、Using temporary（临时表）、Using filesort（额外排序）——后两个重点优化

### 10. 事务与锁

> **原题要点**：ReadView 判断规则与 RC/RR 生成时机；行锁/间隙锁/临键锁时机；RR 下非索引列 update 锁什么；死锁案例定位与解决。

- ReadView 四要素：m_ids（生成时刻活跃未提交事务集合）、min_trx_id（活跃中最小）、max_trx_id（下一个待分配 id）、creator_trx_id（当前事务）
- 版本 trx_id 可见性判断：
  1. trx_id == creator_trx_id → 自己的修改，可见
  2. trx_id < min_trx_id → ReadView 前已提交，可见
  3. trx_id >= max_trx_id → ReadView 之后才开启，不可见
  4. min ≤ trx_id < max：在 m_ids 中（未提交）不可见；不在（已提交）可见
  5. 不可见则沿 roll_pointer 到 undo log 上一版本重复判断
- RC vs RR：RC 每次 select 生成新 ReadView；RR 在事务第一次快照读时生成并全程复用 → 可重复读
- 加锁时机（RR）：
  - 唯一索引等值命中 → 记录锁
  - 唯一索引等值未命中 → 间隙锁
  - 普通索引等值/范围 → 临键锁（next-key = 记录锁 + 前面的间隙）
  - 无索引条件 → 扫描路径逐行加临键锁，近似锁全表；RR 下 `update ... where name=非索引列` 就是这种情况（RC 下有 semi-consistent read，不匹配的行提前放锁）
- 死锁案例（示例，结合自己项目）：
  - 场景：事务 A 先 `select ... for update` 拿到间隙锁后 insert；事务 B 反向先 insert 被 A 的间隙锁挡住（插入意向锁等待），A 再 insert 等 B 已持有的记录锁 → 互相等待
  - 定位：`show engine innodb status` 的 LATEST DETECTED DEADLOCK 段——看两个事务各自 HOLDS THE LOCK / WAITING FOR 的锁类型（lock_mode X locks gap、insert intention waiting）与 SQL，确定等待环
  - 解决：统一加锁顺序、缩小事务、把范围查询改为走唯一索引的点查、降级 RC（减少间隙锁）、"查-插"改为唯一索引 + 捕获重复键
  - 兜底参数：innodb_lock_wait_timeout（默认 50s）、innodb_deadlock_detect

### 11. 主从延迟

> **原题要点**：产生原因（单线程回放/大事务/机器差）与治理（并行复制、半同步、路由策略、强制走主）。

- 原因：
  - 主库写入并行，从库 SQL 线程单线程回放（5.7 之前），写入量大必然堆积
  - 大事务/大 DDL 从库回放耗时长
  - 从库机器配置差、承担大量读压力、长查询与回放互相阻塞
- 治理：
  - 并行复制：5.7 LOGICAL_CLOCK（按组提交并行回放）、8.0 writeset，调大 worker 数
  - 半同步复制：至少一个从库确认收到 binlog 才返回客户端（主要保数据安全，对延迟缓解有限）
  - 读写分离路由策略：一致性敏感读强制走主（下单后查订单）、会话粘性（同一用户短窗口内读主）、按从库延迟动态路由（超阈值摘除）
  - 业务兜底：关键"写后读"走主库或走缓存
  - 监控：Seconds_Behind_Master 不可靠，用 pt-heartbeat 测真实延迟

### 12. 大表优化路线图

> **原题要点**：2000 万行查询变慢，索引 → 读写分离 → 分库分表 → 归档的顺序与判断依据。

1. SQL 与索引（成本最低收益最高）：慢日志定位 → explain 优化索引/覆盖索引/SQL 改写；判断依据：是否根本没走对索引
2. 缓存：热点数据 Redis，削读 QPS
3. 读写分离：读 QPS 单库扛不住；判断依据：读多写少、可接受轻微延迟
4. 冷热分离/归档：查询集中在近期数据时，历史归档到归档库/对象存储
5. 分库分表（成本最高，最后做）：垂直拆（字段/业务）+ 水平拆（hash/范围/时间）；判断依据：单表数据量与增速让索引深度、DDL、备份、buffer pool 命中率都成为瓶颈（2000 万是经验值，与行宽有关，不是硬阈值）
6. 分库分表引入的新问题先想清楚：跨分片查询/聚合、分布式事务、全局唯一 ID、扩容迁移（双写/灰度切流）；中间件 ShardingSphere
- 强调：不要一上来分库分表，先把索引、SQL、缓存做对，多数"变慢"死在前两步

### 13. 场景题：商品列表页「多条件筛选 + 排序 + 分页」

> **原题要点**：DB 方案怎么做；什么信号出现时引入 ES。

- DB 方案：
  - 高频且固定的条件组合建联合索引：等值条件列在前 + 排序列在后，让排序走索引避免 filesort；用覆盖索引减少回表
  - 条件组合有限按组合建少数索引；组合爆炸时收敛产品约束（默认排序、必选类目）
  - 分页：拒绝深分页 limit 100000,20 → 游标分页（where id > last_id order by id limit 20）或延迟关联（先查主键再回表）
  - 总数 count 单独缓存或展示近似值
- 引入 ES 的信号：
  - 条件组合爆炸，联合索引设计不过来，大量 Using filesort/temporary
  - 出现分词/模糊搜索需求（商品名搜索）
  - 深分页 + 多条件组合下 DB RT 与 QPS 超出承载
  - 且愿意付出代价：binlog（Canal）/MQ 同步的一致性维护与运维成本
  - 架构：写 MySQL → binlog/MQ 同步 ES → 列表查询走 ES，详情走 DB + 缓存

## 三、Redis 与缓存

### 14. 数据结构与底层编码

> **原题要点**：SDS、ziplist/listpack、skiplist；ZSet 跳表为什么不用红黑树。

- 五种基础类型与编码：String（int/embstr/raw，底层 SDS）、List（quicklist = listpack 节点组成的双向链表）、Hash（listpack/hashtable）、Set（intset/listpack/hashtable）、ZSet（listpack/skiplist）
- SDS：头部含 len/alloc/flags；O(1) 取长度、二进制安全、空间预分配 + 惰性释放减少 realloc、杜绝缓冲区溢出
- ziplist：连续内存紧凑省空间，但 prevlen 字段可能引发连锁更新；Redis 7 用 listpack 取代（记录自身长度，无 prevlen，消除连锁更新）
- skiplist：多层索引链表，平均 O(logN)，实现简单
- ZSet 双结构：dict（member→score，O(1) 查分数）+ skiplist（按 score 排序做范围查询）；小数据量用 listpack（zset-max-listpack-entries 128 / -value 64）
- 跳表 vs 红黑树：
  - 范围查询：跳表定位起点后沿底层链表顺序遍历；红黑树要中序遍历、实现绕
  - 实现与调试简单、无旋转平衡；span 字段可 O(logN) 算排名（ZREVRANK）

### 15. 过期删除与内存淘汰

> **原题要点**：惰性 + 定期；8 种淘汰策略与 LRU/LFU 近似实现；主从、持久化期间的删除行为。

- 过期删除（对设了 TTL 的 key）：
  - 惰性删除：访问时检查，过期才删（省 CPU，冷 key 可能堆积）
  - 定期删除：事件循环中周期性从 expires 字典随机抽样（默认每批 20 个），过期比例超 25% 继续抽；分慢/快两种模式限流
- 内存淘汰（达 maxmemory 触发）8 种：noeviction（默认，写报错）、allkeys-lru、volatile-lru、allkeys-lfu、volatile-lfu、allkeys-random、volatile-random、volatile-ttl
- LRU 近似实现：不维护全局双向链表，随机采样（maxmemory-samples 默认 5）维护候选淘汰池，精度可接受、代价小
- LFU：24bit（最近衰减时间 ldt + 对数计数器 logc），访问对数递增、按时间周期衰减——解决"偶发访问的旧热点赖着不走"
- 主从：从库不主动删过期 key，等主库删后同步 DEL（3.2 起从库读到逻辑过期 key 返回空但不删数据）
- 持久化：RDB 生成时跳过过期 key，载入时主库丢弃、从库全量载入等主同步 DEL；AOF 在 key 过期时追加 DEL，重写时忽略过期 key

### 16. 穿透/击穿/雪崩 + 缓存与 DB 一致性

> **原题要点**：三类问题与方案；为什么删缓存而不是更新缓存；延迟双删。

- 穿透（查不存在数据，每次打到 DB）：缓存空值（短 TTL）+ 布隆过滤器前置拦截 + 入参合法性校验
- 击穿（热点 key 过期瞬间并发打 DB）：互斥锁重建（setnx 单飞，其余等待重试）或逻辑过期（不设 TTL，发现逻辑过期后异步刷新、先返回旧值）
- 雪崩（大量 key 同时过期 / Redis 宕机）：TTL 加随机抖动、多级缓存（本地 + Redis）、集群高可用（哨兵/Cluster）、熔断限流降级兜底
- 一致性（Cache Aside）：读——未命中查 DB 回填；写——先更新 DB 再删缓存
- 为什么"删"而不是"更新"：
  - 并发写时两个写请求对缓存的更新顺序不可控，可能把旧值覆盖回去；删除是幂等的
  - 写后未必被读，更新冷数据浪费；缓存常是聚合/加工结果，写时算代价高，懒加载更划算
- 删除失败兜底：删除动作进 MQ 重试；或订阅 binlog（Canal）异步删缓存，把一致性与业务代码解耦
- 延迟双删：删缓存 → 更新 DB → 延迟 N（≈主从延迟 + 业务耗时）再删一次，覆盖"更新期间读请求回填旧值"的窗口；只能收窄不一致窗口不能根治，强一致场景用分布式读写锁或接受最终一致 + 版本校验

### 17. 分布式锁追问链

> **原题要点**：SET NX PX + 唯一值 + Lua 释放；Redisson 看门狗；主从切换锁丢失与缓解。

- 加锁：`SET lock_key uuid:threadId NX PX 30000`——NX 互斥、PX 过期兜底防死锁、value 存持有者标识
- 释放必须 Lua 原子：GET 比对 value 是自己的锁才 DEL，防止误删别人的锁（业务超时锁过期后另一客户端已持锁）

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

- Redisson 看门狗：
  - 未指定 leaseTime 时默认锁 30s，后台定时任务每 10s（1/3 周期）检查持锁状态并重置为 30s，业务没执行完锁不过期
  - 指定了 leaseTime 则不启动看门狗（易被追问的点）
  - 实现：Netty 定时器 + Lua 续期脚本；客户端宕机无人续期，锁到点自动释放
- 主从切换锁丢失：主写入锁后未同步到从即宕机，从晋升，新客户端再加锁 → 两把锁并存
- 缓解：业务侧幂等兜底才是真正防线；fencing token（单调版本号，下游校验拒绝旧 token）；RedLock 多数派加锁（实现复杂、时钟依赖有争议，生产少用）；强一致诉求换 ZooKeeper/etcd 临时顺序节点

### 18. Redis 场景题

> **原题要点**：BitMap 近 7 天连续签到与存储量；ZSet 排行榜 Top100 与分数设计；HLL 统计 1 亿 UV 的精度内存权衡。

**BitMap 连续签到**

- 结构：每人每月一个 key `sign:{uid}:{yyyyMM}`，`SETBIT key (day-1) 1`（day 从 0 计）；BITCOUNT 统计当月签到天数
- 近 7 天连续签到：BITFIELD 取最近 7 个 bit，从当天向高位逐位与判断（或用 `x & (x>>1) & (x>>2) ...` 位运算一次判断连续 N 天）；跨月拼两个月的 key
- 存储量：每天 1 bit，一人一月 31 bit ≈ 4B；1 亿用户一年 ≈ 1 亿 × 12 × 4B ≈ 4.8GB，远小于字符串/关系表方案；uid 稀疏时按月 per-user key 更省
- 统计类需求全部位操作完成，CPU 代价极低

**ZSet 排行榜 Top 100**

- `ZADD/ZINCRBY board score uid` 实时更新；`ZREVRANGE board 0 99 WITHSCORES` 取 Top100；`ZREVRANK/ZSCORE` 查我的排名与分数——均 O(logN)
- 分数设计：只按积分排直接用积分；"同分先到先达"用复合分数：`score = 积分 × 10^k + (MAX_TS − 达成时间戳)`（时间编进低位；注意 double 53 位精度上限，超过就改整数拼接或二级排序）
- 规模：千万级 member 单 ZSet 可用；更大时拆日榜/周榜（定期归档合并），Top N 之外异步落库计算
- 一致性：积分变更与 ZINCRBY 之间用 MQ/事务后置动作保证最终一致

**HyperLogLog 统计 UV**

- `PFADD page:uv:{date} uid...`；`PFCOUNT` 取值；跨天合并 `PFMERGE`
- 内存：每个 key 固定约 12KB，与基数无关——1 亿 UV 仍是 12KB（小基数走稀疏编码更省）
- 精度：标准误约 0.81%；UV/大盘类统计可接受；结算/合规要求的精确 UV 不能用 HLL（用 Set 或精确去重服务，1 亿 UV 的 Set 需要数 GB~10GB）
- 权衡话术：12KB 换 0.81% 误差，非精确场景 HLL 是唯一合理解

## 四、分布式基础

### 19. CAP/BASE

> **原题要点**：用自己的话讲 + 项目例子（讲不出例子视为背书）。

- CAP：网络分区（P）必然可能发生，分区发生时一致性（C）与可用性（A）不可兼得；无分区时可同时满足——不是"三选二"
- 例子（注册中心选型）：Eureka/Nacos（临时实例）是 AP，网络抖动时仍返回可能过期的服务列表保可用，靠客户端重试/熔断兜底；ZooKeeper 是 CP，选主期间拒绝服务。我们选 Nacos AP 保注册可用
- BASE：基本可用（限流降级下仍可用）、软状态（允许中间态）、最终一致（异步复制/对账收敛）
- 例子：下单扣库存用"本地事务 + 消息表 + MQ"最终一致，用户短暂看到"处理中"，定时任务对账补偿——软状态 + 最终一致

### 20. 接口幂等实现盘点

> **原题要点**：手段盘点 + 项目落地方案细节（token / 唯一索引 / 状态机选其一说）。

- 盘点：
  1. 数据库唯一索引：天然防重，最可靠的兜底（撞索引时查回已存在记录返回，与首次结果一致）
  2. token 机制：进页面先领一次性 token 存 Redis，提交时 GETDEL 原子校验，删成功才执行
  3. 状态机/条件更新：`update order set status='PAID' where id=? and status='UNPAID'`，影响行数为 0 视为重复请求
  4. 乐观锁版本号：`where version=?`
  5. 分布式锁：互斥但不幂等，性能一般
  6. 前端防重：按钮置灰、requestId——只防误操作不防重放
  7. MQ 消费幂等：消费记录表 / Redis setnx(msgId)
- 落地细节（token + 唯一索引兜底）：token 校验与删除用 `GETDEL`（或 Lua）保证原子；提交前先查重；插入撞 DuplicateKeyException 时回查已有记录返回——三层防线：前端防误点 → token 防重放 → 唯一索引兜底

### 21. 分布式 ID 方案对比

> **原题要点**：UUID/雪花/号段/Redis 对比；雪花时钟回拨处理。

- UUID：无序导致 InnoDB 页分裂、索引膨胀，36 字符长，无趋势语义 → 不适合主键，适合 traceId
- 雪花：64bit = 1 符号位 + 41 时间戳（约 69 年）+ 10 机器位 + 12 序列号；趋势递增、本地生成无网络开销；依赖时钟与 workerId 分配
- 号段：DB 批量取号段放内存，双 buffer 预加载（美团 Leaf），DB 压力小可用性高；趋势递增但重启跳号
- Redis：INCR 原子自增，简单但强依赖 Redis 可用性
- 时钟回拨处理：
  - 回拨小于阈值：等待追平，或用序列号余量自旋顶住
  - 回拨大：拒绝发号抛异常、告警人工介入
  - 预防：启动/运行时持久化 lastTimestamp 比对；NTP 用 slew 平滑调整；Leaf-snowflake 用 ZK 注册 workerId + 启动校验；或改逻辑时钟（序列溢出视为时间前进）

### 22. 分布式锁的合理使用边界

> **原题要点**：哪些场景该用 DB 唯一约束/乐观锁而不是分布式锁。

- 该用数据库自身机制的场景：
  - 防重复插入：唯一索引（幂等兜底第一选择）
  - 库存扣减：`update stock set num = num - 1 where sku_id=? and num >= 1`——行锁 + 条件更新天然原子
  - 状态流转：条件 update（状态机）
  - 并发版本冲突：乐观锁
- 理由：这些本来就是"单行原子更新"，DB 行锁已保证正确性；再套 Redis 锁是多余组件，引入锁服务故障面、超时误删、主从切换丢锁等新问题
- 分布式锁合理边界：保护"跨多资源/跨系统的复杂临界区"——防定时任务多实例重复跑、防并发初始化、外部调用防抖；且必须配幂等兜底，锁只是性能优化不是正确性根基

### 23. MQ 三连

> **原题要点**：不丢消息；重复消费；顺序消息——各结合所用 MQ 举一例（以 RocketMQ 为例）。

- 不丢消息（三段防守）：
  - 生产端：同步发送 + 失败重试；或异步回调失败落库重投；高可靠用事务消息/本地消息表
  - Broker：持久化（RocketMQ 同步刷盘 SYNC_FLUSH + 主从同步复制；Kafka 对应 acks=all + min.insync.replicas≥2）
  - 消费端：手动 ack（RocketMQ 返回 CONSUME_SUCCESS / Kafka 手动提交 offset），处理完才确认；失败重试 + 死信队列人工介入
- 重复消费：重试机制决定至少一次投递，重复不可避免 → 消费端幂等：业务唯一键唯一索引、消费记录表、状态机条件更新
- 顺序消息：
  - 全局顺序：单 Topic 单队列单消费者，牺牲吞吐，极少用
  - 局部顺序（常用）：同一业务键（订单 ID）发同一队列（RocketMQ MessageQueueSelector / Kafka 按 key 分区），消费端该队列单线程或按 key 内存队列串行
  - 注意：消费失败重试会破坏顺序，顺序消费需阻塞重试而非跳过

## 五、工程实战与排查

### 24. 线上排查组合拳（口述 SOP）

> **原题要点**：偶发超时分层排查；jstack 两种大量状态的含义；连接池打满表现/定位/止损；RT 50→500ms 的完整决策树。

**接口偶发超时的顺序**：监控总览（RT 分位/QPS/错误率是否同时异常）→ 全链路 trace 定位慢在哪一层（自身/下游/DB/缓存）→ 自身：线程池队列与拒绝数、GC 日志（STW 频率时长）、锁竞争 → 下游：DB 慢查询与锁等待、缓存命中率与热 key、第三方超时重试 → 变更比对（发布/配置/数据量）

**jstack 状态解读**：
- 大量 `WAITING (on object monitor)`：线程在 Object.wait() 挂起于监视器等待队列——通常意味着存在锁热点，持锁线程执行慢导致排队；重点找对应的 BLOCKED 线程和持锁 owner（locked <0x...>）
- 大量 `TIMED_WAITING (parking)`：LockSupport.parkNanos——线程池空闲 worker 在 getTask 等任务是正常现象；但若业务线程 worker 大量 parking 且队列堆积/吞吐下降，则可能是线程在等下游（连接池、HTTP 池限时等待也走 park），要结合队列长度与下游指标判断
- 配套动作：先看 BLOCKED 数量与持锁者，`top -Hp <pid>` + `printf "%x"` 线程号转 16 进制到 jstack 对号

**数据库连接池打满**：
- 表现：获取连接超时（HikariCP "Connection is not available, request timed out"）、RT 全面飙升、active = max、等待队列堆积
- 定位：池监控（active/idle/waiting）；常见根因四类——慢 SQL/锁等待占住连接、事务范围过大（事务里调 RPC）、连接泄漏（未归还）、池大小配错
- 止损：重启受影响实例、降级非核心调用、kill 长事务/慢 SQL；根治：慢 SQL 优化、事务瘦身、开泄漏检测（leakDetectionThreshold）

**RT 50ms→500ms 排查决策树**：

```text
RT 恶化
├─ 1. 单实例还是全实例？
│   ├─ 单实例 → 机器层：GC 日志、CPU/IO、宿主机邻居、连接数 → 定位不了先摘流量重启观察
│   └─ 全实例 ↓
├─ 2. 有变更吗？（发布/配置/依赖升级/数据量变化）→ 有：先回滚止血再复盘
├─ 3. 流量涨了吗？→ 涨：容量问题，扩容/限流
├─ 4. trace 定位慢段
│   ├─ 慢在自身
│   │   ├─ GC STW 频繁？→ 调参/查内存泄漏
│   │   ├─ 线程池队列堆积/拒绝？→ 池打满，通常是下游拖慢
│   │   └─ 锁竞争（jstack 大量 BLOCKED）→ 优化临界区
│   └─ 慢在依赖
│       ├─ DB：慢 SQL 日志、explain、锁等待
│       ├─ 缓存：命中率下跌？热 key/大 key？击穿？
│       └─ 第三方：超时 + 重试风暴（重试放大流量）→ 加熔断
└─ 5. 全链路无异常但整体慢 → 基础设施：网络丢包、DNS、时钟、宿主机过载
```

### 25. 日志与监控

> **原题要点**：日志规范（traceId/脱敏/分级）；核心接口监控指标；告警阈值防误报。

- 日志规范：
  - traceId 全链路：入口生成/网关下发，MDC 写入，跨服务 header 透传，MQ 塞消息头；一个请求所有日志可按 traceId 串起
  - 分级：ERROR 必须可行动（可告警）、WARN 需要关注、INFO 关键节点、DEBUG 生产关闭；禁止 e.printStackTrace、禁止吞异常不打日志
  - 脱敏：手机号/身份证/银行卡统一在日志工具层打码；密码/token 等不落日志
  - 结构化 JSON + 关键业务字段（订单号、uid）便于检索
- 核心接口监控指标：
  - 流量：QPS/并发数
  - 质量：错误率（按 5xx 与业务错误码拆分）、RT p50/p95/p99/max（不看平均值）
  - 依赖：下游接口 RT 与错误率、DB 连接池 active/idle、缓存命中率、线程池队列、JVM GC 次数与耗时
- 告警阈值防误报：
  - 用历史分位数基线而非拍脑袋固定值：如 p99 超过去 7 天同时段基线 2 倍且持续 5 分钟
  - 多信号组合（RT 涨 + 错误率涨才告警）、持续窗口平滑毛刺、告警收敛与静默、分级路由（P0 电话、P1 群通知）

### 26. 单元测试与代码质量

> **原题要点**：写不写单测、怎么写、Mock 边界、覆盖率门禁；偶现 Bug 定位案例。

- 态度：核心链路（计费、状态机、金额计算）必写单测；纯 CRUD 不强求
- 怎么写：JUnit5 + Mockito；只 Mock 外部依赖（DB 走 Testcontainers/H2、HTTP 走 WireMock），领域逻辑真实执行；Mock 边界 = 架构端口边界，不 Mock 被测类内部方法（那是在测实现而非行为）

### 30. CompletableFuture 并行调用 3 个下游

> **原题要点**：3 个下游并行 + 各自超时降级 + 任一失败不影响其他 + 汇总返回；线程池注入与超时控制的正确用法。

- 思路要点：
  - 必须用自定义有界线程池，不用默认 ForkJoinPool.commonPool（业务阻塞会饿死公共池，影响并行流等其他功能）
  - 超时用 `orTimeout`（JDK9+）配合 `exceptionally`/`completeOnTimeout` 降级；每个 future 独立处理异常，互不影响
  - `allOf` 汇总后统一 join；降级值兜底保证 join 不抛异常

```java
public class AggregateFacade {

    private static final AtomicInteger SEQ = new AtomicInteger();

    // 自定义有界线程池：核心 8、最大 16、有界队列、明确拒绝策略
    private final ExecutorService bizPool = new ThreadPoolExecutor(
            8, 16, 60, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(256),
            r -> new Thread(r, "aggregate-" + SEQ.incrementAndGet()),
            new ThreadPoolExecutor.CallerRunsPolicy());

    public AggregateResult query(String reqId) {
        CompletableFuture<UserDTO> userF =
                supplyWithFallback(() -> userService.get(reqId), 200, UserDTO::empty);
        CompletableFuture<OrderDTO> orderF =
                supplyWithFallback(() -> orderService.list(reqId), 500, OrderDTO::empty);
        CompletableFuture<CouponDTO> couponF =
                supplyWithFallback(() -> couponService.query(reqId), 300, CouponDTO::empty);

        CompletableFuture.allOf(userF, orderF, couponF).join();
        return new AggregateResult(userF.join(), orderF.join(), couponF.join());
    }

    /** 单个下游：独立超时 + 独立降级，失败不影响其他 future */
    private <T> CompletableFuture<T> supplyWithFallback(
            Supplier<T> task, long timeoutMs, Supplier<T> fallback) {
        return CompletableFuture.supplyAsync(task, bizPool)
                .orTimeout(timeoutMs, TimeUnit.MILLISECONDS)
                .exceptionally(e -> {
                    log.warn("downstream failed: {}", e.toString());
                    return fallback.get();
                });
    }
}
```

- 关键点讲解：
  - 任一下游失败/超时 → 该 future 走 exceptionally 返回兜底值，其他 future 不受影响，最终汇总必有完整结果
  - `allOf(...).join()` 等全部完成；已完成的 future join 立即返回。JDK8 无 orTimeout 时用 `future.get(timeout, MILLISECONDS)` 捕获 TimeoutException 降级，或 `completeOnTimeout(fallback, t, unit)`
  - 线程池要点：有界队列 + 明确拒绝策略、按业务隔离池、拒绝策略慎用 AbortPolicy 之外的静默丢弃

### 31. 布隆过滤器判断 URL 存在（内存 1GB）

> **原题要点**：1 亿 URL 判存、内存 1GB；手写思路 + 误判率讨论。

- 容量估算：
  - 直接存 1 亿条 URL（每条约 100B）≈ 10GB，超限
  - 布隆过滤器位数组长度：`m = -n·ln p / (ln2)²`；n=1e8、p=1% → m ≈ 9.6×10⁸ bit ≈ 114MB；hash 个数 `k = (m/n)·ln2 ≈ 6.64` → 取 7
  - 若要求 p=0.1%：m ≈ 1.44GB 超预算 → 只能接受约 1% 误判，或"布隆粗筛 + DB 精判"两级
- 语义与边界：
  - `mightContain=false` 一定不存在；`true` 可能误判
  - 不支持删除（清位会误伤其他元素），要删用计数布隆/布谷鸟过滤器
  - 容量必须按预期上限预留，超装后误判率飙升
- 手写思路：long[] 位数组；对 URL 算一个 64 位 hash（生产用 Murmur/xxHash），旋转拆出 h1、h2，第 i 个下标 = `(h1 + i·h2) mod m`（Guava 双 hash 技巧，省 k 次 hash 计算）；add 置位，contains 查所有位全 1

```java
public class SimpleBloomFilter {
    private final long[] bits;            // 位数组
    private final int numHashFunctions;
    private final long bitSize;

    public SimpleBloomFilter(long expectedInsertions, double fpp) {
        this.bitSize = Math.max(1,
                (long) (-expectedInsertions * Math.log(fpp) / (Math.log(2) * Math.log(2))));
        this.numHashFunctions = Math.max(1,
                (int) Math.round((double) bitSize / expectedInsertions * Math.log(2)));
        this.bits = new long[(int) ((bitSize + 63) >>> 6)];
    }

    public void add(String url) {
        long hash = murmur64(url.getBytes(StandardCharsets.UTF_8));
        long h1 = hash;
        long h2 = (hash >>> 32) | (hash << 32);          // 旋转得到第二个 hash
        for (int i = 1; i <= numHashFunctions; i++) {
            long combined = (h1 + (long) i * h2) & Long.MAX_VALUE;  // 防负数
            long idx = combined % bitSize;
            bits[(int) (idx >>> 6)] |= 1L << (idx & 63);
        }
    }

    public boolean mightContain(String url) {
        long hash = murmur64(url.getBytes(StandardCharsets.UTF_8));
        long h1 = hash;
        long h2 = (hash >>> 32) | (hash << 32);
        for (int i = 1; i <= numHashFunctions; i++) {
            long combined = (h1 + (long) i * h2) & Long.MAX_VALUE;
            long idx = combined % bitSize;
            if ((bits[(int) (idx >>> 6)] & (1L << (idx & 63))) == 0) {
                return false;                            // 任一位为 0 → 一定不存在
            }
        }
        return true;                                     // 全 1 → 可能存在（有误判）
    }

    /** 简化 64 位混合 hash（生产建议 MurmurHash3 / xxHash） */
    private static long murmur64(byte[] data) {
        long h = 1125899906842597L;
        for (byte b : data) {
            h = (h ^ b) * 0x100000001b3L;
        }
        h ^= (h >>> 33); h *= 0xff51afd7ed558ccdL; h ^= (h >>> 33);
        return h;
    }
}
```

- 误判率讨论：`p ≈ (1 − e^(−k·n/m))^k`，n 为实际插入数；m、k 按预期 n 设计，n 超预期误判率上升；分布式场景直接用 RedisBloom（BF.ADD/BF.EXISTS）或 Guava BloomFilter

### 32. 多线程统计 10GB 文件词频

> **原题要点**：文件切分 → 分片统计 → 合并；ForkJoin/线程池划分与并发汇总。

- 思路：
  - 切分：按字节均分为 N 片（N ≈ CPU 核数），**修正边界**——每片起点跳到下一行首，避免单词被切成两半
  - 分片统计：每个任务在自己的局部 HashMap 统计（无锁），返回局部 Map
  - 合并：主线程串行 merge 到总表；不要让所有线程直接怼 ConcurrentHashMap（高竞争反而慢）
  - 词表极大（超内存）时：先按单词 hash 取模写临时文件分桶，再逐桶统计（MapReduce 思想）

```java
public class ParallelWordCount {

    public static Map<String, Long> count(File file, int workers) throws Exception {
        long fileSize = file.length();
        long chunkSize = fileSize / workers;
        ExecutorService pool = Executors.newFixedThreadPool(workers);
        try {
            List<Future<Map<String, Long>>> futures = new ArrayList<>();
            for (int i = 0; i < workers; i++) {
                long start = i * chunkSize;
                long end = (i == workers - 1) ? fileSize : start + chunkSize;
                futures.add(pool.submit(() -> countRange(file, start, end)));
            }
            Map<String, Long> total = new HashMap<>(1 << 20);
            for (Future<Map<String, Long>> f : futures) {       // 合并阶段
                f.get().forEach((word, cnt) -> total.merge(word, cnt, Long::sum));
            }
            return total;
        } finally {
            pool.shutdown();
        }
    }

    /** 统计 [start, end) 区间；起点对齐行首，保证单词不被切断 */
    private static Map<String, Long> countRange(File file, long start, long end) throws IOException {
        Map<String, Long> local = new HashMap<>(1 << 16);
        try (RandomAccessFile raf = new RandomAccessFile(file, "r")) {
            if (start != 0) {                    // 边界修正：跳过上一分片残留的半行
                raf.seek(start - 1);
                while (raf.read() != '\n' && raf.getFilePointer() < end) { /* skip */ }
            }
            long pos = raf.getFilePointer();
            byte[] buf = new byte[1 << 16];
            StringBuilder word = new StringBuilder(32);
            while (pos < end) {
                int n = raf.read(buf, 0, (int) Math.min(buf.length, end - pos));
                if (n <= 0) break;
                pos += n;
                for (int i = 0; i < n; i++) {
                    byte b = buf[i];
                    if ((b >= 'a' && b <= 'z') || (b >= 'A' && b <= 'Z')) {
                        word.append((char) (b | 0x20));      // 统一小写
                    } else if (word.length() > 0) {
                        local.merge(word.toString(), 1L, Long::sum);
                        word.setLength(0);
                    }
                }
            }
            if (word.length() > 0) local.merge(word.toString(), 1L, Long::sum);
        }
        return local;
    }
}
```

- 关键点讲解：
  - 并发正确性：每个任务只写自己的局部 map，无共享可变状态；合并阶段单线程 merge，天然线程安全
  - 边界修正是正确性关键：start != 0 时先回退一个字节找换行，把残缺半行让给前一个分片
  - 性能取舍：10GB 顺序读是 IO 密集，workers 取 CPU 核数~2 倍即可；纯 ASCII 可按字节处理，UTF-8 中文需按字符解码后切词
  - 备选方案：ForkJoin RecursiveTask 返回局部 map 再 join 合并；或 `Files.lines(...).parallel()` + `groupingByConcurrent`（需自己控制内存）；单机内存放不下词表时分桶落盘（手写 MapReduce）
