## 一、高频经典题

### 1. 短链接服务（如 t.cn）

> 原题要点：生成短链、302 跳转、点击统计，日均 1 亿次跳转；追问短码生成方案、301/302 取舍、热点扛量、统计链路、防刷封禁。

#### 容量估算思路

- 读：日均 1 亿次跳转 ≈ 均值 1200 QPS，按 10 倍峰值系数 ≈ 1.2 万 QPS；单机 Nginx/Go 服务可扛 3~5 万 QPS，2~4 台即可，按机房容灾预留 4 倍。
- 写：跳转 1 亿/天，写读比通常 1:100~1:1000，假设日均 100 万新短链，写 QPS 仅 ~12，写不是瓶颈，核心矛盾在读。
- 存储：每条短链元数据约 200B，年增 3~4 亿条，单表亿级 → 按 hash(code) 分 16 库 64 表；点击明细流水另存（亿级/天，走 LSM 系或 OLAP，不进 MySQL）。

#### 架构分层设计

- 接入层：网关/CDN，承接跳转流量，做限流与封禁拦截。
- 跳转服务（无状态读服务）：短码解析 → 缓存 → 拼接长链 302。
- 发号器服务：独立部署，只保证发号不重复。
- 存储层：MySQL（短链元数据）+ Redis（热短链缓存）+ 布隆过滤器（防穿透）。
- 统计链路：跳转服务发消息到 Kafka → 消费端/Flink 聚合 → 明细入 ClickHouse/Doris，汇总入 MySQL。

#### 关键技术点

- **短码生成三方案对比**：
  - 自增 ID + Base62：62^6 ≈ 568 亿，6 位够用；优点无冲突、短、实现简单，缺点 ID 连续可被遍历爬取（可对 ID 做可逆混淆，如 Knuth 乘散列）。
  - 哈希（MurmurHash + Base62）：无需发号器，但 62^6 空间下数据量稍大即有碰撞，需要冲突再哈希或落库比对，写路径复杂。
  - 发号器预分配号段（推荐）：DB 存当前 max_id，服务一次取一段（如 1000 个），内存分配；双 buffer 预加载避免号段用尽时抖动；DB 宕机可用剩余号段撑数小时。生产主流做法。
- **301 vs 302**：301 永久重定向，浏览器缓存后不再回源，省流量但丢失点击统计、无法改跳转目标（换域名即失效）；302 每次经过服务端，可统计、可灰度、可随时改目标。做统计的系统必选 302，用 CDN/边缘缓存 + 边缘打点补服务端压力。
- **热点扛量**：本地缓存（Caffeine）→ Redis（LRU/LFU + 热 key 分片）→ 布隆过滤器（短码不存在直接 404，防穿透；布隆不支持删除，用计数布隆或定期重建）；miss 回源加限流防击穿，缓存空对象防穿透。
- **统计链路**：跳转时只做 Redis INCR + 发 Kafka（异步内存操作），绝不同步写 DB；Kafka 消费端批量聚合成 5 分钟/小时/天粒度，明细入 OLAP。丢少量明细可接受（万分级），关键指标用 Redis 计数 + 定时对账修正。
- **防刷与封禁**：接入层按 IP/设备指纹/UA 限流与黑名单；创建侧对长链做安全检测（钓鱼/黄反词库 + 第三方安全 API，异步扫描已入库链接）；短链加状态位（正常/封禁/待审），封禁后 302 到提示页而非物理删除（保留统计与审计）。

#### 追问点应答

- 同一长链重复生成？按用户/渠道维度允许重复（独立统计），或长链 hash 唯一索引返回既有码，二选一并说明权衡（去重省空间 vs 渠道独立统计）。
- 自定义短码？单独命名空间（加前缀位），与发号器空间隔离避免冲突。
- 过期策略？冷数据归档 KV 存储，跳转服务按 hash 查冷库兜底。

#### 常见坑

- 用 301 导致统计永远丢失，无法补救。
- 统计同步写库拖垮跳转主链路。
- 布隆过滤器只加不清，误判率随元素增长劣化，必须有重建机制。
- 短码可预测被恶意批量生成垃圾短链，创建接口要加频控。

### 2. 秒杀/抢购系统

> 原题要点：10 万 QPS 峰值、1000 件库存、防超卖；追问流量逐层削减、Redis 原子扣减与库存分桶、Redis/DB 一致性兜底、防黄牛一人一单、降级预案。

#### 容量估算思路

- 10 万 QPS 中有效请求 ≤ 1000（库存数），其余 99% 是要被层层削减的无效流量——设计本质是「让流量在越靠近用户的层死掉越便宜」。
- 下单成功峰值 = 库存消耗速度，MQ 消费侧几百 QPS 足够，DB 写压力天然很小。
- Redis 单 key 扣减极限约 8~10 万 ops/s，单 key 恰好顶到上限，所以要分桶。

#### 架构分层设计

- CDN/静态页：秒杀页静态化，倒计时/活动信息走 CDN；动态接口前置答题/验证码打散请求。
- 网关层：令牌桶限流（接口 + 用户 + IP 多维）、黑名单、非法参数拦截。
- 秒杀服务：前置校验（活动状态、售罄标记）→ Redis Lua 预扣减 → 发 MQ。
- 订单服务：消费 MQ 创建订单、DB 真实扣减，支付超时回补。
- 存储：MySQL（订单、真实库存），Redis（预扣库存、一人一单标记）。

#### 关键技术点

- **逐层削减**：页面静态化 + CDN → 按钮置灰 + 答题（天然延迟 2~3 秒削峰）→ 网关限流（如放 2 万 QPS）→ 售罄标记（Redis 内存判断，售罄后直接拒绝，不再到 Lua）→ 预扣成功才进 MQ。
- **Redis Lua 原子扣减**：把「查库存 → 查一人一单 → 扣库存 → 记录用户」合成一个 Lua 脚本，Redis 单线程执行保证原子，天然防超卖。核心逻辑：先 HSET 判 uid 重复则返回 -1；DECR stock 后 <0 则 INCR 回滚并返回 0；否则记录用户返回成功。
- **库存分桶**：stock_0~stock_9 共 10 个 key 各存 1/10 库存，用户 hash 到桶，单 key 热点拆成 10 份，扛到百万级 QPS。分桶副作用与处理：
  - 桶间倾斜（某桶先空）：本桶为空时随机/顺延尝试其他桶，最多重试 2 次；
  - 有库存但扣不到：设兜底桶（10% 库存，其他桶空后统一打到兜底），或后台异步把空桶未售配额再均衡到热桶；极致做法是「扣不到返回排队中」，由后台合并视角再判定。
- **Redis 与 DB 一致性**：Redis 是「预扣/准」，DB 是「实扣/账」。MQ 丢失或订单服务失败 → 少卖（可接受，回补即可）；预扣方向 Lua 已保证不超卖。兜底：①支付超时（15 分钟）延迟消息回补 Redis + DB；②定时对账任务比对「Redis 剩余 + 已售单数 vs DB 库存」，漂移以 DB 为准修正并告警。
- **防黄牛、一人一单**：Redis 层 Lua 内 HSET uid 幂等标记（快速拦截）；DB 层 order 表 (uid, sku_id) 唯一索引兜底，双重幂等缺一不可（Redis 故障/淘汰后 DB 还能拦）。叠加设备指纹/风控名单、答题、同 IP 频控。
- **降级预案清单**：①网关限流阈值动态调小；②活动紧急止血直接返回售罄页；③关闭库存查询等旁路接口；④MQ 堆积时订单服务降级为先落排队表、异步补单；⑤Redis 集群故障 → 活动熔断拒绝而非放行（宁少卖不超卖）；⑥DB 故障 → 停发 MQ，库存锁死。

#### 追问点应答

- 为什么不用 DB 行锁直接扣？10 万 QPS 到 DB 必死，且热点单行锁串行化吞吐只有几百/s。
- 为什么不用分布式锁？锁是串行化，Lua 天然串行且一次网络往返。
- 预扣成功不支付？延迟消息回补，回补前先查订单状态并加锁，防止「回补与支付」并发。

#### 常见坑

- Lua 里写循环/复杂逻辑，阻塞 Redis 全部请求。
- 只在 Redis 判重、DB 唯一索引缺失，Redis 缓存淘汰后重复下单。
- 超时回补与用户恰好支付并发，造成付了钱却回补了库存。
- 分桶后总库存 ≠ 各桶之和（初始化出错），少卖或超卖，上线前脚本校验。

### 3. Feed 流系统（微博/朋友圈）

> 原题要点：推/拉/混合选型与大 V 百万粉丝处理；收件箱/发件箱存储模型与选型；分页翻页、取关清理、删帖同步；冷热分层；推拉结合下的一致性。

#### 容量估算思路

- 假设 1 亿 DAU、人均日刷 10 次、每次 20 条 → 读 QPS 均值 ~2.3 万、峰值 10 万+，读是绝对主体，决定「写扩散换读性能」的方向。
- 发帖日均 5000 万条，写 QPS 低；但大 V 单条触达百万粉丝，写扩散瞬间放大 → 推拉结合的依据。
- 收件箱：1 亿用户 × 1000 条 = 千亿级条目，必须限制收件箱长度（如 3000 条滚动淘汰）。

#### 架构分层设计

- 发布服务：写发件箱（作者 timeline）→ 计算推送目标（推 or 拉）→ 异步推送任务。
- Timeline 服务：读收件箱聚合 + 读时拉大 V 发件箱归并。
- 内容服务：feed 索引只存 post_id，正文/图片按 id 批量取（索引与内容分离）。
- 存储：收件箱 Redis ZSet（score=时间/sequence）；发件箱/内容 DB；归档用 LSM 系（RocksDB/HBase）。

#### 关键技术点

- **推拉结合选型**：
  - 推模式（写扩散）：发布时写入每个粉丝收件箱，读 O(1)；写放大 = 粉丝数。
  - 拉模式（读扩散）：读时拉关注列表各发件箱归并，读放大；大 V 发帖零成本。
  - 混合（主流）：按粉丝数分级，粉丝 < 10 万 → 推；≥ 10 万 → 不推、读时拉；长期不登录用户也可不推，登录时按关注列表拉取补齐。
- **收件箱/发件箱模型**：收件箱 = 每用户一个 ZSet（member=post_id，score=发布时间），ZREVRANGEBYSCORE 做 cursor 翻页（用上页最后一条的 score，避免 offset 深翻页与重复）；ZREMRANGEBYRANK 只留最近 N 条。发件箱 = 作者维度 post 列表存 DB。
- **取关与删帖**：取关不物理清理收件箱（避免 delete 风暴），读时按关注关系过滤，异步低峰批量清理兜底。删帖：发件箱标记删除（tombstone）→ 读时过滤 → 收件箱异步清理；未清理的靠内容服务返回 404 时降级跳过。
- **冷热分层**：活跃（7 天内登录）用户收件箱在 Redis；沉睡用户过期落 HBase/RocksDB，登录触发异步预热回填；超 N 个月的 feed 只保留 id 列表，正文走归档存储。
- **一致性**：先写发件箱拿到全局 sequence，再投递推送（MQ 至少一次）；推送失败重试，读侧兜底「收件箱 + 关注列表拉取合并去重」——即使推送丢也不丢内容。同一作者帖子按 sequence 保序推送，避免乱序。

#### 追问点应答

- 大 V 发帖百万推送？推送任务按粉丝 hash 拆几百个子任务入 MQ，消费端限速执行（几分钟完成，用户无感），配合读时拉兜底。
- 转发链去重？发件箱聚合转发根 id，收件箱按根 id 去重。
- 为什么不用 DB 存收件箱？读 QPS 太高 + 翻页深，Redis ZSet 是最优读写折中；全量存 LSM 系、Redis 只做热层。

#### 常见坑

- 收件箱不设上限，Redis 内存被打爆。
- 翻页用 offset，插入新帖导致重复/漏读；必须 cursor。
- 删帖只删发件箱，收件箱残留数据在读时过滤但没处理内容 404 的降级。
- 推送同步执行，大 V 发帖把发布接口打挂。

### 4. 分布式文件存储（类网盘）

> 原题要点：文件分块、哈希去重、元数据与数据分离；小文件合并存储（Compact）；副本分布（机架感知）与一致性协议；断点续传与秒传；元数据分片与迁移。

#### 容量估算思路

- 设 1 亿用户、实际存量 500PB~1EB：单盘 16TB → 数万块盘、数千节点，硬件故障是常态（日故障盘 = 节点数 × 盘数 × 年故障率/365），副本修复是核心日常。
- 元数据：平均文件 100MB / 64MB 块 → chunk 数亿级，映射 ~100B/条，单机内存可容纳（百 GB 级）；文件数到百亿必须分片。
- 读写比约 10:1（网盘典型），读路径要缓存与就近副本。

#### 架构分层设计

- 客户端 SDK：切块、哈希、断点记录、多线程并行上传。
- 元数据服务（Master 集群）：文件树、file → chunk 列表、chunk → 副本位置。
- 数据节点（ChunkServer）：存 chunk，心跳上报、副本修复。
- 调度组件：上传/下载流量调度、副本放置与容量均衡。

#### 关键技术点

- **分块**：大文件按 4~64MB 切块（太大重传代价高、太小元数据膨胀），并行上传提吞吐；每块算 SHA-256 作为内容寻址 CID。
- **去重与秒传**：上传前先查 CID 索引，命中即「秒传」，只建引用（引用计数 +1）；删除时计数 -1，为 0 才异步 GC 物理删除。注意同 CID 跨用户的权限隔离，引用计数必须有对账。
- **元数据/数据分离**：Master 内存维护全量映射 + WAL/快照持久化（RocksDB），用 Raft 三副本防单点；数据节点只存块。
- **小文件问题**：百万级 1KB 文件 → 元数据爆炸 + 盘上 inode/随机读浪费。方案：小文件（<1MB）追加写入段文件（segment ~1GB），索引记录 (file → segment_id, offset, len) 放 LSM；后台 Compact 合并、回收垃圾段。
- **副本与一致性**：默认 3 副本，放置「本机架 1 + 跨机架 2」（机架感知，防整机架故障又兼顾机架内带宽）；写一致性选 Raft Quorum（强一致）或「主副本写 + 异步从副本」（最终一致，吞吐优先）；冷数据用纠删码 EC（1.5x 开销替代 3x 副本，省 50% 空间，代价是修复带宽高）。
- **断点续传**：按 chunk 粒度上传，服务端记录已收 chunk 清单，重传只补缺失块；全部分片到齐后合并（校验各块 CID）。
- **元数据扩展**：按用户/目录前缀 hash 分片（保留目录局部性，避免 ls 跨片）；迁移用一致性哈希 + 双写期 + 读写切换，或按子树搬迁。

#### 追问点应答

- 副本修复风暴：节点挂掉上千块需重建 → 限速队列，优先级 = 丢失副本数（3→2 优先于 2→1）。
- 一致性协议怎么选：元数据/目录树用 Raft（量小、强一致）；数据块多数场景最终一致即可，按产品语义取舍。
- GC：异步引用计数 + 定期全量对账（元数据 vs 数据节点实际块）。

#### 常见坑

- 元数据不分片又低估文件数，内存溢出后被迫停机迁移。
- 秒传引用计数无对账，出现「删自己的文件把别人的也弄坏」事故。
- 小文件直接进对象存储不合并，成本与延迟双杀。
- 副本修复不限流，占满机房内带宽影响在线读。

### 5. IM 即时通讯系统

> 原题要点：长连接网关单机百万连接（内存/fd/心跳）；消息 ID 与不丢不重不乱序（单聊/群聊）；群聊读写扩散与万人群；离线消息与多端同步（sequence 号）；已读回执、撤回、端到端加密。

#### 容量估算思路

- 1 亿 DAU、人均 1.5 设备 → 峰值 2 亿长连接；单机 50~100 万连接 → 接入层 200~400 台，按 3 倍冗余。
- 消息峰值假设 100 万条/s；存储按条数 × 平均 2KB，年千亿条 → 消息库按会话/时间分片 + 归档。
- 心跳 4.5 分钟/次：单机 100 万连接 → 每秒 ~3700 心跳包，可承受；心跳间隔是电量与假在线的权衡。

#### 架构分层设计

- 接入层（长连接网关）：只管连接、鉴权、心跳、编解码、uid → 连接的路由表。
- 逻辑层（消息服务）：sequence 分配、消息持久化、扩散写、ACK 处理。
- 存储层：消息表（按会话分片）+ 收件箱/序列号表 + 关系库。
- 推送通道：在线走长连接直推，离线走厂商通道（APNs/各厂商推送）。

#### 关键技术点

- **单机百万连接**：epoll/Netty，少量 EventLoop 线程服务海量连接；连接元数据精简到 ~1KB（百万连接 ≈ 1GB 内存）；fd 上限（ulimit、somaxconn）与堆外内存（避免 GC 停顿）；心跳 4.5 分钟（覆盖主流 NAT 表项超时）+ 随机抖动（防集中心跳雪崩）+ 读空闲踢死连接。
- **消息 ID 与顺序**：全局去重用 client_msg_id（客户端 UUID，服务端按其幂等）；会话内排序用服务端 sequence：单聊按「会话」分配、群聊按「群」分配，sequence 单调递增，是收件箱与多端同步的基准。seq 按 hash 分段分派，避开单点热点。
- **不丢**：发送端本地保存待确认消息，超时重发（同 client_msg_id 幂等）；服务端「先持久化 + 写收件箱，再推送」，设备 ACK 后才删除；推送失败重试 + 离线补拉兜底。
- **不重不乱序**：服务端按 client_msg_id 去重；接收端按 sequence 判断——重复 seq 丢弃，中间缺失触发拉取补洞。
- **群聊读写扩散**：小群（<200 人）写扩散到每个成员收件箱（读快）；万人群用读扩散——群消息只写群 timeline 一份，成员各自维护已读位点（last_ack_seq），在线只推「群有新消息、当前 seq=N」信令，端上按需拉取。折中：写扩散到群收件箱 + 成员位点，推送只推信令。
- **多端同步（sequence 机制）**：每用户每设备一个 sync_seq 位点；在线时服务端推消息，设备 ACK 后才推进位点（未 ACK 重推）；设备上线/重连携带本地 sync_seq，服务端返回增量（seq > sync_seq），拉齐后位点对齐——任何设备任何时刻都能恢复完整状态。
- **已读回执/撤回/E2E**：已读是特殊信令消息，服务端转发并更新会话未读数；撤回 = 在原 seq 位置写 tombstone（「已撤回」占位替换），随多端同步自然生效；E2E 用 X3DH 密钥协商 + Double Ratchet（Signal 协议），服务端只见密文——代价是服务端无法搜索/风控/审核，需产品权衡（企业场景通常放弃 E2E 换合规）。

#### 追问点应答

- sequence 服务怎么扛并发？按会话/群 hash 分段，seq 本质是本地单调计数 + 号段预分配，单会话内串行即可。
- 消息漫游？热库保 7 天，历史消息冷库归档按需拉取。
- 万人群推送风暴？只推信令 + 未读数，内容由端上拉取合并，绝不全量推消息体。

#### 常见坑

- 用客户端时间戳排序，时钟漂移导致乱序；必须服务端 sequence。
- ACK 语义不清（收到 vs 已处理）导致重复推送风暴。
- 心跳 30s 一发，耗电且没覆盖 NAT 超时。
- 消息表按 uid 分片导致单聊要跨两个分片查，应按会话 ID 分片。

### 6. 支付系统/账务系统

> 原题要点：复式记账、账户表设计与余额并发扣减防负数；账务强一致与热点账户缓冲/异步记账；对账（日切、文件解析、长短款）；幂等、防重放、限额；挂账、冲正、退款边界。

#### 容量估算思路

- 设大促峰值 10 万笔/s 支付、每笔 2~4 条分录 → 记账 30 万 TPS 级，单库写不动 → 分录表按账户维度分片 + 热点账户异步化。
- 余额读多，走缓存 + 「余额 = 期初 + Σ流水」可重算原则，保证可审计。
- 对账 T+1，日对账文件千万~亿行，解析与比对用分布式批处理。

#### 架构分层设计

- 收单层：收银台/二维码等支付产品 → 支付指令。
- 支付核心：支付单状态机、渠道路由、风控。
- 账务系统：记账引擎（分录生成、余额更新）、账户中心。
- 对账/清结算：渠道对账、内部对账、差错处理、出款。

#### 关键技术点

- **复式记账**：每笔交易生成借贷平衡分录（借=贷），如用户支付 100 元：借「用户支付账户」100、贷「商户待结算」100（平台另记手续费分录）。账户表 (account_id, balance, version, status)；分录流水表 (voucher_no, 借账户, 贷账户, 金额, 业务单号) 只增不改；余额永远可由「期初 + 流水重放」验证——这是审计与对账的根基。
- **余额并发扣减防负数**：单账户事务内 `UPDATE account SET balance = balance - ? WHERE account_id = ? AND balance >= ?`，影响行数=0 即余额不足（天然防负数）；高频账户用行锁（select for update + 分录同事务）。禁止「先查后改」。
- **热点账户**：大商户/大促总账户单行锁成瓶颈。方案：①缓冲记账——交易先记缓冲流水，异步批量汇总入主账户，余额允许分钟级延迟，对外展示「可用余额 = 主余额 + 在途」；②拆影子子账户（100 个，按单号路由）摊并行锁；③记账限流排队。
- **强一致方案**：同库内「业务单 + 分录」本地事务；跨系统（支付 vs 账务）用可靠消息（本地消息表/事务消息）+ 幂等消费，最终一致；关键资金动作用 TCC（try 冻结、confirm 扣减、cancel 解冻）+ 空回滚/悬挂处理。
- **对账**：日切统一（如 23:59:59 切日，渠道与我方口径必须一致，跨日交易按支付成功时间归属）；流程：下载渠道对账文件 → 解析标准化 → 与本地流水按单号+金额+状态比对 → 差异分类：长款（渠道有我方无：掉单，补单或挂账）、短款（我方有渠道无：状态错误，冲正）、金额不符 → 自动差错池 + 人工工作台；当日对不平挂过渡科目（挂账），次日续对。
- **幂等/防重放/限额**：支付单号全局唯一 + 状态机（CREATED→PAYING→SUCCESS/FAILED，只允许合法迁移）；渠道回调按渠道单号唯一索引幂等；防重放：timestamp + nonce（Redis 去重）+ HMAC 签名；限额：单笔/单日/单卡规则引擎，超限拒绝并记风控事件。
- **边界场景**：挂账 = 长款先进过渡科目不进损益；冲正 = 原交易的反向分录（限当日、与原单幂等关联，冲正前先冻结原单防并发）；退款 = 关联原单、累计退款 ≤ 原单金额、可部分多次，退款单同样走完整记账与对账。

#### 追问点应答

- 为什么不追求全局强一致？资金链路「少记可补、多记是事故」，最终一致 + 对账兜底 + 冲正工具，比全局分布式事务更可靠可运维。
- 余额缓存不一致？展示层允许短暂延迟，动账操作永远以 DB 行为准。
- 渠道对账文件延迟？分级处理，先对已到的，缺文件挂起告警续跑。

#### 常见坑

- 先改余额后记流水（崩溃后两表不一致），必须同事务且流水可重放。
- 日切口径与渠道不一致，边界交易永远对不平。
- 冲正与原交易并发，产生双倍动账。
- 热点账户直接加锁，大促时记账线程池被占满拖垮整个账务系统。

## 二、进阶场景题

### 7. 分布式任务调度平台

> 原题要点：单机定时任务集群化的问题与核心目标（分片、不重不漏、failover）；时间轮原理与海量延迟任务存储；分片策略、动态上下线、任务抢占；DAG 编排、重试超时；与 XXL-Job/Elastic-Job 对比及核心模型。

#### 容量估算思路

- 设接入 5 万应用、百万级任务、触发峰值 10 万次/分钟；调度决策是轻计算，瓶颈在「触发精度」与「执行回执吞吐」。
- 延迟任务到千万级/天（如订单超时关闭）时，存储必须按「执行时间分桶」而不是逐条调度。

#### 架构分层设计

- 调度中心（多主分域）：任务管理、触发（时间轮）、分片分配、failover。
- 注册中心（ZK/etcd）：执行器上下线（临时节点）。
- 执行器：业务进程内嵌 agent，拉取分片执行、上报回执。
- 存储：任务定义表、调度日志表、执行记录表。

#### 关键技术点

- **单机定时任务的问题**：多实例同时触发（重复执行）、部分实例宕机没人执行（漏跑）、无统一管理。补丁是每实例抢分布式锁，但无分片、无 failover、无重试与依赖编排——所以要平台化。
- **时间轮**：环形数组 + 指针，槽位=时间粒度（如 1s），任务挂槽位链表，tick 推进触发，插入/删除 O(1)；跨期任务多层时间轮（秒→分→时）降级。海量延迟任务：时间轮只装未来 2 小时内的（内存可控），远期任务落 DB/Redis 按「执行小时」分桶，后台逐小时装载进时间轮；也可用 RocketMQ 定时消息类组件。
- **分片与抢占**：任务定义分片总数 N（如数据范围 0..N-1），调度中心按节点列表一致性哈希分配；节点上下线走 ZK watch 触发 rebalance（最小迁移）；「抢占」用注册租约——节点定期续租，失联节点分片在租约过期后转移（failover），执行器侧按幂等键防重复执行。
- **不重不漏**：调度日志表唯一约束（task_id + 触发时间 + 分片号），先写日志（幂等键）再派发；执行器回执更新状态；超时未回执按策略重试（新触发号，幂等由业务保证）。
- **DAG 编排**：依赖存边表，运行时拓扑排序生成执行计划，上游全成功才触发下游；失败策略：重试 N 次（指数退避）→ 标记失败 → 按「允许失败/阻塞下游/终止整链」语义传播；超时：执行器本地 kill + 调度中心对账强杀（防执行器假死）。
- **对比与核心模型**：XXL-Job 中心化调度 + HTTP 回调，模型简单、社区成熟；Elastic-Job 基于 ZK 分片，去中心化但运维重。自研核心六要素：任务定义 / 触发规则（cron/延迟/依赖）/ 分片策略 / 调度实例（一次触发）/ 执行记录 / 回执，再加时间轮 + 注册中心。

#### 追问点应答

- 时钟漂移？时间轮用单调时间推进 + NTP 校准，秒级任务允许 ±1s 误差，金融级做固定延迟补偿。
- 大任务阻塞？执行器线程池按任务组隔离 + 任务级超时 + 子任务拆分。
- 亿级调度记录？日志表按天分表 + 异步批量写 + 定期归档。

#### 常见坑

- failover 转移时原节点其实还活着（网络分区），两边都跑——执行器必须按调度日志唯一键幂等。
- 节点频繁抖动导致 rebalance 风暴，分片反复迁移——加稳定窗口。
- 时间轮任务触发后忘记从槽移除，引用泄漏。

### 8. 配置中心（类 Nacos/Apollo）

> 原题要点：配置发布、监听（长轮询 vs 推送）、灰度发布；长轮询底层原理与交互时序；多节点一致性；客户端容灾（本地快照）；敏感配置加密与权限。

#### 容量估算思路

- 1 万客户端 × 100 个配置项，监听常驻连接/长轮询数万级；服务端压力集中在「变更推送瞬间」与「重启后全量拉取风暴」。
- 可用性高于一致性延迟：配置中心挂 1 分钟不能导致业务挂，读路径必须多级兜底。

#### 架构分层设计

- 控制台：配置编辑、审批、灰度、回滚。
- 配置服务集群：配置存储（DB 单写源 + 节点缓存）、监听管理、变更通知。
- 客户端 SDK：拉取 + 监听 + 本地快照 + 内存缓存 + 变更回调。

#### 关键技术点

- **发布与监听**：发布 = 写 DB（版本化，每次生成 release 记录）→ 通知各节点刷新缓存 → 通知监听客户端。监听两种实现：
  - 长轮询（Apollo 经典）：客户端携带 key + 本地 md5 发起请求；服务端比对 md5，不一致立即返回变更 key 列表；一致则 hold 住请求（Servlet 异步上下文，如 30s），期间任何变更由内存监听器唤醒返回；客户端收到变更 key 后再单独拉取最新配置内容。
  - 推送（Nacos gRPC）：客户端与服务端建 gRPC 长连接，变更主动推，实时性更好，但要处理连接重建与推送丢失（推失败降级拉取）。
- **灰度发布**：发布时指定灰度规则（IP 列表/实例标签/百分比），灰度配置单独存 release；客户端上报标签，服务端按标签返回灰度版或正式版；验证通过「全量发布」，未通过一键回滚到上一 release（发布历史全保留）。
- **多节点一致性**：配置写走 DB 单写源，节点缓存订阅变更总线（MQ 广播 + DB 增量轮询兜底），秒级最终一致；要强一致可把配置放 Raft 存储。原则：任意节点可读，写必须过主源，避免脑裂。
- **客户端容灾**：三级兜底：①内存缓存（进程活着就能读到）；②本地快照文件（每次成功拉取写盘，配置中心全挂时用快照启动）；③全挂且无快照 → 内置默认值 + 告警。拉取失败指数退避重试。
- **敏感配置**：KMS 信封加密，DB 存密文，客户端持密钥解密且密钥与配置分离下发；权限：命名空间/应用粒度 RBAC + 编辑与发布分离的审批流 + 全量操作审计。

#### 追问点应答

- 长轮询 vs WebSocket？长轮询实现简单、断线自然重试；推送实时但需管理连接状态；Nacos 2.x 用 gRPC 双向流。
- 客户端怎么「无感热更新」？SDK 注册变更回调，key 变更触发业务回调（如重建连接池）。
- 为什么变更通知只带 md5/key 不推内容？内容由客户端按需拉取，避免大配置重复传输与通知包过大。

#### 常见坑

- hold 请求时长超过链路上网关/LB 的空闲超时（如 60s），连接被掐断假死——hold 时长必须小于链路最小超时。
- 灰度配置忘记清理，正式发布后部分实例停留在灰度版本。
- 只依赖内存缓存不落盘，配置中心故障 + 应用重启 = 起不来。
- 变更通知丢一条导致节点缓存长期不一致——必须有周期性全量比对兜底。

### 9. 抢红包系统

> 原题要点：金额拆分算法（二倍均值法等）与执行时机；抢与拆分的原子化（Redis Lua / DB 乐观锁 + 流水）；领取的账务一致性与 24h 退回；明星红包瞬时热点（异步化、排队）。

#### 容量估算思路

- 普通红包：500 元/1000 个，抢的人峰值 5000 QPS——单红包热点，所有请求压同一个 key。
- 明星红包：100 万元/100 万个、1 亿用户参与，瞬时千万级 QPS——必须接入层削减 + 存储分片 + 随机化打散。
- 发红包低频写、抢红包极端读 + 单次写；拆分金额在发红包时预生成，可把「抢」简化为「出队」。

#### 架构分层设计

- 接入层：频控（同 uid/IP）、随机延迟打散、售罄标记。
- 红包服务：发红包（拆分 + 预生成）、抢红包（Lua 原子出队）、领取记录。
- 账务系统：资金冻结、入账划转、退回冲正。
- 延迟任务：24h 未领完退回（时间轮/延迟队列）。

#### 关键技术点

- **拆分算法与时机**：二倍均值法——每次抢在 [0.01, 2 × 剩余金额/剩余个数) 随机，期望均匀、最后一个拿剩余全部（需校验「剩余 ≥ 个数 × 0.01」）。执行时机选「发红包时预拆分」（推荐）：发的时候一次性生成 N 个金额（校验总和=总额、每个≥0.01），写入 Redis List；抢时 LPOP 出队即得金额——抢路径极简、无拆分竞态。实时拆分（抢时才算）要在事务里算金额+写流水，热点下更慢，只适合小并发。
- **抢与拆原子化（Redis Lua）**：一个脚本完成：①判断红包状态（未抢完、未过期）；②LPOP 金额（nil 即抢完，置 sold-out）；③HSET 领取人记录（uid → 金额，天然防同一人重复抢）；④DECR 剩余个数。DB 兜底：red_packet 表乐观锁 `UPDATE ... SET remain = remain - 1 WHERE id=? AND remain>0` + 领取记录唯一索引 (packet_id, uid)；Redis 数据丢失后以 DB 流水重建。
- **账务一致性**：发红包 = 用户余额扣款 + 红包资金池冻结（复式记账）；抢到 = 冻结户划转领取人（MQ 异步入账，抢接口只返回金额）；24h 退回 = 延迟任务基于到期索引/延迟消息精准触发，把剩余金额原路退回付款人并记冲正流水。竞态：退回前把红包状态 CAS 为「结算中」，之后的抢请求直接失败；退回与最后一抢并发由状态机 + 唯一流水保证只发生一个。
- **明星热点**：①拆分结果按 hash 切 N 个 Redis 分片 key（list_0..list_9），接入层随机/按 uid 路由，摊平单 key 热点；②抢到后一切后续（入账、记录、通知）MQ 异步化，抢接口只做内存级 Lua；③产品级削峰：客户端排队动画拉长感知时间；④开抢前详情页静态化 + CDN，按钮解锁时间由服务端下发防本地时钟作弊。

#### 追问点应答

- 二倍均值法为什么合理？剩余均值随领取收敛，整体无和差错误；缺点是先抢的人金额方差大，可用「等概率洗牌预拆」替代。
- Redis 挂了？Redis 只做加速与原子性，DB 有完整发放/领取流水可全量重建；恢复期间红包暂不可抢（宁可暂停不可多抢）。
- 领取记录与转账不一致？以账务流水为准逐笔对账（红包记录 vs 冻结户分录），差异进差错处理。

#### 常见坑

- 实时拆分并发下最后一个红包算成 0 或负数（0.01 保底与「剩余 = 个数 × 0.01」校验缺失）。
- sold-out 标记与 LPOP 非原子，出现「显示抢完但还剩金额」。
- 24h 退回用定时任务全量扫表，量大拖垮 DB——应基于到期索引 + 延迟消息精准触发。

### 10. 代码发布/部署系统（类 PaaS）

> 原题要点：发布流水线建模与发布单状态机；灰度策略（比例/机器/流量标记泳道）；健康检查与自动回滚的触发与实现；多机房发布顺序；配置与代码发布顺序依赖。

#### 容量估算思路

- 设 5000 应用、日均 2000 次发布、单应用 500 实例；发布系统瓶颈不在并发，而在「编排正确性」与「失败恢复速度（MTTR）」。
- 制品：每次构建 ~100MB 镜像，日 2000 次 → 200GB/天，制品库需生命周期清理。

#### 架构分层设计

- 发布控制面：发布单管理、审批流、编排引擎（状态机驱动）。
- 执行面：Agent/Job 平台，在各机器执行「拉制品 → 替换 → 起服务 → 探活」。
- 制品库：镜像/包版本管理，不可变（同版本禁止覆盖）。
- 联动组件：配置中心、注册中心（发布时摘流量、挂元数据标签）。

#### 关键技术点

- **流水线建模与状态机**：应用 → 发布单（一次发布） → 批次（灰度分批） → 实例（机器）；发布单状态机：创建 → 审批 → 构建 → 发布中（批次 1 → 观察 → 批次 2 …）→ 全量 → 完成 / 回滚中 / 回滚完成 / 取消；每次状态迁移落库，支持追溯与断点续跑。
- **灰度策略**：①按机器比例：1 台 → 10% → 50% → 100%，批次间强制观察窗口；②按机器分组：先发非核心机房/实例组；③按流量标记（泳道）：实例打标签（如 gray=feature-x），网关按 header/uid 尾号把带标流量路由到对应泳道，实现请求级灰度；依赖服务通过标签透传实现全链路泳道。
- **健康检查与自动回滚**：三层检查——进程/端口探活、就绪接口（依赖连通）、业务指标对比（错误率/RT/QPS 与旧版本基线比较，如「错误率 > 1% 持续 2 分钟」）。发布时序：先从注册中心摘流量 → 部署 → 探活通过 → 重新注册引流，逐实例滚动。自动回滚：命中触发条件 → 停止后续批次 → 反向把已发批次重新部署上一版本制品（制品不可变，回滚=重部署旧版本）→ 告警通知，回滚同样保留人工卡点防误判。
- **多机房顺序**：按「观察机房 → 核心机房」顺序，机房间设置观察间隔（如 10 分钟）+ 人工卡点；单元化架构按单元逐个发布。
- **配置与代码依赖**：原则「配置先行且向后兼容」——新配置必须兼容旧代码（N-1 兼容）；顺序：发配置 → 观察生效 → 发代码；回滚时先回滚代码再回滚配置；不兼容变更用双配置/双读开关过渡。

#### 追问点应答

- 有状态服务发布？先连接排空（摘流量后等长连接自然结束或最长 N 秒强断），本地状态做副本迁移/主从切换。
- 发布系统自身挂了？控制面无状态多活、状态全落库；执行面 agent 支持断点续跑；保留 SSH 手工发布兜底通道。
- 构建可重复性？镜像不可变 + 构建环境锁定（同一 commit 构建出同一 digest）。

#### 常见坑

- 制品覆盖式发布（同名 tag 被覆盖），回滚回的是「名同实异」的包。
- 摘流量后立即杀进程，长连接用户请求被掐断。
- 自动回滚无审批直接跑，指标误判引发事故——回滚也要有卡点。
- 配置与代码顺序颠倒，新代码读不到新配置启动失败。

### 11. 实时大盘/实时统计系统（类双十一大屏）

> 原题要点：数据链路（埋点→采集→计算→存储→展示）各环节选型；Flink 窗口、水位线、乱序处理；UV 精确去重 Bitmap/RoaringBitmap/HyperLogLog 取舍；实时与离线对不上（Lambda/Kappa）。

#### 容量估算思路

- 设峰值埋点 500 万条/s、每条 ~1KB → Kafka 入口 ~5GB/s，topic 200+ 分区，消费者并行度对齐分区数。
- 计算后中间结果骤减（千级指标 × 秒级），存储与展示层压力极小；瓶颈全在采集与流式计算的乱序处理。

#### 架构分层设计

- 采集：端上埋点 SDK（批量上报、本地缓冲、失败重试）→ 接入网关 → Kafka。
- 计算：Flink 实时聚合（GMV、订单量、UV），维度预聚合。
- 存储：明细入 OLAP（ClickHouse/Doris）支持下钻；预聚合指标入 Redis/MySQL 供大屏接口。
- 展示：查询 API + WebSocket 主动推送（节流 2s 一次），前端数字滚动动画可再掩盖 1~2s 延迟。

#### 关键技术点

- **窗口与乱序**：用事件时间（埋点业务时间）开窗口而非处理时间；watermark = 当前最大事件时间 − 允许乱序度（5~10s），到达触发窗口计算；迟于 watermark 的数据走 sideOutput 迟到流，对已产出结果做 retract/更新修正（Doris/ClickHouse 支持更新语义）。Exactly-Once = Flink checkpoint（屏障对齐）+ 事务/幂等 sink（Kafka 事务、Doris 按批次 id 原子覆盖写）。
- **UV 去重取舍**：
  - Bitmap：精确，1 亿用户 1 亿 bit ≈ 12MB/窗口，但 uid 稀疏时内存浪费。
  - RoaringBitmap：分桶压缩解决稀疏问题，亿级可行且精确，支持交并差（多维下钻如「A 省 B 渠道 UV」），预聚合合并快；Flink/Doris/ClickHouse 均有内置支持——核心大屏首选。
  - HyperLogLog：12KB 固定内存、误差 ~0.8%，适合维度组合爆炸、允许近似的场景（页面标注估算值）。
  - 结论：核心 UV 用 RoaringBitmap 精确 + 预聚合，长尾多维探索用 HLL。
- **实时 vs 离线对不上**：Lambda 架构（实时层 + 离线层 + 服务层合并，离线 T+1 校准实时，代价两套代码）vs Kappa（只有流处理，重算靠 Kafka 回放，代价回放成本）。工程实践：大屏以实时层为准、口径明确（支付成功事件时间、不含未支付），离线 T+1 出最终报表；两者差异超阈值（如 0.5%）告警并归因。对不上的常见根因：事件时间 vs 到达时间口径不一致、迟到数据被丢、埋点丢失/重复、退款未扣减。
- **可靠性**：埋点 SDK 本地持久化防丢；Kafka 多副本；Flink 作业失败自动拉起 + RocksDB state backend + checkpoint 到 HDFS/OSS；大屏接口兜底「最新成功快照」，计算层故障时大屏不空白只停滞。

#### 追问点应答

- 零点写入洪峰？Kafka 攒批、Flink 反压 + 端上预聚合一层、OLAP 批量导入而非逐条 insert。
- 口径管理？指标定义统一在指标平台（GMV=支付成功且未退款），实时与离线共用同一口径代码，避免两套 SQL 各写各的。
- 为什么 WebSocket 而不是轮询？服务端主动推省连接峰值下的空轮询，配合 2s 节流。

#### 常见坑

- watermark 设 0 秒追实时，乱序数据大量丢失，GMV 偏小。
- 用处理时间开窗，回溯/补传埋点全进当前窗口，数据跳变。
- ClickHouse 逐条 insert，merge 压力巨大——必须攒批写。
- 实时与离线各写一套统计逻辑，口径漂移没人发现。

### 12. 开放平台 API 网关

> 原题要点：核心功能拆解（路由、鉴权、限流、熔断、协议转换、审计）与插件化设计；鉴权选型（AppKey/Secret 签名、OAuth2、JWT）；网关高可用高性能（异步非阻塞、无状态）；灰度路由、流量染色、重试副作用防护。

#### 容量估算思路

- 设对外开放 5000 个 API、峰值 50 万 QPS；网关是所有流量必经点，单机（Netty 异步、无重逻辑）透传 3~5 万 QPS，需 15~20 台 + 冗余。
- 网关每请求增加 1~2ms；鉴权/限流全部本地内存或 Redis 集群化，绝不在网关做同步重逻辑（如查 DB）。

#### 架构分层设计

- 接入层：LB → 网关集群（无状态多活）。
- 网关核心：路由匹配 → 插件链（鉴权/限流/熔断/审计…）→ 协议转换 → 转发。
- 控制面：管理后台、API/应用/策略元数据下发（配置中心，热生效）。
- 数据面依赖：密钥/路由本地缓存、限流计数（本地 + Redis 两级）、审计日志异步批投 Kafka → ES。

#### 关键技术点

- **功能拆解与插件化**：路由（path/header/权重多级匹配）、鉴权、限流、熔断、协议转换（HTTP↔Dubbo/gRPC）、审计。插件模型：责任链 Filter（pre → route → post → error 四阶段），插件实现统一接口（match() + execute()）+ 顺序注解 + 开关 + 热加载（元数据版本变更触发重建链）；插件无状态、数据走 Context 传递——新插件即插即用，故障可单独降级下线。
- **鉴权选型**：
  - AppKey/Secret + HMAC 签名：服务端到服务端（开放平台 B2B）场景；请求参数 + timestamp + nonce 做 HMAC-SHA256，服务端验签 + 时间窗（±5min）+ nonce 去重，防篡改防重放。
  - OAuth2.0：涉及最终用户资源授权（授权码模式 + access/refresh token）。
  - JWT：无状态本地验签、不查存储，适合内部服务间；注意注销（短有效期 + refresh / 黑名单）与密钥轮换。
  - 组合实践：开放 API 用 AppKey 签名（应用维度），用户态 API 用 OAuth2 换 JWT token，网关统一解析后把调用方身份注入请求头传给后端。
- **高可用高性能**：Netty 异步非阻塞（少量线程扛高并发，严禁插件内同步阻塞调用）；无状态（元数据/计数全外置）随时水平扩缩；多机房部署；控制面下发失败用「最后已知良好配置」继续服务；对象池化/堆外内存避免 Full GC；全链路超时 + 对下游熔断快速失败，防止网关线程堆积雪崩。
- **灰度路由与染色**：按规则（uid 尾号/header/地域）路由到灰度集群或稳定集群；网关入口生成 X-Trace-Tag（如 gray=1）全链路透传（服务、消息均携带），实现全链路灰度；标签同时写入审计日志便于回放定位。
- **重试副作用防护**：写请求（POST）默认不自动重试；GET 等幂等方法重试限 1~2 次 + 指数退避 + 抖动；业务要求重试写请求时，网关强制注入 X-Idempotency-Key 幂等键并透传，后端按幂等键去重；重试切实例重试 + 全局重试比例上限（如 ≤10%）防重试风暴。

#### 追问点应答

- 网关挂了怎么办？无状态多活 + LB 摘除；控制面故障只影响变更不影响转发；极端情况业务方走「直连兜底域名」逃生预案。
- 限流怎么做？单机令牌桶（本地内存，无网络开销）+ 集群精确限流（Redis + Lua，按 AppKey/API 维度）两级，Redis 故障时本地兜底。
- 协议转换？插件内做 HTTP → Dubbo/gRPC 参数映射与响应包装，schema 由控制面下发（IDL/JSON 配置）。

#### 常见坑

- 插件里同步调远程鉴权服务，一次抖动打满网关线程池，全站故障——必须本地缓存 + 超时熔断。
- 重试没有幂等键保护，下游重复扣款/重复下单。
- 配置热更新无版本回滚与灰度，一条错误路由规则让全站 404。
- 审计日志同步写成为性能瓶颈——必须异步化并区分丢弃策略（保关键审计，丢 debug 级）。
