## 一、限流（Rate Limiting）

### 算法层（必考）

**1. 四种经典限流算法追问链**

> 固定窗口突刺怎么产生；滑动窗口 LeapArray 实现；漏桶为何无法应对突发；令牌桶与 Guava RateLimiter（SmoothBursty/SmoothWarmingUp）；两者本质区别一句话。

- **固定窗口计数器**
  - 实现：一个计数器 + 窗口起始时间，窗口到期清零；内存 O(1)、实现最简单。
  - 突刺成因：限流 100/min 时，第 1 分钟最后 1 秒与第 2 分钟最前 1 秒可各放 100——两个窗口配额各自独立、时间上相邻，临界处 2 秒内最多 200 请求（临界双倍流量）。
  - 可接受场景：对瞬时毛刺不敏感的统计/配额类需求、内部异步任务；不能用于保护脆弱下游（如秒杀、DB 前置）。
- **滑动窗口计数器（Sentinel LeapArray）**
  - 实现：环形桶数组，每个 `WindowWrap` 记录 pass/block/RT 等样本；用 `当前时间 / 单桶时长` 定位桶下标，对过期桶 CAS 抢占复用；统计时累加「当前桶 + 前 N-1 桶」得到完整窗口。
  - 权衡：桶数越多，窗口切得越细、突刺越平滑、精度越高，但内存与遍历开销越大；桶数太少退化为固定窗口。Sentinel 1s 窗口默认 sampleCount=2（两个 500ms 桶），对毫秒级判定足够。
- **漏桶（Leaky Bucket）**
  - 请求先入池，以恒定速率放行，池满即拒——出口绝对平滑，本质是**整形（shaping）**。
  - 无法应对突发：出口速率恒定，突发只能排队（拉长 RT、占内存）或被拒；对需要瞬间并行的场景（开闸抢购）反而放大时延。
- **令牌桶（Token Bucket）**
  - 以恒定速率向桶投令牌（预分配），桶有容量上限；请求取到令牌即过，取不到则等待/拒绝。空闲期攒令牌 → 允许 burst 到桶容量，语义是「限平均速率 + 容忍配额内突发」，更贴近真实容量。
  - Guava RateLimiter：
    - `SmoothBursty`：标准令牌桶，按 permitsPerSecond 平滑生成，允许攒约 1s（maxBurstSeconds）的突发；
    - `SmoothWarmingUp`：预热限流——冷启动期「生成令牌的间隔由长逐渐缩短」（按平方积分爬坡），达到稳定期后速率才达标；用于服务刚启动/扩容新实例时，给缓存、连接池、JIT 预热留时间，避免一上线就被全量流量打垮。
- **本质区别一句话**：漏桶限的是「流出速率」（出口恒定、绝对平滑）；令牌桶限的是「平均流入速率」并允许配额内突发。
**2. 单机限流实现层**

> 手写并发安全令牌桶（CAS/synchronized 取舍）；Guava RateLimiter 的坑；Redis+Lua 脚本；Redis 挂了 fail-open 还是 fail-close。

- **手写并发安全令牌桶（示例）**

```java
public class TokenBucket {
    private final double capacity;      // 桶容量 = 允许的最大突发
    private final double ratePerNano;   // 每 ns 生成令牌数 = QPS / 1e9
    private double tokens;              // 当前令牌数
    private long   last = System.nanoTime();

    public TokenBucket(long qps, double burst) {
        this.capacity = burst;
        this.ratePerNano = qps / 1_000_000_000.0;
        this.tokens = burst;            // 冷启动预分配
    }

    /** 非阻塞获取，成功返回 true */
    public synchronized boolean tryAcquire() {   // 临界区仅几条指令
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - last) * ratePerNano); // 惰性补给
        last = now;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;
    }
}
```

  - 取舍：synchronized 版临界区极小、实现简单无竞态，常规 QPS（万级）吞吐足够；极高并发（百万级抢占）可换 CAS 自旋——把 `(tokens, last)` 打包成不可变快照放 `AtomicReference<Snapshot>` 做单次 CAS（避免双字段两次 CAS 的中间态竞态），代价是竞争激烈时自旋空转烧 CPU。
- **Guava RateLimiter 的坑**：单机语义——多实例部署实际阈值 = 配置值 × 实例数，不支持分布式；`acquire()` 会**阻塞当前线程**（可能占住业务线程很久），高并发入口要用 `tryAcquire(timeout)`；预支语义——允许透支未来令牌，突发后后续请求会等待补偿；无持久化与规则热更。
- **Redis + Lua 分布式限流**
  - 为什么必须 Lua：`GET → 判断 → SET` 三步非原子，并发下计数超卖；Lua 把「读-算-写 + EXPIRE」原子化，还避免「SET 后进程挂掉导致 key 永不过期」。
  - 令牌桶脚本思路：用 HASH 存 `tokens` 与 `lastRefillTs`，ARGV 传 capacity/rate/now/请求数；脚本内按 elapsed 补令牌（`min(capacity, tokens + elapsed*rate)`），够则扣减返回 1，不够返回 0；首次初始化 tokens=capacity，并设置 TTL 防冷 key 常驻。
  - 滑动窗口 ZSet 版：member=请求唯一 id、score=时间戳；脚本内 `ZREMRANGEBYSCORE` 清窗口外 → `ZCARD` 计数 → 未超限 `ZADD` + `PEXPIRE` → 返回 1。精确但每请求都写 ZSet，内存与 O(logN) 开销高，适合低频高价值接口（登录、短信、支付验证）。
- **Redis 挂了怎么办（fail-open vs fail-close）**
  - fail-open（放行）：保可用性，风险是限流失效可能压垮下游；适合 Redis 只做「防刷/配额」而非保命的场景。
  - fail-close（拒绝）：保系统不被打垮，牺牲可用性；适合下游脆弱、超限即雪崩的核心链路。
  - 工程折衷：Redis 异常时切**本地兜底限流**（阈值 = 全局阈值/实例数并放宽 1~2 倍），而非全开；对 Redis 调用本身设短超时+熔断；告警人工介入。原则：Redis 正常时严格、异常时放宽但不是裸奔。
**3. 分布式集群限流的进阶方案追问链**

> 集中式计数瓶颈；Sentinel token server 配额分割与降级；为什么「每实例限 总QPS/实例数」是错的。

- **集中式计数（Redis）**：全局精确、实现简单；但每请求一次 Redis 往返（1~3ms），Redis 单节点 10w QPS 量级即成瓶颈，热 key 与网络放大问题，且引入对 Redis 的强依赖。适合中低流量或低频接口。
- **配额分割（Sentinel 集群流控 token server）**
  - 原理：全局配额由 token server 持有，应用实例（client）每次调用向 token server 申请令牌，server 原子扣减，保证集群总 QPS 不超；部署上有独立 token server 与 embedded（内嵌选主，一实例兼任）两种模式。
  - 配额分割优化：client 可**预分配/批量申请**一段额度到本地，本地先消费、周期性向 server 汇报补充，把「每请求一次 RPC」降为「每 N 请求一次」，降低时延与 server 压力（代价是局部短暂超卖，用分割粒度换精度）。
  - 降级：token server 不可用/超时时，client 自动退化**本地限流**（阈值 = 全局阈值 / 存活实例数），即 fail-open 到本地的折衷；token server 做主备 + 故障自动切换。
- **「每实例限 总QPS/实例数」为什么是错的**
  - 流量不均：负载均衡不完美、有状态路由、波动期各实例负载差异 → 有的实例被误杀、有的实例配额浪费；
  - 实例数动态变化：autoscaling 扩缩容瞬间阈值失真（扩容后均分阈值变小、缩容后超限）；
  - 单实例被打挂后流量转移到健康实例，均分阈值照样打垮健康实例。
  - 正确姿势：全局协调者按存活实例动态分配配额 + 自适应限流（BBR 类）做容量视角兜底。
**4. 限流的位置与维度**

> 接入层与应用层分工；限流维度与热点参数限流原理；并发数限流 vs QPS 限流。

- **分工**：接入层（Nginx `limit_req`/`limit_conn`、网关）做粗粒度全局保护——IP、租户、全局 QPS，扛洪峰、防刷，离用户近先挡明显恶意流量；应用层做业务语义细粒度——接口、用户、热点参数，并能结合业务返回降级响应。原则：**越靠外越粗、越靠内越细，逐层收敛**。
- **维度**：全局 QPS（保机器容量）、单接口（保下游/DB）、单用户/单 IP（防刷防爬）、单租户（多租户公平、防邻居噪声）。
  - 热点参数限流原理：在普通滑窗之上按「参数值」再建一层统计（Sentinel ParamFlow：参数值哈希分桶计数 + 阈值 + 热身期概率放行），对单个热点值（某爆款商品 ID）单独限流，避免一个 SKU 打垮整个接口。
- **并发数 vs QPS**：QPS 是通过速率，前提是请求都「快」；慢调用时在途请求数 = QPS × RT 膨胀——QPS 不变、线程池/连接池照样被瞬间占满。并发数限流（信号量/线程池）直接约束在途请求数，慢调用也被快速拒绝。定位：**QPS 限流防「量」，并发限流防「慢」**，两者互补。

### 实战层

**5. 被限流的请求怎么处理**

> 直接拒绝 / 排队等待 / 降级响应怎么选；429 + Retry-After 的意义。

- 直接拒绝（快速失败）：立即返回不占资源——**写操作首选**（下单），宁可失败也不排队把 RT 拉爆。
- 排队等待（匀速排队 + 超时）：漏桶思想削峰填谷，适合异步/可延迟任务（积分发放、消息推送）；必须带队列长度与超时上限，防堆积传染。
- 降级响应：查询类返回缓存旧值/默认值/静态兜底。
- 选择：下单 = 快速失败 + 前端「排队/稍后重试」提示；查询 = 降级响应优先。
- 状态码：`429 Too Many Requests` + `Retry-After`——明确告诉客户端多久后再试，**防止客户端立即重试形成重试风暴**；网关层也可用 503；对内服务用错误码区分 `BLOCKED` 与业务失败，block 指标单独埋点告警。

**6. 限流阈值怎么定**

> 压测容量法、经验系数法、自适应（BBR 思想）。

- 压测容量法（首选）：对单实例/集群压测，取 **P99 RT 达标 SLA 时的最大吞吐（拐点吞吐，而非极限吞吐）**，再乘安全系数（如 80%）；有数据、可回归（每次大版本重新压）。
- 经验系数法：历史峰值 × 增长系数 × 冗余系数；无压测条件时的兜底，需留较大裕度。
- 自适应（BBR 思想 / Sentinel System Rule / BBRSentinel）：基于采样窗口的 `minRT`（历史最小 RT）与当前在途并发推算容量（BBR 取 2 倍系数，maxQps ≈ 并发数 / minRT × 2），或按 CPU 负载触发；阈值随系统真实容量自动伸缩，解决「拍脑袋阈值」。风险：抖动期推算值波动大，需平滑与下限保护。
- 落地：三者结合——压测定基线，经验系数做预估，自适应做最后防线。
**7. 场景题**

> 10w QPS 峰值、容量 6w 的逐层限流分配；IP 刷接口的两级限流 + 黑名单与 NAT 误伤。

- **大促 10w QPS、容量 6w 的逐层分配**
  - 原则：上游总闸 + **逐层收敛、每层留 buffer**（每层限流值 ≤ min(自身容量, 下层容量) × 0.9~0.95），保证下层永不被压垮。
  - 分配：网关入口 6w（等于系统容量，10w−6w 的差额在入口排队/候场消化或提前扩容）→ 服务A 6w → A→B 收敛到 5.5w（若 1 次下单触发多次调用，按调用放大系数折算）→ DB 层用连接池/并发数限制对应 5w 级别。
  - 理由：越往下修复成本越高（DB 挂了全站瘫），buffer 应对 RT 波动与重试放大；多余流量用排队/降级/候场吸收，前端配合「排队页」削峰；每层 429 + Retry-After；监控逐层 block 指标验证收敛是否符合设计。
- **IP 刷接口：两级限流 + 黑名单**
  - 网关层：`limit_req` 按 IP 限速（如 10 QPS/IP + 小额 burst），命中黑名单直接 403；黑名单来源：实时统计（Redis 计数发现超阈 IP）+ 风控规则，推送到网关（shared dict / 配置热更）。
  - 应用层：IP+接口 维度再限一次（更细），叠加「IP+用户 ID/设备指纹」维度防换 IP 绕过。
  - NAT 误伤：对已知 NAT 出口（运营商/大企业网段）白名单或放宽阈值；用多维度（设备指纹、登录用户、行为验证码）替代纯 IP 硬限；被限后返回验证码挑战而非直接拒绝，误伤可自助恢复；黑名单设 TTL + 人工审核通道，按 IP 维度 QPS 分布做告警。

## 二、熔断（Circuit Breaking）

### 模式与原理（必考）

**8. 熔断器模式追问链**

> 三态模型状态机；为什么需要熔断；半开并发探测；断路器粒度。

- **三态状态机**：
  - `Closed`（正常放行）→ 统计窗口内失败率/慢调用比例超阈值 → `Open`；
  - `Open`（快速失败，不发远程调用）→ 熔断时长到期 → `Half-Open`；
  - `Half-Open` → 放行限量探测，成功率达标 → `Closed`（重置统计）；探测失败 → 回 `Open`（重新计时）。
- **为什么需要熔断（传导路径）**：故障实例 RT 飙升 → 调用方线程被占住 → 上游重试使流量放大（重试风暴）→ 调用方线程池/连接池堆积 → 超时扩散、调用方自身也变慢 → 故障沿调用链逐级上传 → 整链雪崩。熔断在「持续失败」时切断调用，把故障隔离在第一跳，不把调用方拖死。
- **半开并发探测**：进入 Half-Open 只放行 N 个探测请求（常为 1 或小比例），其余直接快速失败/降级；用原子计数器分配探测名额（`AtomicInteger` 递减抢占）；探测成功后**渐进放量**（10%→50%→100%）恢复，避免全量流量瞬间打到刚恢复的下游（冷启动）再次打挂；探测失败立即回 Open。
- **粒度**：按服务（粗，误伤面大——一个接口故障把整个服务熔断）、按接口/方法（推荐，定位准）、按实例（配合负载均衡摘除）、按调用组（共享资源池的接口一组）。过细：规则爆炸、统计样本不足易误判；过粗：无关接口被连带熔断。折衷：核心依赖按接口建熔断器，共享同一资源池的用组粒度。
**9. 熔断判定策略追问链**

> 异常比例/异常数/慢调用比例分别适合什么故障；统计窗口与最小请求数；熔断时长怎么定。

- 异常比例：适合**快失败**类故障（抛异常、5xx）——失败返回快，占比很快反映；异常数：适合**低流量**接口（小样本下比例方差大，用绝对次数更稳）。
- **慢调用比例**：RT 超阈值的请求占比——适合**慢故障**（GC 抖动、慢 SQL、网络劣化）。慢调用更危险：不抛异常、默默占线程，线程池以「每秒新增 = QPS」的速度被占满，之后整个服务所有接口无线程可用；比快失败扩散更快且更隐蔽（监控上只见 RT 涨、错误率平）。
- 统计窗口与 `minRequestAmount`：窗口内请求数达到最小值才启用比例判定——防低峰期「2 个请求失败 1 个 = 50%」的误熔断；滑窗时长权衡「反应速度 vs 平滑度」（太短抖动误判、太长反应迟钝）。
- 熔断时长：经验起步 5~30s 或 RT 的 10~100 倍；太短 → Open/Half-Open 反复抖动（下游没恢复又被探测打）；太长 → 下游恢复后白白浪费容量。配合下游健康检查（探活先行）+ 半开渐进放量，恢复更平滑。

**10. 主流实现对比**

> Hystrix 为何淘汰；Resilience4j；Sentinel；Spring Cloud CircuitBreaker；手写简版断路器的核心并发点。

- **Hystrix**：线程池隔离 + 滑窗统计，RxJava 实现、API 重、每命令一线程池开销大，Netflix 进入维护模式被淘汰；「线程池隔离 + 舱壁」思想仍被继承。
- **Resilience4j**：轻量函数式**装饰器组合**（CircuitBreaker/RateLimiter/Bulkhead/Retry/TimeLimiter 自由堆叠），`Ring BitBuffer`（bit 数组记成功/失败，O(1) 内存）统计，零依赖，Spring Cloud 官方推荐替代品。
- **Sentinel**：LeapArray 滑窗、流控/熔断/热点/系统自适应一体、规则中心动态推送（热更）、集群流控 token server、控制台可视化；阿里大促生产验证，国内生态好。
- **Spring Cloud CircuitBreaker**：抽象层统一 API、可插拔底层（Resilience4j/Sentinel）；gRPC/Dubbo 经拦截器/Filter 集成（如 Dubbo + Sentinel Filter），RPC 框架层也可内置熔断。
- **手写简版断路器**：`AtomicReference<CircuitState>`（推荐把状态+计数+时间戳封装成**不可变 State 对象**整体替换）+ 计数器 + 时间窗口。核心并发点：
  - 状态切换的原子性：CAS 失败重读重试，避免多线程同时切换；
  - 「切状态」与「清计数」的一致性：两步操作必有中间态，必须合成一次 `AtomicReference.set`（整体替换不可变对象）；
  - Half-Open 探测名额的原子分配：`AtomicInteger` 递减抢占，防止半开期放行超额。
### 实战层

**11. 熔断对调用方的语义**

> 熔断后抛什么；怎么区分「熔断失败」与「业务失败」。

- 熔断后：Sentinel 抛 `BlockException`（DegradeException）、Resilience4j 抛 `CallNotPermittedException`，或由 fallback 转成降级响应；**不能静默吞掉**——调用方必须知道「请求根本没发出去」。
- 区分设计：错误码分层——熔断/限流是「系统级未执行」（如 `CIRCUIT_OPEN`/`RATE_LIMITED`，HTTP 503/429），业务失败是「执行了但结果错」（业务码）；监控埋点区分 **block 指标**（被熔断/限流）与 **error 指标**（业务异常）：block 突增 = 下游故障需要介入，error 突增 = 业务 bug 排查代码；两者告警对象与处理动作完全不同。

**12. 熔断与重试的配合陷阱**

> 重试风暴；retry budget；指数退避 + jitter 实现。

- 重试放大：1 次失败重试 3 次 → 故障期流量最多放大 4 倍；下游刚恢复又被重试浪潮打回去（重试风暴），熔断反复振荡。
- **重试预算（retry budget）**：窗口内按正常流量比例发重试额度（如最多 10% 正常流量），预算耗尽直接失败不再重试——保证重试总量有上界；或按实时失败率动态关闭重试。
- **指数退避 + jitter**：`sleep = random(0, min(cap, base × 2^n))`（full jitter），或 `base×2^n + random(0, base)`（equal jitter）；随机抖动打散所有客户端的重试时刻，避免「同一时刻同步重试」形成周期性波峰；设最大重试次数与总超时上限。
- 原则：只重试**幂等**请求；重试层与熔断层协同（熔断打开时重试直接短路）；**跨层重试去重**（网关重试了，RPC 框架层就不再重试——重试总次数 = 各层乘积是灾难）。

**13. 场景题**

> GC 抖动 RT 飙 3s 的完整防护链；熔断误触发调参；弱依赖「加强」还是「降级掉」。

- **下游 GC 抖动 RT 偶发 3s → 上游线程池堆积 → 全服务被拖垮的防护链**
  1. **超时收敛**（第一道，治根）：RPC 超时从默认 30s 收敛到 P99×2（如 500ms~1s），连接池借出超时；保证「单次等待有上限」，线程必然能释放；
  2. **慢调用熔断**：慢调用比例策略（RT>500ms 且占比 >50%，minRequestAmount 达标）→ Open 10s，快速失败释放线程；
  3. **半开恢复**：到期后放 1~N 个探测，渐进放量 10%→50%→100%，防下游刚恢复就被全量打回原形；
  4. **下游限流自保**：下游对上游入口限流 + 自适应（CPU/RT 触发），防上游恢复期重试放大；线程池/信号量隔离限制上游可占用的并发额度；
  5. 兜底与观测：调用方配置缓存旧值降级；线程池水位、RT 分位、block 指标告警。
  - 顺序逻辑：超时定「单请求上界」→ 熔断定「持续故障的止血」→ 半开定「恢复节奏」→ 限流定「下游自保」，四层各拦一个传导环节。
- **熔断误触发（低峰被熔断）**：根因是低峰样本少，偶发失败率/慢调用比例虚高触发判定。调参：调大 `minRequestAmount`（如 20）、拉长统计窗口、阈值留裕度；对已知流量低谷单独配时段规则；排查是否熔断器粒度过粗导致共享误伤；上线前用流量回放验证判定参数。
- **弱依赖频繁熔断：加强 or 降级（依赖分级评审）**：三个判断维度——①业务可用性是否依赖它（降级后体验损失量化）；②其故障概率/抖动频率（历史 SLA 数据）；③成本对比（扩容/优化投入 vs 降级开发量）。结论矩阵：核心体验强相关且可修复 → **加强依赖**（限流 + 扩容 + 慢 SQL 治理）；非核心且故障高发 → **降级掉**（异步化、静态兜底、砍功能）。评审结论沉淀为预案文档，随架构演进定期重审。

## 三、降级（Degradation / Fallback）

### 策略层

**14. 降级的分类追问链**

> 读降级、写降级、功能开关降级；「返回旧值」的一致性红线。

- **读降级**（牺牲新鲜度/丰富度保可用）：缓存旧值 → 默认值 → 静态兜底页 → 精简字段（个性化推荐 → 热销榜、实时评价 → 缓存总数）。
- **写降级**（牺牲实时性保写入可用）：异步化（先落 MQ/本地消息表后补，用户看到「处理中」）、限流写入、关闭非核心写入（大促关评价、关收藏）。
- **功能开关降级**：非核心功能整体关闭（关退款入口、关直播评论），把资源让给核心链路。
- **一致性红线**：价格、库存可售状态、订单金额等强一致字段**不允许返回旧值**——展示过期价格/库存会直接资损与客诉。此类字段降级 = 明确提示「暂时无法购买/价格加载中」并禁用下单，而不是回旧值。红线字段清单必须在预案中显式标注、评审确认。

**15. 降级开关的工程管理**

> 开关存哪；谁能开（审批/审计/回滚）；自动 vs 手动；预案演练。

- **存哪**：配置中心（Nacos/Apollo，秒级热更推送）+ **本地兜底文件/代码默认值**（配置中心不可用时仍能执行——开关系统自身不能成为单点）；命名带业务域+动作+场景（`degrade.order.refund.promo`），标注 owner、生效条件、**有效期**（到期自动提醒回收，防僵尸开关）。
- **谁能开**：生产开关变更走审批流 + **双人复核**；操作全量审计（谁、何时、从什么改成什么）；配置中心保留历史版本支持**秒级回滚**；高危开关接入预检查（开启前校验兜底数据存在且新鲜）。
- **自动 vs 手动**：自动降级（熔断联动、指标阈值触发）响应快，但**误降级会放大故障**（指标毛刺触发自动关闭支付入口，本来只是抖动）；折衷：低风险开关允许自动、高风险开关只告警 + 人工确认；任何自动动作必须保留人工一键恢复通道。
- **演练**：大促前按预案清单逐项演练：开开关 → 验证兜底表现（页面可用、数据新鲜度、资损校验）→ 观察监控 → 关闭恢复 → 验证恢复；结论写回预案，未演练的开关视同没有。
**16. 兜底数据从哪来**

> 静态兜底文件、多级缓存旧值、默认规则；兜底自身的可用性。

- 来源：构建期/离线**预生成静态兜底文件**（默认商品图、默认文案、离线算好的热销榜）；多级缓存的旧值；默认规则计算（默认运费、默认推荐位）。
- 兜底自身的可用性：
  - 静态文件推 **CDN 多副本多地域**，不依赖源站；
  - 旧值缓存「**逻辑不过期 + 后台刷新**」：物理 TTL 设长，逻辑上标记生成时间，由刷新任务续期，避免恰好过期；
  - 兜底生成链路本身要监控（「最后成功生成时间」告警）；
  - 兜底数据纳入演练校验（开关打开时验证兜底新鲜度），过期即告警。

### 实战层

**17. 降级的业务协商**

> 哪些功能可降是提前约定评审过的——怎么推动落地。

- 以「预案」为载体而非口头约定：拉业务方做**依赖分级评审**（核心/重要/可降三级），每个可降项写清：降级动作、用户侧表现、资损/体验影响、恢复标准；
- 产物落地为：降级预案文档 + 开关清单（配 owner/审批）+ 兜底数据（配生成链路），纳入变更管理与发布流程；
- 推动手段：新功能上线评审必须申报「可否降级、怎么降」（卡点机制）；用历史故障复盘做杠杆——「当时若有预案可 5 分钟止损」比讲道理有效；每季度/大促前重审一次。

**18. 场景题**

> 商品详情页依赖分级预案；「为什么当时没降级」三层改进；恢复顺序与预热放量。

- **商品详情页依赖分级与大促预案**
  - 库存：核心——降级为「库存紧张/到货通知」，禁下单或展示模糊库存（「有货」需合规评估）；
  - 价格：核心红线——不可降旧值，降级为「价格异常，暂时无法购买」并禁用购买按钮；
  - 推荐：可降——热销榜/默认推荐位/整模块隐藏；
  - 评价：可降——隐藏评价模块或展示缓存总数（标注「仅供参考」）。
- **P2 复盘「为什么当时没降级」三层改进项**
  - 无开关：非核心依赖上线必须申报降级开关（卡在架构评审/发布流程）；存量依赖做补开关排查清单；
  - 有开关但没演练：开关纳入大促前必演练清单；演练自动化（定期注入验证开关真实生效）；
  - 开关开了但兜底数据过期：兜底生成链路加「最后成功时间」监控告警；兜底改「逻辑不过期 + 后台刷新」；演练时校验兜底新鲜度。
- **降级恢复顺序**：先恢复「被其他链路依赖的上游」（价格/库存这类供数方）→ 再恢复流量入口功能 → 非核心最后；每步**预热放量**（先 5%~10% 流量观察 RT/错误率，再逐步 100%）——防止恢复瞬间缓存冷启动、连接池激增造成二次故障；每步之间设确认点（人工或指标自动确认）。

## 四、隔离与综合（三板斧合体）

**19. 隔离的三种手段追问链**

> 线程池 vs 信号量隔离；实例/集群隔离；数据隔离。

- **线程池隔离 vs 信号量隔离**：
  - 线程池隔离：独立线程池跑远程调用，故障不占主线程，支持排队与超时控制；代价是线程切换开销 + 线程数膨胀；适合**高扇出的远程 RPC**。
  - 信号量隔离：计数限制并发，零切换开销；适合**本地/纯内存/低开销调用**；缺点是调用线程被占住、无异步超时能力。
  - 演进：Feign 早期默认线程池（Hystrix 时代），后默认信号量（性能优先，配合熔断+超时使用）；按调用重要性选择策略。
- **实例/集群隔离**：核心服务（交易/支付）与非核心（评价/推荐）物理隔离部署，非核心故障不抢核心资源；单元化（set 化）按用户分片部署完整单元，故障爆炸半径 = 一个单元。
- **数据隔离**：核心库（订单）与统计库（报表）分离，慢查询不影响交易；读写分离——故障时读可切从库（接受旧数据）、写主库独立保护；缓存实例分池同理。

**20. 舱壁模式（Bulkhead）**

> 一句话解释 + 系统里哪些资源是隔离的，漏了哪个会连环雪崩。

- 一句话：像船的水密隔舱——把资源切分成独立隔间，一个隔间进水（故障）不会淹没整船，故障爆炸半径限制在单隔间。
- 系统中的隔离资源：线程池（每个下游 RPC 独立）、连接池（DB/Redis 分池）、缓存实例（核心/非核心分开）、MQ topic（按业务与优先级分）、部署集群（核心链路独立）、限流配额（按租户）。
- 最容易漏的：**共享的 DB 连接池 / Redis 实例**——一条慢查询或一个热 key 打满共享池，所有使用方一起挂，连环雪崩；共享 MQ topic 消费阻塞反压上游也是典型。
**21. 综合场景题（压轴）**

> 下单链路完整稳定性方案（每段依赖的限流/熔断/降级）；雪崩复盘五维改进项；演练注入点与验收标准。

- **电商核心下单链路稳定性设计**
  - 容量预估：日常峰值 × 增长系数 → 峰值（如入口 5w QPS），压测得链路容量，规划水位 ≥ 峰值 × 1.4。
  - 限流（逐层收敛）：入口网关总闸（= 容量上限 + 排队削峰）→ 订单服务 → 库存（按 1 次下单 N 次库存操作的放大系数折算 + **热点商品参数限流**）→ 券服务（配额低于订单，可降）→ 支付渠道（渠道侧配额路由）→ 风控（同步只做黑名单快查，其余异步化前置）。每层 = min(自身容量, 下层容量) × 0.9。
  - 熔断：券/风控/营销等**非强依赖**按接口配慢调用 + 异常比例熔断，半开渐进恢复；库存/价格**强依赖不熔断**（熔断即下单失败，无意义），改用限流 + 排队 + 降级应对。
  - 降级：券不可用 → 跳过用券继续下单（事后补偿差价）；推荐不可用 → 默认推荐位；评价/详情非核心模块隐藏；积分、消息通知异步化可积压。
  - 故障传导路径 × 防线：流量洪峰 → 网关限流/排队拦；下游变慢 → 超时收敛 + 慢调用熔断拦；熔断打开期 → 降级兜底拦；资源争抢 → 舱壁隔离拦；DB 过载 → 连接池隔离 + 并发数限流拦。**每道防线拦截一个传导环节，纵深防御**。
- **雪崩复盘（A 慢 → B 线程池满 → B 全接口超时 → 拖垮网关）五维改进项清单**
  - 限流：B 入口加 QPS 总闸 + 自适应限流兜底，防重试流量放大；
  - 熔断：B 对 A 的调用加**慢调用熔断**（RT 阈值 + 比例），A 慢时快速失败而非占满线程；
  - 降级：B 的非核心接口配降级开关 + 兜底数据，A 慢时返回旧值；
  - 隔离：B 按「调 A / 调其他下游」拆分线程池（舱壁），A 故障只影响调 A 的隔间；
  - 超时：B 调 A 的 RPC 超时从 30s 收敛到 P99×2（如 800ms），快速失败腾出线程；网关对请求总超时做预算约束。
- **预案有效性验证（故障演练）**
  - 注入点：延时（验超时/慢调用熔断）、异常（验异常比例熔断/重试预算）、满载（验限流闸门/自适应）、进程 Kill（验摘除与恢复）；
  - 验收标准：限流 = 被限请求 429 且系统指标不劣化；熔断 = 触发时间 < 线程池耗尽时间、恢复期无二次雪崩；降级 = 用户侧可用且无资损（价格/订单强校验）；隔离 = 非故障隔间 SLA 不受影响；超时 = 无请求等待超过上限；
  - 演练例行化：大促前全量、平时抽样，结论回流预案文档。
**22. 开放题**

> 四者各自的「第一责任」；向新人四句话讲清关系。

- 第一责任：**限流 = 保护自己**（不超自身容量）；**熔断 = 保护链路**（切断故障传导、防重试风暴，也给下游恢复空间）；**降级 = 保护体验**（牺牲功能丰富度保可用性）；**隔离 = 控制爆炸半径**（把故障限制在最小范围）。
- 四句话版本：
  1. 限流是「门口保安」：超过容量的请求进不来，保自己不被压垮；
  2. 熔断是「电闸」：下游坏了立刻跳闸，不再连坐也不去火上浇油；
  3. 降级是「备用方案」：跳闸之后生活还能继续，哪怕过得简单点；
  4. 隔离是「防火墙」：把可能着火的房间隔开，火烧不成一片。
  - 一句话总纲：**限流保自己、熔断保链路、降级保体验、隔离保半径**——四者组合成纵深防御，缺一道防线就有漏。
